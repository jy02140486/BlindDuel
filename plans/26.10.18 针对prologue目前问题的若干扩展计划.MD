# moveActorByDirection 扩展：可选 y-baseline

## 背景
序章 Charlotte 战斗退避路径中，moveActorByDirection 只做相对方向位移。
由于战斗触发器的高度（Y）不确定，夏洛特沿方向移动结束后可能仍停在战场中间的 Y 深度，
视觉上像挡在战场里而不是退到战场侧后方观战。

## 目标
在保持现有 moveActorByDirection 语义完全不变的前提下，增加一个可选的 Y 轴终点约束。
水平方向继续由 dir 决定，Y 轴独立收敛到指定基线，两者不耦合。

## 语义定义（三方共识）
- **未指定 yBaseline 时**：完全维持现有行为，方向向量同时决定水平和垂直位移。
- **指定 yBaseline 时**：
  - 水平（X）移动仍由 dir[0] 决定
  - Y 轴从动作开始时的当前 Y 位置，在 durationMs 内**线性收敛**到 yBaseline
  - 动作结束时，actor.root.position.y **必须精确等于 yBaseline**（不只是接近）
  - dir[1] 在指定 yBaseline 时**不再参与 Y 位移计算**，避免两套规则竞争
- yBaseline 是**调用方提供的世界坐标值**，moveActorByDirection 自身不推断“战场外侧”等业务语义。

## clip 配置示例
```json
{
  "type": "moveActorByDirection",
  "startMs": 10200,
  "durationMs": 500,
  "dir": [-1, -0.5],
  "yBaseline": 1.2
}
```
- 当 yBaseline 存在时，dir 的 Y 分量被忽略（仅 dir[0] 参与水平推进）
- 当 yBaseline 不存在时，完整保持现有行为（dir[0] 和 dir[1] 均参与位移）

## 实现要点

### TimelineSequencer.moveActorByDirection 内部状态扩展
start() 阶段记录 Y 收敛所需的状态量：
```
state.yStart = actor.root.position.y
state.yEnd   = clip.yBaseline
state.yStep  = (state.yEnd - state.yStart) / durationMs
state.useYBaseline = typeof clip.yBaseline === 'number'
```

### update() 阶段 Y 轴分岔
```
if (state.useYBaseline) {
    // X: 继续按 dir 水平分量
    actor.root.position.x += state.nx * speed * dtSec
    // Y: 用线性收敛替代 dir[1] 位移
    actor.root.position.y = state.yStart + state.yStep * localMs
} else {
    // 原有行为不变
    actor.root.position.x += state.nx * speed * dtSec
    actor.root.position.y += state.ny * speed * dtSec
}
```

### end() 阶段精确保底
```
if (state.useYBaseline) {
    actor.root.position.y = state.yEnd  // 消除浮点累积误差，确保精确落位
}
```

### 对现有调用方的影响
- 不传 yBaseline：行为零变化，所有现有 sequence 继续正常运行
- 不修改 dir 向量的解释（水平语义不变），只是额外加了一条 Y 收敛路径

## 不在本次实现范围内的内容
- dir 非水平时的特殊处理（beat'em up 视角下 dir 天然以水平为主）
- 运行时动态计算 yBaseline（调用方自己提供）
- 与 FollowingBehavior offset 的整合（见下方第二部分）
- Charlotte idle→observe 表现问题（见下方第三部分，非 P2 待定）

# FollowingBehavior：打通 NpcDef→Behavior 的 offset 配置链路

## 背景
序章第一场战斗中，intro 结束后敌人直接位于镜头可见范围内。
Charlotte 作为回避战斗的同伴，此时走在主人公右侧（targetOffsetX=2.0 默认值）表现得像引路 NPC，
与“大敌当前应退到侧后方”的剧情语义矛盾。

第二场 tutor 战斗距离较远，同样的默认 offset 表现合理。
两场差异本质是 **scenario 不同 → 需要不同的 followOffset**。

## 现状
FollowingBehavior 内部已经接受 options 参数（targetOffsetX / targetOffsetY），
但 NpcController 创建 FollowingBehavior 时没有传入任何参数，
导致所有 NPC 共用内部默认值 { targetOffsetX: 2.0, targetOffsetY: 0 }。

这是一条典型的**有行为能力缺配置通路**的问题。

## 设计原则（三方共识）
- FollowingBehavior 是纯行为策略层，只认 options 参数，**不读 scenario / worldState / 剧情状态**
- scenario→offset 的映射属于 NPC 实例配置层（NpcDef 的职责）
- 采用与 aiTuningOverrides 完全相同的模式：实例声明自己的行为偏好，未声明则兜底默认

## 配置方案
在 NpcDef 中为 initialStateMap 的条目增加 followOffset 字段：
```json
{
  "initialStateMap": [
    { "if": { "scenarioMin": 1, "scenarioMax": 3 }, "state": "following", "followOffset": { "targetOffsetX": -1.8, "targetOffsetY": 0.3 } },
    { "if": {}, "state": "idle" }
  ]
}
```
- followOffset 是可选字段；不存在时沿用 FollowingBehavior 内部默认值
- 条件评估仍走现有 _matchCondition 机制

## 实现链路

### NpcController.applyInitialState(npc, worldState, hero)
命中 following 条目时，将 followOffset 传入 FollowingBehavior 构造：
```
// 现有
this._followingBehavior = new FollowingBehavior();

// 改为
const followOpts = { ...(entry.followOffset ?? {}) };
this._followingBehavior = new FollowingBehavior(followOpts);
```

### applyInitialState 内 teleport 逻辑同步
现有 teleport 到 hero 旁的 offsetX 读取：
```
const offsetX = this._followingBehavior?.options?.targetOffsetX ?? 1.0;
```
此处已有 fallback，followOffset 传入后会自动生效，无需额外改动。

## 不在本次实现范围内的内容
- offset 从世界坐标升级为相对朝向（当前 beat'em up 视角不涉及 180° 转身）
- sequence 运行时动态修改 offset（属于后续扩展点，不进本次）
- sequence 运行时动态修改 offset（属于后续扩展点，不进本次）

# IdleBehavior：NpcDef 配置 scenario→idleClip 条件映射

## 背景（与 FollowingBehavior offset 同源）
序章 intro 结束后 Charlotte 进入观察态（observe clip）——角色原地张望、左右观察。
序章第一场战斗敌人已在镜头内，此时大敌当前，这个观察姿态表现不合时宜，应该用普通待机制式。

第二场 tutor 战斗距离较远，observe 表现合理。
两场差异本质是 **scenario 不同 → 需要不同的待机动画**。

## 设计原则（三方共识）
- **不在 IdleBehavior 内部写条件**。IdleBehavior 只做一件事：根据传入的 clip 参数进入对应状态。
  硬编码 scenario 判断会让 IdleBehavior 膨胀成条件垃圾桶，是特事特办。
- scenario→clip 的条件判断归属 **NpcController.enterIdle**——它天然持有 worldState 和 npcDef，
  复用已有的 _matchCondition 机制，条件匹配后把 clip 传给 IdleBehavior。
- 与 FollowingBehavior followOffset 完全同款的设计模式：NpcDef 声明 scenario→行为参数的映射，
  NpcController 执行条件解析，Behavior 层只认参数不认 scenario。

## 配置方案
在 NpcDef 的 `idle` 字段里增加 `clipMap` 条件列表（可选，缺省行为完全不变）：
```json
// NpcDef（companion）
{
  "kind": "npc",
  "controller": "npc",
  "idle": {
    "clip": "observe",
    "clipMap": [
      { "if": { "scenarioMin": 102, "scenarioMax": 103 }, "clip": "idle" },
      { "if": {}, "clip": "observe" }
    ]
  }
}
```
- `idle.clip` 是兜底值（clipMap 全部不命中时使用），保持向后兼容
- `clipMap` 的 `if` 字段完全复用 NpcController 已有的 `_matchCondition` 机制
- 条件列表按声明顺序匹配（与 initialStateMap 一致），首个命中的 clip 生效
- **后续扩展**：不止 scenario——任何现有 condition 都能触发 idle clip 切换（flag、quest、scenario 范围）

## 实现链路

### NpcController 构造时
```
// 现有
const idleClip = npcDef?.idle?.clip ?? "idle";
this._idleBehavior = new IdleBehavior({ clip: idleClip });

// 不变，clip 仍来自 npcDef.idle.clip（兜底值）
```

### NpcController.enterIdle(npc) 时
每次进入 idle 都重新解析 clip（scenario/flag 可能已变化）：
```
enterIdle(npc) {
    // 新增：动态解析 clip
    const def = this.npcDef?.idle;
    let clip = def?.clip ?? "idle";
    if (Array.isArray(def?.clipMap) && def.clipMap.length > 0) {
        for (const entry of def.clipMap) {
            if (this._matchCondition(entry.if)) {
                clip = entry.clip ?? clip;
                break;
            }
        }
    }
    this._idleBehavior.options.clip = clip;  // 更新 Behavior 参数
    this._idleBehavior.enter(npc, {});        // 其余 enterIdle 逻辑不变
}
```

## 与 FollowingBehavior followOffset 的对称关系

| 维度 | FollowingBehavior offset | IdleBehavior idleClip |
|---|---|---|
| Behavior 层已有能力 | options.targetOffsetX/Y | options.clip |
| 缺的是 | NpcDef→Behavior 配置通路 | NpcDef→Behavior 配置通路 |
| scenario 差异表达 | NpcDef.initialStateMap[].followOffset | NpcDef.idle.clipMap |
| 解析时机 | applyInitialState 一次性构造 | enterIdle 每次动态解析（支持运行时 scenario 变化） |
| 执行层 | NpcController 传入 options | NpcController 更新 options.clip |
| Behavior 层改动 | 零（已 options 驱动） | 零（已 options 驱动） |

## 为什么不是特事特办
- 这个配置表达的是**稳定独立的概念**：同一个 NPC 在不同剧情阶段可能有不同的待机动画选择
- 任何有多个待机 clip 的 NPC 都能受益（Charlotte 有 idle/observe，未来 merchant 也可能有 idle/greeting 两态）
- 条件判断完全走通用 _matchCondition 机制，不引入新特判

## 不在本次实现范围内的内容
- 自动触发（stateGraph transition）而非手动 enterIdle 的场景
- sequence 运行时临时覆盖 idle clip（可作为后续扩展，类似 moveActorByDirection 加 yBaseline 的做法）
- 与社交层（greeting 气泡）的整合（greeting 是 NpcController 独立状态，不走 enterIdle 链路）
