# 投掷物拾取-消耗逻辑

> 状态：方案已定稿（GPT 评审通过） | 创建：2026-10-03
> 前置：投掷物基础逻辑（Projectile + ProjectileManager + ProjectileContactResolver）已完成；PickableEntity + InventoryManager + ExploreMode 拾取序列已完成

---

## 1. 背景与目标

投掷物系统已有完整的飞行-碰撞闭环，但缺少**弹药限制**和**拾取→消耗**的数据通路：
- 当前 BattleMode.#onThrowRelease() 只要动画事件触发就 spawn Projectile，无任何前置检查
- 主人公需要先在探索模式捡到 dagger pickable，才能在战斗中拥有 1 发投掷弹药
- AI 具备投射能力时，弹药数直接在 BattleDef 里配置，不走拾取

## 2. 已确认的设计决策

### 2.1 弹药模型：独立计数器（B）

弹药由 ThrowComponent 独立维护，不直接等于背包物品数。玩家路径和 AI 路径分别初始化：
- **玩家路径**：BattleMode.enter() 时从 `inventoryManager.getThrowables('dagger').length` 同步到 ThrowComponent.ammo
- **AI 路径**：BattleMode.enter() 时读 BattleDef combatant 的 `throwAmmo` 字段直接赋值

选 B 而非 A（ammo = 背包 count）的唯一理由：AI 没有背包，需要一个统一接口让玩家和 AI 都通过 `character.throwComponent.ammo` 访问弹药数。

### 2.2 投掷 Gate：ammo=0 连动画都不进

在 CombatCharacter._matchesTransitionCondition 中，throw command 的 transition 评估额外检查 canThrow()。拦截点和现有 canAct()（全局 CD）同层：

```
command → transition 评估链：
  canAct() ?           ← 已有（全局 CD 闸门）
  canThrow() ?         ← 新增（ammo > 0）
  has pendingCommand ? → 进入 throw 状态 → 动画
```

### 2.3 消耗时机：release 帧同步扣减（原子性保证）

ammo 和背包物品在 release 成功后**同步扣减**，保持 1:1 比例。

关键约束：ThrowComponent.release(context) 必须在 ProjectileManager.spawn() 成功返回后才消耗 ammo。
如果 spawn 失败（scene missing 等边界情况），release() 返回 false，ammo 和背包都不扣。

### 2.4 战斗间弹药：每次 BattleMode.enter() 从背包重新同步

背包在 release 时已经 remove（如果扔了的话），下次 enter 自然拿到剩余 count。不做持久化。

### 2.5 cooldown：暂时不加

现阶段动画播放时间 + 公共招数 CD（canAct 里的 globalCooldownMs）已够用，不额外加投掷专属 cooldown。

### 2.6 AI 弹药：BattleDef combatant 里写 throwAmmo 字段

BattleMode.enter() 遍历 combatants 时，读 `combatant.throwAmmo` 直接配置。不动 AIKnowledgeRegistry 层。

### 2.7 ThrowComponent 归属：混合模式

**语义归 Character，生命周期归 BattleMode**：
- CombatCharacter 加 `throwComponent = null` 可选字段（和 `_battleYMin/_battleYMax` 同构，不是构造时装配的核心组件）
- BattleMode.enter() → new ThrowComponent() → character.throwComponent = ... + 初始化 ammo
- BattleMode.exit() → character.throwComponent = null
- 理由：BattleMode 不应该知道"怎么投飞刀"的细节；但 ThrowComponent 只在战斗中有用，不需要 ExploreMode 也挂着

### 2.8 release() 路由 + Inventory 同步边界

BattleMode.#onThrowRelease() 不再直接 spawn，而是通过 ThrowComponent.release(context) 间接调用：

```
AnimationEvent: throw_release
  → BattleMode.#onThrowRelease(payload)
      → 验证 thrower 是本场 combatant
      → 组装 context: { projectileManager, dirX }
      → thrower.throwComponent.release(context)
          ├─ ammo > 0 ？
          ├─ 自己生成 dagger spawn config
          ├─ projectileManager.spawn(config)
          ├─ consumeAmmo()
          └─ return boolean
      → if (success) inventoryManager.removeItem("dagger")
```

ThrowComponent **不依赖 InventoryManager**。Inventory 同步完全由 BattleMode 负责，依据 release() 的 boolean 返回值决定是否扣减。

## 3. 数据流总览

```
【探索模式】
  PickableEntity(dagger_pickup)
    → ExploreMode._startPickupSequence()
    → consumeType === "pocket"
    → InventoryManager.addItem(dagger{throwable:true})
    → InventoryBar UI +1 图标

【进入战斗】BattleMode.enter()
  遍历 combatants：
    if 玩家英雄:
        throwComponent.ammo = inventory.getThrowables('dagger').length
    if AI && battleDef.combatant.throwAmmo != null:
        throwComponent.ammo = battleDef.combatant.throwAmmo

【战斗中投掷】
  PlayerController.pushCommand("throw")
    → StateGraph transition 评估
      → CombatCharacter._matchesTransitionCondition
        → canAct() + canThrow() + hasCommand
    → 条件全中 → throw 状态 → throw 动画
      → AnimationEvent: throw_draw   → 创建 carry sprite（已有）
      → AnimationEvent: throw_release → BattleMode.#onThrowRelease()（已有，改造路由）
                                       → throwComponent.release(context) → spawn + consumeAmmo（新增）
                                       → success → BattleMode 调 inventory.removeItem（新增）

【战斗退出】BattleMode.exit()
  遍历 combatants → character.throwComponent = null
  背包已在 release 时同步扣减
```

## 5. 架构约定摘要

### ThrowComponent 职责边界
| 负责 | 不负责 |
|------|--------|
| ammo 计数 + canThrow() | Projectile 生命周期（ProjectileManager 的活） |
| release(context) → spawn + consume | Inventory 管理（探索侧系统） |
| dagger projectile 的 spawn config | 投掷方向计算（BattleMode 算好 dirX 传进来） |

### BattleMode 职责边界
| 负责 | 不负责 |
|------|--------|
| 接收 AnimationEvent + 验证事件来源 | dagger 的具体 spawn config |
| 组装 release context（dirX、projectileManager） | ammo 消耗规则 |
| InventoryManager.removeItem 同步 | Projectile 创建 |
| ThrowComponent 装配 / 初始化 / 销毁 | |

### CombatCharacter 新增字段
| 字段/方法 | 类型 | 说明 |
|-----------|------|------|
| `throwComponent` | `ThrowComponent \| null` | 可选，BattleMode 在 enter 时赋值、exit 时置 null |
| `canThrow()` | delegate | 直接 return `this.throwComponent?.canThrow() ?? false` |

## 7. 实现步骤

> 核心原则：**先增量后改量**。先建新文件/加字段（零影响现有代码），再装配，最后才动现有可跑的 #onThrowRelease 路由。每步改完单独验收。

### Phase 1：数据层准备（零风险，纯增量）

- **改动**：`Data/ItemDefs.js` — dagger 条目加 `throwable: true`
- **验收**：console `inventoryManager.getThrowables()` 能搜到 dagger
- **依赖**：无

#### Step 2：确认 tavern hall dagger pickable 配置
- **动作**：SceneDefs/*.json 里已有 pickable 的 itemDef.itemId 确认为 `"dagger"`（和 ItemDefs 对应）
- **验收**：无（数据确认，不写代码）
- **依赖**：无

---

### Phase 2：ThrowComponent 组件实现（自包含，不接现有链路）

#### Step 3：新建 ThrowComponent.js
- **改动**：`scripts/Systems/ThrowComponent.js`（**新增**）
- **核心成员**：
  - `ammo`（number）
  - `canThrow()` → `return this.ammo > 0`
  - `consumeAmmo()` → `this.ammo = Math.max(0, this.ammo - 1)`
  - `release(context)` → 内部搬 BattleMode.#onThrowRelease 现有硬编码 dagger spawn config（**原封不动搬，不准改参数**），流程：
    1. `this.ammo <= 0 → return false`
    2. `context.projectileManager.spawn(config)` → 存 result
    3. `if (!result) return false`（原子性保证：spawn 失败不扣）
    4. `consumeAmmo()`
    5. `return true`
- **验收**：手动实例化 → canThrow/consume 行为正确；mock spawn 返回 null → ammo 不扣
- **依赖**：Step 1（spawn config 里的 projectile spriteUrl 已存在）

---

### Phase 3：CombatCharacter 侧接入（增量，不影响现有战斗）

#### Step 4：CombatCharacter 加 throwComponent 字段 + canThrow delegate + gate
- **改动**：`scripts/Enties/CombatCharacter.js`
- **核心动作**：
  1. 加 `this.throwComponent = null;`（和 `_battleYMin/_battleYMax` 同层，不是构造时装配的核心组件）
  2. 加 `canThrow()` → `return this.throwComponent?.canThrow?.() ?? false;`（**null 安全**，没装配的角色直接返回 false）
  3. `_matchesTransitionCondition(condition)` command 分支里加：
     ```js
     if (condition.command === "throw" && !this.canThrow()) return false;
     ```
     位置：canAct() 检查之后、hasCmd 检查之前（和 canAct 同层）
- **验收**：
  - 没装配 throwComponent 的角色 → canThrow() 返回 false → throw command transition 被拦截（console 手动 pushCommand("throw") → 不进 throw 状态）
  - 手动给 character.throwComponent = new ThrowComponent({ammo:1}) → canThrow() true → transition 能过
- **依赖**：Step 3

---

### Phase 4：BattleMode 装配 + release 路由重构（核心，先装后改）

#### Step 5：BattleMode.enter() 装配 ThrowComponent + 初始化 ammo
- **改动**：`scripts/Systems/Modes/BattleMode.js`
- **核心动作**：
  - import ThrowComponent
  - enter() 里新增装配逻辑：
    ```js
    for (const c of this._combatants ?? []) {
        // 玩家：从背包同步
        if (c.kind === "player" && inventoryManager) {
            const ammo = inventoryManager.getThrowables("dagger").length;
            c.throwComponent = new ThrowComponent({ ammo });
        }
        // AI：从 battleDef 读 throwAmmo
        else if (c.kind !== "player" && battleDef?.combatants?.[c.id]?.throwAmmo != null) {
            c.throwComponent = new ThrowComponent({ ammo: battleDef.combatants[c.id].throwAmmo });
        }
    }
    ```
  - exit() 里加清理：遍历 combatants → `c.throwComponent = null;`
- **验收**：进战斗后 console 看 `hero.throwComponent.ammo` → 从背包 dagger 数量正确同步；AI 没配置 throwAmmo → throwComponent=null → canThrow() false
- **依赖**：Step 4
- **注意**：**这一步先不改 #onThrowRelease**，跑通装配链路再动 release 路由

#### Step 6：#onThrowRelease 路由重构（最高风险步骤，改完立刻测）
- **改动**：`scripts/Systems/Modes/BattleMode.js`（同一个文件，最小改动）
- **核心动作**：
  - **先保留 carry sprite dispose**：现有 `#disposeCarriedSprite(thrower.id)` 这句**保留在最前面**（在调 release 之前就 dispose）—— carry sprite 是视觉，和 release 成败无关
  - **删掉原有硬编码 spawn 块**（已搬去 ThrowComponent.release 里）
  - **新增路由逻辑**：
    ```js
    const tc = thrower.throwComponent;
    if (!tc) { console.warn("[BattleMode] throw_release but no ThrowComponent on", thrower.id); return; }
    const dirX = opponent ? Math.sign(opponent.root.position.x - thrower.root.position.x) : 1;
    const success = tc.release({ projectileManager: this._projectileManager, dirX });
    if (success && thrower.kind === "player") {
        inventoryManager?.removeItem("dagger");
        inventoryBar?.update(inventoryManager.items);
    }
    ```
- **验收（核心链路）**：
  1. ammo=0 → pushCommand("throw") → 连 throw 状态都不进 → gate 生效
  2. ammo>0 → 进 throw 动画 → throw_draw 创建 carry sprite → throw_release → spawn 成功 → ammo 归零 → 背包 dagger 减 1
  3. spawn 失败（手动 mock projectileManager.spawn 返回 null） → release 返回 false → ammo 不减 → 背包不减
- **依赖**：Step 5

## 8. 风险控制

| 风险 | 防护 | 在哪步 |
|------|------|--------|
| ThrowComponent.release 里的 spawn config 和原 BattleMode 不一致 → projectile 行为变了 | 原封不动搬 BattleMode.#onThrowRelease 里的硬编码参数（velocity、arcHeight、gravity 全保留） | Step 3 |
| canThrow() 在 throwComponent=null 时抛错 | 用 optional chaining `throwComponent?.canThrow?.() ?? false` | Step 4 |
| 改完 #onThrowRelease 整个投掷链路断了 | Step 6 先 dispose carry sprite（保留原有视觉行为），再路由到 release；改完立刻测完整路径 | Step 6 |
| 玩家没捡 dagger → 战斗里 ammo=0 → throw command 被拦截 | gate 逻辑正确 | Step 4 + Phase 6 验收 |
| spawn 失败时 ammo 被白白扣 | release() 里 spawn 非 null 才 consume | Step 3 |
