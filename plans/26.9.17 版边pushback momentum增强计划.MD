# 版边 Pushback Momentum 增强 — 实施计划

> 目标：边界场景下 attacker 被反推的距离 = victim 没推出去的量 + attacker 攻击动作剩余前冲距离
> 核心设计：从攻击者攻击动作的 frameSpeeds 自动推导剩余前冲动量，叠加到 boundary compensation 上
> 范围：**只做 hit 立即路径**，clash/parry 延迟路径不动（clash 状态自身 frameSpeeds 已有后退，暂时够用）

---

## 1. 问题诊断

### 1.1 当前边界 pushback 只守恒 victim 没推出去的量

上一份计划（`26.9.16 版边pushback，hitstopframes分招式配置计划.MD`）Step 2 的 Boundary compensation 算法是**纯守恒**：

```
residual = requested - victimActualX       ← victim 被墙挡住没推出去的量
attackerCompX = clamp(-sign(requested) × abs(residual), attackerAvailable)
```

Victim 撞墙 0.18m knockback 只被推出去 0.03m → residual 0.15m → attacker 只被反推 0.15m。

但 attacker 的攻击动作此时可能还在往前冲——比如 `zornhut` 的 frameSpeeds `[0.4, 1.2, 0, 2.4, 0.4]`，如果命中在 frame 2，还剩 `[2.4, 0.4]` 没走完——这部分前冲动量没有被计入反推。

### 1.2 直观体感

- **边界场景下 attacker 反推不够远**——重招撞墙时 attacker 应该被"弹开"得更远，感觉像是被反击力道压退
- **前冲猛的招式碰墙反推应该更远**，前冲分散的招式反推应该更近——这个差异当前表达不出来

### 1.3 根因

ImpactMovementResolver 的 residual 计算只管了"victim 这侧的守恒"，但没有管"attacker 自己前冲的 momentum"。

---

## 2. 架构决策

### 2.1 不打破守恒，而是扩大"守恒"的范围

原来的守恒：`victim 没推出去的量 → 全部转给 attacker`

新的守恒：`victim 没推出去的量 + attacker 剩余前冲动量 → 统一转给 attacker（clamp 到 attacker 边界）`

两边都是"attacker 最终被反推的量"，合并后统一 clamp，总量不做截断。

### 2.2 剩余前冲动量的推导方式

**从攻击者当前攻击状态的 frameSpeeds 自动推导**，不需要手动配置：

```
剩余前冲动量 displacement = Σ(frameSpeeds[i] × dtSec)
其中：
- i 从 (currentFrameIndex + 1) 到 frameSpeeds.length - 1
- 只累加正值（前向速度），负值是回退帧，不算
- dtSec = 1/60（固定 60fps，和 CharacterBase._applyMovement 一致）
```

**为什么从 currentFrameIndex+1 开始？**

`CharacterBase.fixedUpdate` 调用链：

```
animation.fixedUpdate → frameIndex 推进到新帧
_applyMovement → position.x += frameSpeeds[新frameIndex] * dtSec   ← 当前帧已被消费
```

CombatSystem.fixedUpdate 在 Character.fixedUpdate 之后执行（见 BattleMode 调用顺序），命中发生在新帧之后，所以当前帧的 frameSpeed 已经被消费了。剩余帧从 `currentFrameIndex + 1` 开始。

### 2.3 自动分招式的效果

| 招式 | frameSpeeds | 假设命中帧 | 剩余前冲 displacement |
|------|-------------|-----------|----------------------|
| zornhut（重斩） | `[0.4, 1.2, 0, 2.4, 0.4]` | frame 2（前冲刚要爆发） | (2.4 + 0.4) × 0.01667 = **0.047m** |
| quart（刺击） | `[0.4, 0, 0.2]` | frame 0（刚起势） | (0 + 0.2) × 0.01667 = **0.003m** |
| nachschlag（重劈收尾） | `[0, 0, 0.2, 0.7, -0.4]` | frame 3（刚劈完） | 只有 -0.4（负值不算）= **0m** |

**前冲猛的招式 residual pushback + momentum pushback 叠加 → 反推更远；
前冲分散或已经走完的招式 momentum 贡献小 → 反推主要靠 residual**。

**不需要手动配置每招的 pushback 值**——从攻击动作本身自动推导出来。

### 2.4 ImpactMovementResolver 扩展但不改定位

ImpactMovementResolver 仍然是**纯边界求解器**——它不知道 StateGraph、不知道 ContactResolver。

只是多接受一个已经算好的 `attackerAdditionalPushbackX`（momentum pushback），和 residual pushback 合并后统一 clamp attacker 边界。

### 2.5 Impact 配置可选加 pushbackMultiplier（调体感用）

StateGraph 的 `impact` 里可以加一个可选系数：

```json
"impact": {
    "knockback": 0.18,
    "hitstopFrames": 10,
    "pushbackMultiplier": 1.0
}
```

- 默认 1.0：完全自动推导
- > 1：反推更猛
- < 1：弱化反推
- 不填 = 1.0

**这个系数只影响 momentum pushback 部分，不影响 residual 守恒部分**（守恒是物理直觉，不应该被打破）。

### 2.6 不做的事（明确排除）

| 不做 | 原因 |
|------|------|
| clash/parry 延迟路径 boundary compensation | clash 状态自身 frameSpeeds 已有后退（LongSwordMan `[-1,0]`，RabbleStick `[1,0]`），post-combat clamp 兜底不飞出边界；clash 远少于 hit，暂时够用 |
| ImpactContext 扩展 attackerId | 上面排除 clash/parry → TimeControlSystem 不碰 |
| BattleMode 传 worldContext | 上面排除 clash/parry → CombatCharacter.fixedUpdate 不改签名 |
| 全局 CombatTuning 加 pushbackMultiplier | 改为分招式 impact 字段，更灵活 |
| 破坏守恒（让 residual 部分也乘系数） | 物理直觉的守恒感很重要，只对 momentum 部分加系数 |

## 3. 实施步骤

### Step 1：CombatCharacter 加 `getRemainingAttackMomentumDisplacement()`

**文件**：`scripts/Enties/CombatCharacter.js`

在类的公开方法区域（`getCombatSnapshot` 附近）新增：

```js
/**
 * 计算当前攻击动作还没走完的前冲 displacement（单位：米）
 * 只统计 frameSpeeds 中当前帧之后的正值（前向速度），负值回退帧不算
 * 如果当前不在 attackActive 状态或无 frameSpeeds，返回 0
 */
getRemainingAttackMomentumDisplacement() {
    const state = this.currentStateDef;
    if (!state?.attackActive || !state?.frameSpeeds) return 0;

    const frameSpeeds = state.frameSpeeds;
    const frameIndex = this.animation.currentFrameIndex;
    const dtSec = 1 / 60; // 固定 60fps，和 CharacterBase._applyMovement 一致

    let remaining = 0;
    // 从当前帧+1 开始（当前帧已被 _applyMovement 消费），算到 frameSpeeds 末尾
    for (let i = frameIndex + 1; i < frameSpeeds.length; i++) {
        const v = frameSpeeds[i];
        if (v > 0) remaining += v * dtSec;
    }
    return remaining;
}
```

### Step 2：ImpactMovementResolver 扩展参数

**文件**：`scripts/Systems/ImpactMovementResolver.js`

`resolve` 方法签名新增 `attackerAdditionalPushbackX = 0`：

```js
static resolve({ attacker, victim, victimKnockbackX, boundary, attackerAdditionalPushbackX = 0 }) {
```

在 residual 计算之后，把两个 pushback 合并：

```js
// 原来的 residual → attackerRequested
const attackerRequested = -Math.sign(requested) * Math.abs(residual);

// 新增：把 momentum pushback 加进来（已经是带符号的）
const totalAttackerRequested = attackerRequested + attackerAdditionalPushbackX;

if (Math.abs(totalAttackerRequested) < 1e-6) {
    return { victimActualX, attackerCompX: 0 };
}

// 后续 clamp attackerAvailable 不变，但用 totalAttackerRequested 替代原来的 attackerRequested
const attackerDir = Math.sign(totalAttackerRequested);
// ... attackerAvailable 计算不变 ...
const attackerMagnitude = Math.min(Math.abs(totalAttackerRequested), Math.abs(attackerAvailable));
const attackerCompX = Math.sign(totalAttackerRequested) * attackerMagnitude;
```

### Step 3：CombatSystem hit handler 接线

**文件**：`scripts/Systems/CombatSystem.js`

在 hit handler 的 ImpactMovementResolver 调用块（约 line 88-93）之前，新增 momentum pushback 计算：

```js
if (boundary && attackerId && finalKnockbackX !== 0) {
    const attacker = characters.find(c => c?.id === attackerId);
    if (attacker) {
        // ===== 新增：momentum pushback =====
        const momentumDisp = typeof attacker.getRemainingAttackMomentumDisplacement === "function"
            ? attacker.getRemainingAttackMomentumDisplacement()
            : 0;
        const dir = Math.sign(target.root.position.x - attacker.root.position.x); // attacker → victim
        const pushbackMultiplier = effect.context?.pushbackMultiplier ?? 1.0;    // 从 impact override 读
        const momentumPushbackX = momentumDisp > 0
            ? (-dir) * momentumDisp * pushbackMultiplier : 0;
        // =================================

        const result = ImpactMovementResolver.resolve({
            attacker,
            victim: target,
            victimKnockbackX: finalKnockbackX,
            boundary,
            attackerAdditionalPushbackX: momentumPushbackX,  // 新增参数
        });
        finalKnockbackX = result.victimActualX;
        if (result.attackerCompX !== 0) {
            attacker.root.position.x += result.attackerCompX;
            attacker._suppressFrameSpeeds = true; // 已有逻辑：enterState 自动清零
        }
    }
}
```

**注意**：`pushbackMultiplier` 需要 CombatSnapshot 把它传到 effect.context 里。需要确认 ContactResolver 读了 StateGraph impact 后把 pushbackMultiplier 也写进 effect.context。

### Step 4：CombatSnapshot → ContactResolver → effect.context 传 pushbackMultiplier

2. `ContactResolver` 构建 hit effect 时是否把 snapshot 里的 impact.pushbackMultiplier 写进 effect.context？

**如果当前 impact 只传了 knockback 和 hitstopFrames，需要补上 pushbackMultiplier**。

## 4. Impact Movement Resolver 完整推导链（更新版）

```
输入：
  victimKnockbackX = contactResolver 已算好的带符号 intent
  attackerAdditionalPushbackX = -dir × momentumDisp × pushbackMultiplier（带符号）

Step 1 — Victim 侧（不变）
  dir = sign(victim.x - attacker.x)          // 战斗接触方向
  requested = victimKnockbackX                 // 已带符号
  victimAvailable = dir > 0 ? (maxX - victim.x) : (victim.x - minX)
  victimMagnitude = min(abs(requested), abs(victimAvailable))
  victimActualX = sign(requested) × victimMagnitude

Step 2 — Residual + Momentum 合并
  residual = requested - victimActualX
  attackerResidualPushback = -sign(requested) × abs(residual)  // 带符号
  totalAttackerRequested = attackerResidualPushback + attackerAdditionalPushbackX  // 新增：合并
  if abs(totalAttackerRequested) < 1e-6 → return { victimActualX, attackerCompX: 0 }

Step 3 — Attacker 边界 clamp
  attackerDir = sign(totalAttackerRequested)
  attackerAvailable = attackerDir > 0 ? (maxX - attacker.x) : (attacker.x - minX)
  attackerMagnitude = min(abs(totalAttackerRequested), abs(attackerAvailable))
  attackerCompX = attackerDir × attackerMagnitude

输出：
  { victimActualX, attackerCompX }
```

## 5. 验证 Checklist

- [ ] 开阔地命中：victim 正常被推，attacker 不被反推（residual=0，momentum pushback 也被 ImpactMovementResolver clamp 到 0 因为 attacker 边界够？不对——开阔地时 boundary 应该也有，只是 victimAvailable 够大 → residual=0 → totalAttackerRequested = 0 + momentumPushbackX → 还是会有反推！**这是预期行为**——开阔地也有轻微反推，因为 attacker 的前冲动量被"卸掉"了
- [ ] 边界命中：vicim 被墙挡住，attacker 被反推 = residual + momentum
- [ ] attackerCompX 不会把 attacker 推出边界
- [ ] _suppressFrameSpeeds 在 enterState 时自动清零（已有逻辑）
- [ ] 连续命中同一 attacker：每次都算新的 momentum pushback（基于当前帧位置）
- [ ] hitstop 结束后 attacker 不会被 frameSpeeds 推回来（_suppressFrameSpeeds 保持到攻击状态结束）
- [ ] clash/parry 行为**完全不变**（本计划不改它们的路径）

## 6. 和上一份计划（26.9.16）的关系

上一份计划做的是 **Boundary Compensation 架构**——ImpactMovementResolver、CombatSnapshot impact 字段、post-combat clamp 都是那份的产出。

这份计划是它的**增量扩展**：在已有的 Boundary Compensation 之上，额外加了 Momentum Pushback。两份计划在 ImpactMovementResolver 的集成点就是 `attackerAdditionalPushbackX` 参数——传 0 就和上一份行为完全一致。
