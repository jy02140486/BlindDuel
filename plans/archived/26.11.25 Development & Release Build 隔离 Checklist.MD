# BlindDuel — Development / Release Build 隔离 Checklist

> 类型：工程发布准备 / 构建环境整理  
> 目标：建立稳定的开发分支与发布分支，隔离开发专用功能，形成可重复的 Production Build 流程  
> 原则：尽量复用现有工程结构，不引入不必要的构建复杂度，不改变游戏运行逻辑。

## Phase 1：现状检查

### 1. Git 分支与版本管理

- [ ] 检查当前 Git 分支、工作区状态及未提交修改。
- [ ] 确认当前 `main` 是否可以作为稳定版本基线。
- [ ] 检查是否已有其他分支及其用途。
- [ ] 制定 `main` / `dev` 双分支方案。
- [ ] 确保当前未提交的工作不会在分支切换过程中丢失。
- [ ] 建立 `dev` 分支，保留 `main` 作为稳定发布分支。

预期结构：

- `main`：稳定、可发布版本。
- `dev`：日常开发、功能集成与测试。

发布流程：

`dev → 集成测试 → main → Production Build → itch.io`

发布时使用 Git Tag 标记版本，例如 `v0.1.0`。

### 2. 构建系统检查

- [ ] 检查 `package.json`。
- [ ] 确认当前使用的构建工具（Vite / Webpack / 其他）。
- [ ] 检查现有 npm scripts。
- [ ] 确认是否已有 Production Build。
- [ ] 确认构建输出目录（例如 `dist/`）。
- [ ] 检查是否存在开发服务器专用逻辑。
- [ ] 检查是否存在依赖开发服务器才能正常工作的资源加载路径。

如果尚未使用构建工具：

- [ ] 评估是否有必要引入 Vite。
- [ ] 不要仅仅为了形式统一而引入复杂工具链。

## Phase 2：开发专用功能隔离

### 3. 开发功能盘点

搜索并整理项目内所有开发专用开关、调试入口及调试依赖。

重点检查：

- [ ] Inspector。
- [ ] 无限弹药。
- [ ] AI Debug / AI 决策可视化。
- [ ] Collision Box / Hitbox / Weaponbox 可视化。
- [ ] Debug HUD。
- [ ] 战斗状态及内部参数显示。
- [ ] 调试快捷键。
- [ ] 测试用场景、测试角色及测试入口。
- [ ] 其他仅供开发测试使用的功能。

输出一份清单，记录每个功能的：
- 所在文件及模块。
- 当前启用方式。
- 是否依赖外部调试库。
- 是否可能进入正式构建。
- 建议隔离方式。

### 4. 开发环境与正式环境隔离

如果项目使用 Vite，优先使用：

`import.meta.env.DEV`

以及：

`import.meta.env.PROD`

隔离开发专用功能。

- [ ] Inspector 只在 DEV 环境加载。
- [ ] Inspector 相关依赖不进入正式构建。
- [ ] 无限弹药只允许 DEV 环境启用。
- [ ] AI Debug 只在 DEV 环境注册。
- [ ] Collision Debug 可视化只在 DEV 环境注册。
- [ ] Debug HUD 只在 DEV 环境创建。
- [ ] 开发专用快捷键在正式版本中不可触发。
- [ ] 检查所有调试入口，避免通过其他调用路径绕过环境限制。

注意：

1. 不要只隐藏调试 UI，而应隔离对应的功能入口。
2. 不要只依靠 JSON 配置中的 `debugEnabled` 控制开发专用功能。
3. 不要把游戏设计参数误判为开发专用参数。
4. 尽量使用静态环境条件，使构建工具能够执行 Dead Code Elimination / Tree Shaking。
5. 不要为了隔离调试功能而大幅重构现有游戏系统。

## Phase 3：配置分类

### 5. 配置职责划分

检查现有配置，将其分成三类：

| 类型 | 示例 | 管理方式 |
|---|---|---|
| 开发专用配置 | Inspector、无限弹药、Debug HUD | DEV 环境隔离 |
| 游戏设计配置 | AI 权重、攻击参数、碰撞参数 | JSON / 游戏配置 |
| 玩家选项 | 音量、显示设置、操作设置 | Runtime Settings |

- [ ] 确认现有配置归属。
- [ ] 避免开发专用配置混入正式游戏配置。
- [ ] 避免将正常游戏设计参数错误地限制在 DEV 环境。
- [ ] 不为这次整理额外引入复杂配置框架。

## Phase 4：Production Build

### 6. 建立正式构建命令

目标是形成稳定、可重复的构建入口，例如：

- `npm run dev`：开发运行。
- `npm run build`：正式构建。
- `npm run preview`：本地预览正式构建产物。

- [ ] 确认 Production Build 使用正式环境变量。
- [ ] 确认构建输出目录。
- [ ] 确认构建过程无错误。
- [ ] 确认开发专用模块没有进入正式构建。
- [ ] 确认没有意外依赖开发服务器地址或本地文件路径。

### 7. 资源完整性检查

重点检查 BlindDuel 的动态资源加载：

- [ ] 场景 JSON。
- [ ] 角色及敌人 spritesheet。
- [ ] 动画数据。
- [ ] 音频文件。
- [ ] 投掷物资源。
- [ ] UI 资源。
- [ ] 其他运行时动态加载的文件。

确认：
- [ ] 所有运行时资源均进入最终构建目录。
- [ ] 动态路径与文件名大小写一致。
- [ ] 不存在指向源码目录的错误引用。
- [ ] 不依赖开发服务器的特殊资源访问行为。
- [ ] Vite `base` 配置适合 itch.io iframe 部署，优先评估 `./` 相对路径。

## Phase 5：发布验证

### 8. 本地 Production Build 测试

- [ ] 执行正式构建。
- [ ] 使用本地 Preview 或静态服务器运行构建产物。
- [ ] 不通过开发服务器测试正式版本。
- [ ] 检查控制台错误。
- [ ] 检查资源加载失败。
- [ ] 检查场景切换。
- [ ] 检查探索模式。
- [ ] 检查战斗模式。
- [ ] 检查 AI 行为。
- [ ] 检查投掷物。
- [ ] 检查音频。
- [ ] 检查键盘及手柄输入。
- [ ] 检查全屏功能。
- [ ] 确认正式版本不存在开发专用功能入口。

### 9. itch.io ZIP 准备

- [ ] 将最终构建目录打包为 ZIP。
- [ ] 确认 `index.html` 位于 ZIP 根目录。
- [ ] 确认没有多余的外层目录。
- [ ] 确认 ZIP 内没有源码、开发缓存及无用文件。
- [ ] 确认资源加载路径在 itch.io iframe 环境下正常。
- [ ] 上传 itch.io Private 页面进行实际测试。
- [ ] 测试通过后再公开发布。

## Phase 6：交付与文档

- [ ] 更新项目 README 中的开发运行命令。
- [ ] 记录正式构建命令及输出目录。
- [ ] 记录分支管理约定。
- [ ] 记录发布流程。
- [ ] 创建首个正式发布 Tag。

## 实施约束

1. 先检查现状，再提交实施计划，不要直接假设项目使用 Vite。
2. 优先采用增量修改，不重构无关模块。
3. 不改变战斗、AI、场景管理、资源管理等游戏系统的既有行为。
4. 开发环境与正式环境隔离应尽可能在构建阶段完成，而不是依赖运行时隐藏开关。
5. 每个 Phase 完成后进行验证，避免一次性大规模修改导致难以定位问题。
6. 如果发现现有架构不支持某项要求，先说明原因和替代方案，不要自行扩大改造范围。

## 最终验收标准

- [ ] `dev` 可以正常进行日常开发。
- [ ] `main` 始终保持可发布状态。
- [ ] 开发专用功能不会进入正式构建。
- [ ] 正式构建可以独立运行，不依赖开发服务器。
- [ ] 所有动态加载资源均能正常访问。
- [ ] 构建产物可以直接打包上传 itch.io。
- [ ] 发布流程可以重复执行，不依赖手工修改源码。

**最终交付：** 分支结构、开发/正式环境隔离、Production Build 命令、发布验证记录，以及一份简明的构建与发布说明。
