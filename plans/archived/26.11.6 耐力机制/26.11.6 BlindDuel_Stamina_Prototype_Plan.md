# BlindDuel 耐力系统原型计划

> 状态：提案 / 待项目 AI 评审，不是最终实现规格  
> 目标：验证耐力机制能否改善连续无脑进攻的问题，并形成更有节奏的攻防交换  
> 范围：第一版只做最小可玩原型，不扩展成完整体能模拟系统

---

## 0. 背景与问题定义

目前 BlindDuel 的战斗系统已经具备：

- 基于 StateGraph 的攻击、防御与动作执行；
- 攻击距离、startup / active / recovery、武器碰撞与 clash 判定；
- 对手攻击预测、preemptive、Clash Seeker；
- guard、parry、dodge、盾牌及投掷物交互；
- 基于 Utility AI 的 attack / defense / throw / positioning 竞争；
- CombatMemory、repetitionCost、feedback 等短期行为反馈。

近期 playtest 发现一个潜在问题：玩家可以不断轮换攻击招式、持续制造攻击机会。即使 AI 能够识别单次攻击并做出合理反应，玩家仍可能依靠大量攻击尝试，最终等到某次攻击命中并获胜。

这可能有两种原因：

1. 开发者长期 playtest，已经熟悉 AI 的决策习惯，能够利用其行为规律；
2. 战斗经济缺少跨招式共享的持续成本，导致连续进攻的代价不足。

目前不能仅凭主观体验确定是哪一种。因此本计划首先验证第二种可能，而不是直接认定当前 AI 有缺陷。

### 核心假设

增加一个双方共用的耐力资源，使攻击、防御和高强度动作产生体能成本，并让低耐力逐渐降低攻击效率，可以：

- 提高连续无效攻击的代价；
- 让有效攻击、合理距离和正确时机具有更长期的价值；
- 让持续攻防后出现脱离、恢复、重新进入交战的节奏；
- 使玩家和 AI 都需要考虑连续行动的成本。

耐力不是为了惩罚玩家频繁按键，也不是为了限制攻击次数，而是为了让战斗行为具有累积成本。

## 1. 设计原则

### 1.1 耐力首先是战斗系统机制，不是 AI 专属机制

所有战斗角色使用同一套基础耐力规则。玩家与 AI 的攻击时序、消耗、恢复和疲劳效果必须由同一套战斗规则计算。

AI 不应拥有另一套独立的耐力模拟，也不应通过特殊规则绕过玩家使用的机制。

### 1.2 奖励有效交战，增加无效行动成本

不应让所有攻击无论结果如何都付出完全相同的总成本。

建议区分：

- 发动动作的基础成本；
- 动作结果产生的追加成本。

例如，挥空、被格挡、成功 clash、命中等结果可以产生不同的追加消耗。具体数值暂不确定，应通过原型测试校准。

### 1.3 疲劳影响应连续、可预测

不建议只设置一个“耐力低于某阈值就突然变慢”的硬切换。

第一版考虑使用连续曲线，让耐力下降时攻击逐渐变慢；耐力耗尽时仍允许行动，只是动作明显变慢。

### 1.4 第一版控制影响面

第一版优先验证：

1. 耐力资源；
2. 动作消耗与结果追加消耗；
3. 随时间恢复；
4. 耐力对攻击 startup 的影响。

暂不同时引入伤害倍率、移动速度倍率、防御能力倍率、最大耐力永久损伤等多重疲劳效果。

### 1.5 不以“模拟完整 HEMA 体能”为目标

参考 Hellish Quart 的设计思路：有效攻击、挥空、格挡、clash 可以有不同的体能成本；疲劳也可以影响战斗表现。

但 BlindDuel 第一版只借鉴“按战斗结果区分成本”这一原则，不照搬其完整耐力模型或具体数值。

## 2. 第一版机制范围

### 2.1 每个战斗角色拥有耐力资源

概念字段：

```js
stamina
maxStamina
staminaRatio // stamina / maxStamina，范围 0..1
```

字段名称和数据归属由项目 AI 根据现有 Character / Combatant / Component 架构决定。不要为了耐力建立一套与现有角色资源管理重复的系统。

### 2.2 耐力消耗

建议将成本拆成两部分：

```text
总消耗 = 动作基础消耗 + 战斗结果追加消耗
```

第一版考虑以下事件：

| 行为 / 结果 | 第一版处理方向 | 说明 |
|---|---|---|
| 发动攻击 | 消耗基础耐力 | 可按攻击重量或动作特征区分，不要求所有攻击同价 |
| 攻击命中 | 不额外惩罚，或追加很低成本 | 命中已经实现攻击目的，不应与挥空同价 |
| 攻击被格挡 | 追加少量成本 | 攻击受到有效防御 |
| 攻击挥空 | 追加较高成本 | 尤其考虑在 recovery 阶段结算额外成本 |
| weapon clash | 追加成本较低 | 不应简单视同完全挥空或普通命中 |
| 实际格挡 / 盾牌拦截 | 防守方产生消耗 | 以成功发生的防御接触事件为准 |
| parry | 适量消耗 | 可低于普通硬格挡，具体待测试 |
| dodge / 高强度闪避 | 消耗 | 依据动作实际发生结算，避免每帧重复扣除 |
| 普通站立 / 轻微调整距离 | 第一版不消耗 | 避免角色因正常等待而被动耗尽耐力 |

以上是设计方向，不是已经确定的数值表。项目 AI 需要先检查现有 CombatSystem outcome / projectile event / state transition，确认哪些事件可靠且只触发一次，再决定扣费时机。

#### 特别注意：动作被打断

攻击已经开始、但在 active 之前被打断时，应该承担已发生的基础成本；不应因为没有完整执行到 recovery，就完全免除成本。

因此基础成本应与动作 commit / 启动事件关联，而不是只在攻击命中后扣除。

结果追加成本则应由 CombatSystem 的最终 outcome 事件触发，避免 AI 和战斗系统重复扣费。

### 2.3 耐力恢复

第一版使用基于时间的连续恢复：

- 处于低强度状态时恢复；
- 正在进行高强度攻击、防御或闪避时，可以暂停恢复或降低恢复速度；
- 不要求必须完全脱离战斗才允许恢复；
- 不使用复杂的恢复阶段状态机。

需要项目 AI 检查现有角色状态与事件系统，选择最少侵入的恢复条件。

建议避免把“必须距离对手足够远”作为唯一恢复条件，否则角色可能因对手持续压迫而永远无法恢复，形成难以打破的疲劳循环。

### 2.4 耐力对攻击时序的影响

第一版只考虑影响攻击 startup，不同时改变 damage、移动速度和防御能力。

建议使用连续的疲劳倍率曲线。一个待测试的初始示意为：

```js
const fatigueRatio = 1 - staminaRatio;
const startupMultiplier = 1 + 0.4 * fatigueRatio * fatigueRatio;

// staminaRatio = 1.0 → multiplier = 1.0
// staminaRatio = 0.5 → multiplier = 1.1
// staminaRatio = 0.0 → multiplier = 1.4
```

这意味着：

- 满耐力：正常 startup；
- 中等耐力：轻微变慢；
- 低耐力：明显变慢；
- 耐力耗尽：startup 最多增加约 40%；
- 不因耐力耗尽而完全禁止攻击。

`0.4` 和平方曲线只是原型参数，不是最终平衡值。项目 AI 可以提出替代曲线，但应先保持单一、可解释的疲劳映射，不要马上增加多组阈值和倍率。

## 3. 动作时序一致性：本计划的关键技术风险

疲劳会改变 startup，因此实际执行、攻击预测和碰撞判定必须读取同一份有效时序。

### 3.1 单一时序来源

建议在现有战斗动作时序计算层提供统一的有效 timing：

```text
base StateGraph timing
        + stamina fatigue modifier
        ↓
effective action timing
        ├── actual animation / state execution
        ├── attack active window
        ├── AIKnowledgeRegistry / attack profile
        ├── predictedOpponentEvents
        └── clash / preemptive / projectile timing checks
```

不能出现以下情况：

- 动画播放变慢，但 weaponbox active 时间仍然使用原始值；
- AI 预测了疲劳后的 startup，但实际动画没有变慢；
- AI 预测使用一套倍率，ContactResolver 又使用另一套倍率；
- fatigue 改变 startup 后，active / recovery 时间的映射含义不明确。

### 3.2 一次动作的时序应保持稳定

建议第一版在动作 commit 时，读取当时的 staminaRatio 并计算该动作的有效 timing，动作执行期间不因耐力的细微变化反复重算同一招的 startup。

这样可以避免动作进行中 timing 不断变化，导致预测窗口、动画进度和有效帧出现不稳定。

### 3.3 防止动作自身消耗导致自身额外变慢

需要明确扣费和时序采样的先后关系。

建议动作 commit 时先基于动作开始前的 staminaRatio 计算本次 timing，再结算本次动作的基础消耗。否则会出现“刚按下攻击，先扣耐力，再用扣费后的耐力计算本次攻击速度”的自我惩罚，可能使同一招的速度取决于实现顺序。

项目 AI 应检查现有 state transition / action commit 生命周期，选择最符合当前架构的具体顺序。

## 4. AI 接入边界

本次不建立 Stamina AI 子系统，不给每个评分函数都增加 stamina 判断。

### Phase 1：先让 AI 与玩家遵守相同的资源规则

- AI 发动攻击时消耗耐力；
- AI 格挡、parry、dodge 时按相同战斗规则消耗耐力；
- AI 的攻击 timing 使用当前耐力对应的有效时序；
- AI 对玩家攻击的预测使用玩家当前耐力对应的有效时序；
- 暂时不要求 AI 主动优化耐力使用。

第一阶段主要验证：仅靠真实资源消耗和 fatigue timing，是否已经能减少持续无脑攻击的收益，并让 AI 的连续攻击自然受到限制。

### Phase 2：必要时增加统一的行动成本评价

如果 Phase 1 测试发现 AI 虽然会疲劳，但仍然无视耐力成本持续选择高消耗动作，再考虑在 Utility 层统一引入候选动作的预期 stamina cost。

建议原则：

- 成本由动作定义或战斗系统提供；
- 候选评分层统一读取预期成本；
- 不要在 `#scoreAttack`、`#scoreDefense`、`#scoreThrow` 中分别硬编码不同版本的耐力规则；
- 只在成本确实影响行动选择时才扣分；
- 不增加 `retreatWhenTired` 之类专用分支，先观察现有 positioning 是否能利用攻击效率下降和行动成本形成合理行为。

### Phase 3：必要时评估对手疲劳

若测试证明 AI 有必要主动利用玩家疲劳，再考虑使用 `oppStaminaRatio` 调整 punish / attack opportunity。

第一版不做角色预测能力噪声、耐力欺骗或专门的耐力狩猎策略。

## 5. 与现有系统的集成原则

项目 AI 需要先检查以下位置，提出最小侵入式实现方案：

1. **Character / Combatant 生命周期**：耐力资源应归属角色，而不是 AIController。
2. **StateGraph timing**：确认 startup、active、recovery 的时间如何驱动动画和攻击有效帧。
3. **CombatSystem outcomes**：确认 hit / block / clash / miss / parry / dodge 等事件的唯一结算位置。
4. **ProjectileResolver**：投掷物防御是否需要额外耐力，第一版可先沿用通用 dodge / cut 事件，不为投掷物另建耐力模型。
5. **AIKnowledgeRegistry**：攻击 profile 是否读取有效 timing，而非始终读取 base timing。
6. **predictedOpponentEvents**：预测的攻击窗口必须使用对应角色当前的耐力状态。
7. **Scene / Battle 生命周期**：第一版每场 Battle 开始时重置耐力，不跨场景继承疲劳。

### 场景与章节范围

第一版建议：

- 每场 Battle 初始化时，将耐力恢复到满值；
- 战斗结束后无需保存耐力；
- 不跨房间、大厅、室外等不同战斗场景继承疲劳；
- 未来若设计无缝连续遭遇战，再单独讨论跨战斗继承。

## 6. 暂不做的内容

第一版明确不包含：

- 耐力耗尽后禁止攻击或强制进入疲劳状态；
- 多级疲劳状态（轻度 / 中度 / 重度 / 力竭）；
- 攻击伤害随耐力变化；
- 移动速度随耐力变化；
- 防御能力或盾牌强度随耐力变化；
- 最大耐力永久损伤；
- 饮食、休息、营地等场外资源管理；
- 复杂的职业耐力成长系统；
- AI 专用的耐力行为树或专用决策 kind；
- 为每种武器、每个角色建立大量独立耐力参数。

如果第一版证明耐力确实改善战斗，后续再根据玩家反馈选择是否扩展。

## 7. 原型验证方案

不要直接把耐力机制视为确定要发布的系统。先建立可开关的 prototype，进行对照测试。

### 7.1 三种玩家行为测试

| 测试 | 玩家行为 | 目的 |
|---|---|---|
| A：无脑进攻 | 轮换不同攻击，不考虑距离、时机和对手行为 | 验证持续攻击是否仍然可以低成本获得胜利 |
| B：判断后进攻 | 观察敌人动作，只在合理距离和时机出招 | 验证系统是否奖励正确的时机与距离判断 |
| C：攻防后脱离 | 连续交换后主动后撤，等待恢复再重新交战 | 验证耐力是否自然形成 engage / exchange / disengage / re-engage 节奏 |

最好让至少一名没有参与开发的测试者参与，避免开发者长期 playtest 导致熟悉 AI 行为规律。

### 7.2 记录指标

沿用现有 combat log / AI-Diag，必要时只增加耐力事件日志。建议记录：

- 战斗开始、结束时双方 stamina；
- 每次 stamina 消耗的来源和数值；
- 每次恢复的数值；
- 动作 commit 时 staminaRatio；
- 本次动作实际 startup multiplier；
- hit / block / clash / miss 等 outcome；
- 双方有效攻击次数、挥空次数、格挡次数；
- 平均战斗时长和胜负结果。

不要为原型建立新的庞大分析系统，能够从日志还原资源变化即可。

### 7.3 对照组

至少比较：

1. 无耐力系统；
2. 有耐力消耗与恢复，但不影响 startup；
3. 有耐力消耗、恢复与 startup fatigue。

这样可以区分：战斗改善来自“攻击有成本”，还是来自“疲劳导致动作变慢”。

### 7.4 验收方向

- 无脑轮换攻击的长期收益应下降，但不应变成完全不可行；
- 合理距离和时机下的攻击应比连续挥空更经济；
- 玩家不能通过一直按住防御、等待 AI 耗尽来获得不合理优势；
- AI 不应因为耐力机制出现站桩、无限后撤或永远不敢攻击；
- 耐力耗尽后仍然可以行动，但应能明显感受到疲劳；
- 角色与 AI 的实际招式时间、预测时间和碰撞时间必须一致；
- 正确的 clash、parry、block 等互动不应因为耐力接线出现判定回归。

## 8. 待项目 AI 评审的问题

请先做架构检查和数值建议，不要直接一次性实现完整系统。

### 决策 A：耐力资源归属

- 现有 Character / Combatant / Component 中，哪个位置最适合持有 stamina？
- 是否已有可复用的资源组件或生命周期？
- 如何保证玩家和 AI 使用同一套机制？

### 决策 B：事件与扣费时机

- 哪些现有 outcome 可以可靠地区分 hit / block / clash / miss / parry / dodge？
- 发动成本应在何处结算，如何避免被打断后不扣费？
- 结果追加成本如何保证只结算一次？
- 是否存在一个攻击同时产生多个结果事件，导致重复扣费的可能？

### 决策 C：时序接线

- 当前 startup / active / recovery 的权威来源在哪里？
- 是否能以角色当前 staminaRatio 生成一份 effective timing，并让动画执行、碰撞判定、AIKnowledgeRegistry 和 predictedOpponentEvents 共用？
- 如何在动作 commit 时固定本次 timing，避免动作自身扣费反过来影响自身 startup？

### 决策 D：恢复规则

- 哪些角色状态可以视作低强度状态？
- 是否能用简单的状态分类控制恢复，而不增加复杂状态机？
- 战斗中被持续压迫时是否仍有合理的恢复机会？

### 决策 E：原型数值

请提出一组最小数值供测试：

- maxStamina；
- 不同攻击重量的基础成本；
- hit / block / clash / miss 的追加成本；
- guard / parry / dodge 的成本；
- 每秒恢复速度；
- startup fatigue 曲线。

数值需要能通过少量测试调整，不要为每个角色和招式提前引入大量独立 knob。优先使用现有 attackWeight、trajectory、action outcome 等信息推导成本。

### 决策 F：AI 第一阶段范围

请确认 Phase 1 是否可以只做到：AI 遵守与玩家相同的耐力规则、实际动作和预测使用疲劳后的有效 timing，而暂不增加新的 Utility 评分项。

如果认为必须在 Phase 1 增加 Utility 耐力成本，请说明现有行为在哪个具体场景会失效，以及为什么不能等 Phase 1 测试后再加。

## 9. 建议实施阶段

```text
Phase 0：架构审查
    检查资源归属、动作 timing、outcome 事件、AI 预测的数据流
    输出最小侵入式实施方案和初始数值

Phase 1：战斗机制原型
    stamina resource
    action base cost
    outcome additional cost
    time-based regeneration
    startup fatigue modifier
    Battle start reset

Phase 2：AI 公共机制接线
    AI 与玩家共享消耗、恢复、有效 timing
    Prediction 使用疲劳后的 timing
    暂不新增专用 AI 决策类型

Phase 3：对照 playtest
    比较无耐力 / 仅资源成本 / 资源成本+疲劳时序
    根据数据判断是否保留机制

Phase 4：必要时增加 AI Utility 成本评价
    只在测试证明 AI 忽略耐力成本时实施
```

## 10. 本提案的完成标准

本提案不是要求把耐力系统做得尽可能复杂，而是验证它是否能给战斗带来更好的攻防节奏。

第一版成功的标准是：

1. 玩家连续无脑攻击的收益和可持续性下降；
2. 合理的距离、时机和攻防交换获得相对优势；
3. 耐力状态能够被玩家直观理解；
4. AI 仍能正常攻击、防御、clash、投掷和管理距离；
5. 新增机制没有迫使 AI 系统增加大量专用分支和参数。

如果原型没有明显改善战斗体验，应该允许放弃或缩减耐力系统，而不是因为已经投入开发就继续扩大范围。

**核心目标：让连续战斗行为具有可理解的累积成本，而不是再给 AI 增加一个需要无限调参的新维度。**
