# BlindDuel — Fatigue-aware Attack Policy

> 类型：AI 架构补充 / 实施设计
>
> 状态：待项目 AI 结合当前代码核对并细化实施
>
> 背景：2026-11-06 耐力系统初步落地后，playtest 发现 AI 即使处于低耐力、攻击动作已明显减速的状态，仍会按照原有进攻偏好持续主动出招，导致耐力迅速耗尽，并在长前摇状态下容易被玩家抓住时机惩罚。
>
> 本文目标：在不重构现有 Utility AI、不新增 conserve 候选、不改变既有评分模型的前提下，为攻击候选增加统一的耐力储备资格 Gate；同时通过 `fatigueAwareness` 表达不同 AI 管理自身耐力的能力。

---

## 0. 设计结论

### 0.1 核心原则

**耐力管理不是一种新的战术行为，而是对现有战术行为施加资源约束。**

AI 原本就会攻击、抢先攻击、寻求 clash、惩罚 recovery、格挡、闪避和调整距离。耐力管理不应再创造一套 `conserve` 行为或新的 Utility 评分体系，而应决定：当前是否值得为某个攻击候选支付耐力成本。

本方案第一版采用：

- **攻击族资格 Gate（veto）**，不新增攻击评分项。
- Gate 按具体攻击候选判断，而不是对整个攻击族简单一刀切。
- 根据本次攻击的预计基础消耗，计算 commit 后的耐力储备。
- 耐力低于角色的储备阈值时，普通攻击候选被过滤；只有满足既有高价值机会资格的攻击才能放行。
- `fatigueAwareness` 控制 AI 是否采用这套主动疲劳管理策略；它不改变真实耐力、动作时序或预测结果。
- `baseAggression` 表达角色的进攻意愿，同时用于派生其愿意保留多少耐力。二者相关但不等价。

### 0.2 明确不做

第一版不做：

- 新增 `conserve` / `recover` 等独立候选 kind。
- 新增 Utility 加性评分项或全局攻击评分乘数。
- 为 light / heavy 分别新增一套独立人格参数。
- 新增 `staminaDiscipline` 等第二个耐力管理 knob。
- 为耐力管理重写预测系统或 AIKnowledgeRegistry。
- 让 AI 因 `fatigueAwareness = 0` 而使用错误的动作时间预测。
- 将 `throw` 自动纳入近战攻击储备 Gate；投掷继续使用现有独立 cooldown 和规则，后续按 playtest 再决定是否需要资源约束。

## 1. 问题与设计动机

耐力系统的规则层已初步落地：攻击、guard、dodge 等动作会消耗耐力，部分战斗结果会追加消耗；耐力随时间恢复；低耐力会使攻击类动作减速。AI 也已能根据耐力风险调整 guard / dodge 策略。

但 playtest 发现：AI 在低耐力时仍持续按照原有攻击评分选择主动攻击。即使攻击前摇因疲劳显著延长，它仍可能连续出招，最终在低耐力、长前摇状态下被玩家轻易抓住攻击时间差。

这不是单纯的动作执行问题，而是**资源成本尚未传导到攻击决策资格**：攻击评分仍在比较“当前哪一招分数最高”，却没有判断“支付这次攻击的基础成本后，是否会把自己推入不希望进入的耐力区间”。

本方案补上这一层，但刻意不改变 attack 候选之间现有的相对评分。

## 2. `baseAggression` 与 `fatigueAwareness` 的职责

二者应表达不同维度：

| 字段 | 语义 | 不代表什么 |
|---|---|---|
| `baseAggression` | 角色的基础进攻意愿；同时派生其愿意把耐力消耗到多低 | 不代表角色是否能正确预测实际攻击时间 |
| `fatigueAwareness` | AI 是否会主动根据自身疲劳管理攻击储备与耐力不足的防御风险 | 不改变真实疲劳、动作倍率或物理预测 |

建议的行为解释：

- `fatigueAwareness = 0`：不主动管理耐力。攻击沿用原有决策；仍然读取真实疲劳后的动作时间。既有 guard 风险机制也按当前项目设定处理，不因本方案误改。
- `fatigueAwareness = 1`：完整采用疲劳管理策略，但不等于“只有满耐力才攻击”。仍可在低耐力时执行有明确价值的抢攻、clash 或 punish。
- 中间值：通过疲劳管理周期开始时的概率锁存，决定本周期是否采用疲劳管理策略；不应每个 decision tick 重新掷骰。

### 2.1 从 aggression 派生储备阈值

第一版建议使用一个简单映射，不额外增加独立配置：

```js
const normalizedAggression = clamp(baseAggression, 0, 1);
const reserveThreshold = 0.7 - 0.5 * normalizedAggression;
```

示意：

| `baseAggression` | 储备阈值 | 直观行为 |
|---:|---:|---|
| 0.0 | 70% | 非常节制，较早开始保留体能 |
| 0.25 | 57.5% | 偏保守 |
| 0.5 | 45% | 均衡 |
| 0.75 | 32.5% | 积极，允许较低耐力 |
| 1.0 | 20% | 激进，愿意消耗到较低水平 |

**注意：** 当前项目允许 `baseAggression` 大于 1（例如精英 / Boss 的 1.2、1.3）。派生储备阈值时应将其 clamp 到 `[0, 1]`，避免原有攻击 multiplier 配置意外把阈值外推到设计区间之外。攻击评分仍按现有规则使用原始人格配置，不因该 clamp 改变。

这一映射是第一版的设计假设，数值应通过 playtest 调整；不要因为某个敌人表现不合预期，就立即增加每角色独立的储备阈值字段。

## 3. 攻击族 Gate：位置与行为

### 3.1 为什么第一版使用 Gate，而不是 Utility Score

此前多轮 AI 迭代中，新增攻击评分项容易改变 attack、defense、positioning 等候选之间的相对排名，引发难以预测的行为回归。

耐力储备管理表达的是一个资源约束，不是新的攻击偏好。因此第一版不增加：

- `staminaAttackBonus`
- `staminaAttackPenalty`
- `attackStaminaMultiplier`
- 其他参与 attack utility 连续加减分的参数

而是在具体 attack 候选已按原逻辑完成资格检查和评分后、进入最终候选排序前，执行统一的疲劳资格过滤。

推荐数据流：

```text
生成 attack 候选
      ↓
既有攻击资格与评分（原逻辑不变）
      ↓
Fatigue Attack Eligibility Gate
      ├─ 通过：候选保留原分数
      └─ 拒绝：候选不进入最终 pool，记录拒绝原因
      ↓
与 defense / positioning / throw 等候选正常仲裁
```

Gate 不应在全局 winner 已经选出之后才执行。否则一个高分 attack 被 veto 后，系统可能直接 fallback，而没有让其他合法候选正常竞争。

### 3.2 按具体招式判断，不应简单全族禁用

每个 attack 候选都应单独计算：

- 本次动作的基础耐力成本。
- 本次 commit 后的预计耐力比例。
- 是否满足储备阈值。
- 若不满足，是否具备高价值机会资格。

这样低耐力时，昂贵的 heavy attack 可以比 light attack 更早被限制，而不必额外增加 `lightOnly` 特例。

### 3.3 预计 commit 后耐力

不要只看当前 `staminaRatio`。应把本次攻击的基础 commit 成本纳入判断：

```js
const projectedStamina = Math.max(0, currentStamina - baseCommitCost);
const projectedStaminaRatio = projectedStamina / maxStamina;
```

其中：

- `currentStamina` 是当前实际耐力。
- `baseCommitCost` 是当前攻击在 commit 时支付的基础成本。
- 不预扣尚未发生的 miss / parried / guard-blocked 等 outcome 追加成本。

资格判断：

```text
projectedStaminaRatio >= reserveThreshold
    → 常规攻击候选正常保留

projectedStaminaRatio < reserveThreshold
    → 只有符合机会攻击条件的候选可以保留
```

例：当前耐力 30，储备阈值 20%。若 light 成本 15、heavy 成本 25，则：

- light commit 后剩余 15（15%）：低于阈值，需要机会资格。
- heavy commit 后剩余 5（5%）：同样需要机会资格，且更不容易被放行。

**待项目 AI 核实：** 当前状态进入时的耐力消耗与疲劳倍率锁存顺序。实际动作时序与预测必须使用相同的 commit stamina snapshot。建议先按 commit 前快照计算本次动作倍率，再扣除基础成本；若项目现有实现采用其他顺序，也可以保留，但执行层与 AI 预测必须完全一致。

## 4. 低耐力下的机会攻击资格

低于储备阈值并不意味着禁止所有攻击，而是常规主动攻击需要让位给有明确战术价值的机会。

机会判断必须落实到**具体攻击候选**，不能只看对手处于某个 phase。对手在 recovery 不代表所有攻击都赶得上；对手在 startup 也不代表所有攻击都能截断或 clash。

第一版优先复用现有系统：

| 机会类别 | 资格依据 | 必要约束 |
|---|---|---|
| Preemptive | 现有预测证明该招能够抢先截断对手攻击 | 使用疲劳调整后的自身 startup / active 时间；按现有 preemptive 资格规则验证 |
| Clash Seeker | 现有 Clash Seeker 资格检查通过 | 双方攻击有效窗口重叠、武器 reachSum 足够、对手攻击 profile 有效等既有条件全部成立 |
| Recovery Punish | 对手存在 recovery / vulnerability 窗口 | 当前具体攻击能够在窗口内到达并命中，不能只凭 `opp.phase === recovery` 放行 |
| 其他明确机会 | 现有系统已经能证明的高价值命中窗口 | 必须有可验证的时序与空间依据；第一版不为此另建预测模型 |

### 4.1 避免把角色变成纯 counter AI

机会类别不应只包含 startup 和 recovery。Clash Seeker 与其他已有高价值窗口也应纳入。

同时，疲劳 Gate 只限制攻击候选，不应压制其他现有行为：

- approach 仍可用于保持压迫、重新建立距离。
- hold 仍可在合适距离维持位置。
- retreat 仍由现有 positioning 规则决定。
- defense 仍按既有 threat / timing 逻辑运行。

高侵略性角色在低耐力时可以减少无价值挥击，但仍然可以积极接近、保持压力，并抓住真正出现的攻击机会。

### 4.2 空耐力边界

空耐力不应成为规则层的“禁止攻击”状态。若某个机会攻击通过既有时序与空间资格，第一版允许它进入决策；实际动作仍按疲劳后的时序执行。

但项目 AI 需要核实：在 `stamina = 0` 时，动作基础成本为 0、预计耐力仍为 0，Gate 是否会把所有候选都视作低于阈值并正确要求机会资格，而不是发生除零或边界绕过。

## 5. Fatigue Awareness：统一策略认知与锁存

### 5.1 一个 knob 暂时足够

第一版保留一个：

```json
{
  "aiProfile": {
    "fatigueAwareness": 1.0
  }
}
```

建议默认值与现有项目约定一致；档位可以继续使用：

- 教学 / 低级 rabble：0.0
- 普通敌人：0.5
- 精英 / Boss：1.0

不新增 `staminaDiscipline`。只有未来确实需要表达“能感知疲劳，但管不住自己”这类独立人格时，再考虑拆分感知与自律。

### 5.2 概率锁存

在进入疲劳管理周期时，根据 `fatigueAwareness` 进行一次判定：

```js
aware = random() < fatigueAwareness;
```

判定结果在本次周期内锁存：

- `aware = true`：攻击储备 Gate 生效；guard 风险管理按既有 fatigue-awareness 设计生效。
- `aware = false`：不主动管理攻击储备，攻击沿用原有决策偏好；真实疲劳时序仍然生效。

不要在每个 200ms decision tick 重新掷骰，否则角色可能在相邻决策中反复切换策略。

### 5.3 周期退出与滞回

建议采用耐力阈值滞回：

- 低于进入阈值时开始一个疲劳管理周期并锁存 awareness。
- 耐力恢复到高于退出阈值时结束周期；退出阈值应高于进入阈值。
- 下一次重新进入疲劳区间时，才重新掷骰。

注意区分：锁存的是“角色是否采用疲劳管理策略”；机会攻击是否成立仍然每次根据当前 Situation / predictedOpponentEvents 重新计算，不得锁存 2.5 秒。

**待项目 AI 确定：** 进入阈值与退出阈值的具体来源。第一版可以围绕角色派生的 `reserveThreshold` 加一个小滞回带，不新增独立的每角色 knob。避免角色耐力在临界点附近抖动时频繁开始 / 结束周期。

### 5.4 物理认知与策略意识必须分离

`fatigueAwareness = 0` 不能导致 AI 使用错误的动作时间。

所有 AI 都必须知道真实的疲劳倍率，并使用调整后的 startup / active / recovery 等时间进行：

- 自身攻击评分中的时序计算。
- Preemptive 与 Clash Seeker 窗口判断。
- `predictedOpponentEvents` 的时间估计。
- dodge i-frame 资格判断。
- 投掷物斩落 / 闪避可行性预测。

`fatigueAwareness` 只决定 AI 是否主动管理资源，不决定它是否正确感知物理事实。

## 6. Throw 与非攻击行为的边界

### 6.1 Throw 暂不进入本次近战攻击 Gate

当前 throw：

- 不扣耐力。
- 有独立 `throw.cooldownMs`。
- 动作时间仍受疲劳倍率影响。

第一版继续保持 throw 独立，不因本次近战攻击储备管理而自动 veto throw。

这是一个明确的范围选择，不代表无限投掷永远合理。若 playtest 发现 AI 或玩家在疲劳期通过投掷绕过近战耐力约束，再单独评估 throw 的资源成本或 cooldown；不要提前扩大本次改动范围。

### 6.2 Positioning 不新增 conserve 候选

当普通攻击候选被 Gate 过滤后，现有 defense / approach / hold / retreat / throw 候选自然参与仲裁。

不新增：

- `kind: "conserve"`
- `kind: "recover"`
- 专门的 stamina-reposition 状态

低耐力双方短暂拉开距离、等待恢复，可以是正常战斗节奏，不应仅因为双方同时保留体能就被 `holdTimeout` 强制打破。

## 7. 双方都低耐力时的恢复与僵局

第一版不专门添加打破 conserve 对峙的机制。

预期循环：

```text
双方耐力低于储备阈值
        ↓
普通攻击候选被过滤
        ↓
现有 positioning / defense 等候选接管
        ↓
脱离 attack / guard / dodge / hitstun 等恢复黑名单状态
        ↓
按现有恢复规则恢复耐力
        ↓
耐力超过退出阈值
        ↓
疲劳管理周期结束
        ↓
攻击候选重新正常参与竞争
```

Guard 中是否被动恢复：第一版继续暂停恢复；成功防御的既有耐力回补规则保持不变。避免持续举盾成为零风险的恢复方式。

不要用 `holdTimeout` 强制双方在耐力不足时重新进攻。先验证恢复速度、positioning 与现有压力机制能否自然恢复交战节奏。

## 8. 对现有评分体系的保护

本次实现必须遵守以下约束：

1. 不改变 `#scoreAttack` 原有各评分项的数值、权重和相对顺序。
2. 不新增 `staminaAttackBonus` / `staminaAttackPenalty` 等 Utility 分项。
3. 不把耐力成本乘进所有 attack score；只在攻击候选最终进入全局 pool 前做资格过滤。
4. Gate 对每个 attack 候选独立判断，不能简单地在选出全局 winner 后才 veto。
5. 被过滤的候选记录原因与关键数值，但不修改它原本的评分日志。
6. Gate 关闭时，行为应完全回归当前耐力管理关闭状态下的原决策结果。
7. 机会资格复用现有预测和资格检查，不新建第二套近似但口径不同的时序 / reach 模型。

### 8.1 对低意识 AI 的保护

`fatigueAwareness = 0` 时，攻击 Gate 不得过滤攻击候选；原有 attack scoring 应保持不变。

但动作执行仍然受真实耐力影响：低耐力会让招式变慢。这正是低意识敌人“知道得少、管理得差，但身体仍然会疲劳”的表现。

## 9. 日志与诊断

不需要建立新的大型诊断系统。沿用现有 AI-Diag，在 attack 候选被 Gate 检查时增加必要字段：

```text
[AI-Diag] fatigueAttackGate
  state=smash
  stamina=30/100 ratio=0.30
  baseCommitCost=25
  projected=5 ratio=0.05
  reserveThreshold=0.20
  awareness=true
  opportunity=clashSeeker
  result=ALLOW
```

拒绝示例：

```text
[AI-Diag] fatigueAttackGate
  state=smash
  stamina=30/100 ratio=0.30
  baseCommitCost=25
  projected=5 ratio=0.05
  reserveThreshold=0.20
  awareness=true
  opportunity=none
  result=BLOCK
  reason=below_reserve_no_opportunity
```

建议记录：

- 当前耐力 / 最大耐力 / 比例。
- 当前攻击候选与基础 commit 成本。
- projected stamina ratio。
- 派生储备阈值。
- 当前 fatigue-awareness 锁存结果。
- 通过了哪一种机会资格。
- 最终 Gate 结果与拒绝原因。

日志应能区分：角色没有攻击欲望、攻击候选本身无效、候选被 fatigue Gate 过滤。不要只输出一个笼统的 `fatigue blocked`。

## 10. 测试矩阵

至少覆盖以下对照：

| 角色配置 | Awareness | 目标行为 |
|---|---:|---|
| 高 aggression | 0.0 | 不管理攻击储备；仍按真实疲劳时序行动，可能持续浪费体能 |
| 高 aggression | 1.0 | 耐力充足时积极进攻；低耐力时减少无价值攻击，但仍会压迫并抓机会 |
| 低 aggression | 1.0 | 较早保留耐力；等待高价值机会，不应变成永久站桩 |
| 中 aggression | 0.5 | 疲劳管理周期概率锁存，表现介于两者之间 |

行为场景：

1. **双方 idle，AI 耐力充足：** 原攻击偏好不变。
2. **双方 idle，AI 低耐力：** awareness 高时普通攻击被过滤，positioning 正常接管；awareness 低时仍按原行为尝试攻击。
3. **AI 低耐力，对手 startup：** 可行的 Preemptive / Clash Seeker 候选仍放行；不可行的慢招不因 phase 名称而放行。
4. **AI 低耐力，对手 recovery：** 能在窗口内命中的攻击可以 Punish；赶不上的重招仍被过滤。
5. **AI 低耐力，只有重招成本会使 projected stamina 低于阈值：** 验证具体招式成本判断，而不是整个攻击族统一禁用。
6. **AI 空耐力：** 不出现除零、NaN 或所有机会攻击被意外放行；符合机会条件的攻击仍能执行，但使用疲劳后的真实 timing。
7. **双方低耐力：** 可以短暂拉开并恢复，不触发强制攻击或无限 retreat。
8. **低耐力 AI 面对投掷物：** 现有 projectile defense / throw 行为正常；疲劳预测的时间与位移估计正确。
9. **Awareness 周期：** 临界值附近不每个 200ms tick 反复切换；机会事件本身仍实时计算。

## 11. 实施顺序

### Phase A：先接入 Gate 框架，默认关闭

- 新增候选过滤入口与诊断日志。
- `fatigueAwareness = 0` 或 Gate 总开关关闭时，保证原行为完全不变。
- 先验证 Gate 的执行位置：必须在最终候选排序之前。

### Phase B：接入储备计算

- 读取当前耐力与具体攻击的基础 commit 成本。
- 计算 projected stamina ratio。
- 派生 reserve threshold（`baseAggression` clamp 到 `[0,1]` 后映射）。
- 先只实现常规攻击资格过滤，不改变攻击分数。

### Phase C：接入机会攻击放行

- 复用 Preemptive 资格。
- 复用 Clash Seeker 资格。
- 复用 Recovery Punish 的时序 / 空间验证。
- 确认疲劳后的 timing 已进入全部相关资格判断。

### Phase D：接入 fatigue-awareness 锁存

- 周期开始时概率判定。
- 周期内锁存。
- 采用进入 / 退出阈值滞回。
- 与已有 guard 风险锁存协调，避免两个独立计时器发生冲突。

### Phase E：回归与 playtest

- 对照不同 awareness / aggression 组合。
- 验证低耐力时 AI 不再无意义地连续进攻。
- 验证积极角色仍有压迫感和机会攻击能力。
- 验证 Gate 不改变原有攻击候选分数与族内排序。

## 12. 验收标准

本次改动完成应满足：

- [ ] 满耐力时，原有 AI 攻击行为与评分基本一致。
- [ ] `fatigueAwareness = 0` 时，攻击 Gate 不过滤候选。
- [ ] 高 awareness AI 在低耐力时不再无意义地连续消耗重招。
- [ ] 高 aggression + 高 awareness 仍表现积极：有压力、有接近、有机会攻击，不变成纯被动 counter。
- [ ] 具体攻击的基础成本会影响 projected stamina 判断，heavy 比 light 更容易触发储备限制。
- [ ] Preemptive / Clash Seeker / Punish 的放行基于具体候选的时序与空间可行性。
- [ ] Gate 不改变任何现有 attack utility 分数；只改变候选是否进入最终 pool。
- [ ] 低耐力状态下的实际动作时间与 AI 预测一致。
- [ ] 不出现低耐力双方永久僵局、无限后撤或站桩。
- [ ] throw 保持本次范围外的现有行为，且疲劳时序仍正确。
- [ ] Gate 可独立关闭，关闭后行为回归原系统。

## 13. 请项目 AI 在实施前重点核对

1. 当前 attack 候选的生成、评分、Gate 和最终 pool 仲裁的真实顺序，确保 Gate 放在最终排序前且不会改变候选原始评分。
2. 各攻击的 `baseCommitCost` 从哪里取得，是否与 `CharacterBase.enterState` 实际扣费使用同一个计算函数，避免 AI 预测成本与真实成本不一致。
3. commit 时疲劳倍率与 stamina 扣费的先后顺序，确保本次动作执行、AI 自身预测、对手预测读取同一份 commit snapshot。
4. 现有 Preemptive、Clash Seeker、Recovery Punish 是否都能提供可复用的“具体候选可行”判据；不要只用 `opp.phase` 作为机会资格。
5. 已有 `fatigueAwareness` guard 风险锁存与本方案攻击储备锁存，是否应该共享一个疲劳意识周期，避免重复掷骰或状态冲突。
6. 进入 / 退出阈值滞回应如何从现有 reserve threshold 派生，避免为第一版增加过多独立配置。

如果当前代码结构与本文假设不一致，请先指出差异并给出最小适配方案，不要直接重构现有 AI 架构。

## 14. 最终设计原则

**不要把耐力管理做成“AI 什么时候不允许攻击”，而要做成“AI 什么时候觉得这次攻击值得消耗耐力”。**

第一版不追求让 AI 学会完整的体能战术规划，只要求它能区分普通主动进攻与具有明确时机价值的机会攻击，同时保留角色侵略性差异。

耐力是战斗系统的公共资源事实；疲劳后的动作时间是所有角色都必须遵守的物理事实；`fatigueAwareness` 则是 AI 的策略认知差异。三者不要混为一谈。
