# 投掷能力组件化与拾取-消耗方案评审

> 状态：待项目 AI 结合现有代码评审  
> 创建：2026-10-03  
> 背景：Projectile 基础系统已经完成，当前准备补齐 Pickup → Ammo → Throw Consume，并顺手整理 ThrowComponent 职责边界。

---

## 1. 当前已完成的 Projectile 基础链路

目前已经具备：

- `Projectile`
- `ProjectileManager`
- `ProjectileContactResolver`
- Projectile 飞行 / 轨迹
- Projectile ↔ Character 碰撞
- Weapon ↔ Projectile 斩落判定
- Projectile 生命周期
- Projectile 已接入 Scene 的 render interpolation duck-typing

当前 Projectile 不伪装成 Character，不实现假的 `getCombatSnapshot()`。

### CombatSystem 结构

当前倾向保持：

```text
CombatSystem
├── CharacterContactResolver
│   └── character ↔ character
│
└── ProjectileContactResolver
    ├── projectile ↔ character
    └── weapon ↔ projectile
```

Projectile resolver 可以直接读取 Character 的 `getCombatSnapshot()` 获取 weaponbox 所需的：

- `boxRole`
- `attackTrajectory`
- 其他已有攻击数据

不要求 Projectile 拥有 Character 的 stateGraph / animation / attackInstanceId。

例如：

```js
const canCut =
    projectile.cuttable &&
    weapon.boxRole === "attack" &&
    weapon.attackTrajectory === "slash";
```

当前规则：

- slash → 可以斩落 projectile
- thrust → 不斩落 projectile，直接穿过

## 2. 当前 Projectile 的 fixedUpdate / interpolation 约束

BattleMode 当前固定更新链路大致为：

```text
characters.fixedUpdate()
    ↓
pushboxResolver.resolve(combatants)
    ↓
stageBoundary.clampCharacter()
    ↓
projectileManager.fixedUpdate(dtMs, tickCount)
    ↓
combatSystem.fixedUpdate(combatants, projectiles)
    ↓
stageBoundary.clampCharacter()  // post-clamp
```

Projectile 必须在 CombatSystem 的 projectile contact resolve 之前完成本帧运动积分，因此：

```text
Projectile motion integration
    ↓
ProjectileContactResolver
```

顺序不能反过来。

### Scene interpolation

Scene 的 `_snapshotEntityPositions()` / `_restoreEntityPositions()` / `_interpolateEntities()` 已经是 duck-typed：

```js
entity.renderTransform
entity.supportsRenderSampling
entity.snapshotRenderTransform?.()
entity.restoreRenderTransform?.()
```

Projectile 不需要继承 CharacterBase。

只需要提供类似：

```js
this.renderTransform = {
    previous: new BABYLON.Vector3(),
    current: new BABYLON.Vector3()
};

snapshotRenderTransform() {
    // previous ← current
    // current ← root.position
}

restoreRenderTransform() {
    // root.position ← previous
}
```

如果现有调用时序确认是 fixed tick 语义，那么：

```text
renderTransform.previous
```

可以同时作为未来高速 projectile swept collision 的 previous simulation position 使用。

这一点请项目 AI 结合实际 Scene 调用链确认。

## 3. 当前玩家投掷 release 链路

现阶段 Projectile spawn 仍由 `BattleMode` 直接处理：

```text
FrameAnimationComponent.fixedUpdate
    ↓
animation release event
    ↓
AnimationEventBus.dispatch({
    type: "throw_release",
    source: thrower,
    ...
})
    ↓
BattleMode.enter() 中注册的订阅
    ↓
BattleMode.#onThrowRelease(payload)
    ├─ 验证 thrower 是本场 combatant
    ├─ dispose carried sprite
    ├─ thrower.getHandAnchorWorld()
    ├─ 找 opponent / 计算 dirX
    └─ projectileManager.spawn({
           ...dagger 配置...
       })
```

这套实现作为 Projectile 基础系统的 prototype 没有问题。

但现在要加入 ammo / Pickup 后，`#onThrowRelease()` 已经开始承担“投掷能力”的 gameplay 职责，因此倾向做一次小型职责重构。

# 4. ThrowComponent 的职责边界

## 4.1 核心判断

倾向认为：

> `ThrowComponent` 在语义上属于 Character 的 optional gameplay capability，而不是 BattleMode 的业务逻辑。

BattleMode 仍负责 battle orchestration，但不应该知道“怎么投飞刀”的细节。

### 当前建议

```text
AnimationEvent
    ↓
BattleMode.#onThrowRelease()
    ↓
thrower.throwComponent.release(...)
    ↓
ProjectileManager.spawn(...)
```

也就是说：

### BattleMode

负责：

- 接收 `throw_release` 事件
- 验证事件来源 / battle participant
- 提供 battle context（例如发射方向、ProjectileManager）
- 将 release 路由给 throwComponent

不负责：

- dagger 具体配置
- ammo 消耗规则
- “有没有投掷能力”
- Projectile 的具体 gameplay 参数

### ThrowComponent

负责：

- 是否具备投掷能力
- 当前 ammo
- `canThrow()`
- `consumeAmmo()`
- 当前 projectile type / item type
- 在 release 时生成对应 projectile 的请求
- 只有 release 成功时才消耗 ammo

### ProjectileManager

继续负责：

- Projectile 创建
- Projectile update
- active projectile 生命周期
- destroy / flush

不应把 Projectile 生命周期塞进 ThrowComponent。

# 5. ThrowComponent 的生命周期：待结合现有 Component 架构确认

目前有两个候选：

## A. BattleMode 临时装配

```text
BattleMode.enter()
    ↓
有投掷能力的 combatant
    ↓
new ThrowComponent()
    ↓
初始化 ammo
```

BattleMode.exit() 时销毁。

优点：

- 当前投掷只发生在 BattleMode
- ammo 每次进入战斗时重新同步
- 不会让 ExploreMode 中的 Character 挂载无用组件

缺点：

- 从语义上看“投掷能力”并不完全属于 BattleMode

## B. CombatCharacter optional component

```text
CombatCharacter
 ├─ stateGraph
 ├─ ...
 └─ throwComponent? 
```

优点：

- 投掷能力在角色层归属更自然
- 以后如果 ExploreMode 也需要投掷，不需要重构
- BattleMode 只负责初始化本场战斗状态

缺点：

- 当前 ExploreMode 不需要它时可能是多余的

## 当前倾向

更偏向：

> `ThrowComponent` 的语义归属是 Character；BattleMode 负责在进入战斗时装配 / 初始化。

但是否采用这一形式，应以项目现有 Component 生命周期模式为准，不要为了理论上的 ownership 强行改变现有架构。

# 6. Ammo 模型

当前倾向保持“独立计数器”模型：

```text
ThrowComponent.ammo
```

而不是让 ThrowComponent 每次都直接读取 Inventory 数量。

理由：

- AI 不一定拥有 Inventory
- 玩家和 AI 都需要统一通过 `character.throwComponent.ammo` 访问本场可用投掷次数
- `Inventory` 更像探索资源，`ThrowComponent.ammo` 是战斗能力状态

### 玩家进入 BattleMode

```text
inventoryManager.getThrowables("dagger").length
    ↓
throwComponent.ammo
```

### AI 进入 BattleMode

```text
BattleDef.combatant.throwAmmo
    ↓
throwComponent.ammo
```

AI 不需要为了投掷额外创建 Inventory。

# 7. Pickup → Ammo → Consume 数据链

当前背景：

- `PickableEntity`
- `InventoryManager`
- `ExploreMode` pickup sequence

已经存在。

探索阶段：

```text
PickableEntity(dagger pickup)
    ↓
ExploreMode._startPickupSequence()
    ↓
consumeType = "pocket"
    ↓
InventoryManager.addItem(...)
```

建议 Item / Pickup 使用稳定 `itemId` 关联，而不是通过 sprite / prefab / entity class 判断。

例如：

```text
itemId = "dagger"
```

那么：

```text
Pickup
    itemId = "dagger"

ThrowComponent
    projectileId = "dagger"

Projectile
    projectileId = "dagger"
```

sprite / visual 可以分别定义：

```text
dagger
├── pickupVisual
├── heldVisual
├── projectileVisual
└── stuckVisual (future / optional)
```

三种视觉不需要是同一个 sprite。

# 8. 玩家投掷消耗流程

目标：

```text
Player input "throw"
    ↓
StateGraph transition
    ↓
canAct()
    ↓
canThrow()
    ↓
throw state
    ↓
throw animation
    ↓
throw_release animation event
    ↓
BattleMode route
    ↓
ThrowComponent.release()
    ↓
ProjectileManager.spawn()
    ↓
consume ammo
```

## Throw gate

当前倾向：

```text
canAct()      // 已有全局 action / cooldown gate
canThrow()    // 新增，至少要求 ammo > 0
has command
```

即：

> ammo = 0 时，连 throw 状态 / 动画都不进入。

不要等到了 `throw_release` 才第一次发现没有 ammo。

---

# 9. 消耗时机：release 帧

当前倾向：

> ammo 应在真正 release / spawn 成功的时机消耗，而不是进入 throw 状态时消耗。

即：

```text
throw animation
    ↓
release event
    ↓
spawn projectile 成功
    ↓
ammo--
```

这样如果未来动画被中断、状态被取消，未真正释放 projectile 时不会白白消耗弹药。

# 10. Inventory 与 ThrowComponent 的同步

当前设计：

### BattleMode.enter()

```text
Inventory
    ↓
ThrowComponent.ammo
```

### 成功 release 后

```text
ThrowComponent.consumeAmmo()
    ↓
InventoryManager.removeItem("dagger")
```

保持：

```text
1 projectile
↔
1 ammo
↔
1 inventory dagger
```

下次进入 BattleMode 时重新：

```text
inventoryManager.getThrowables("dagger").length
    ↓
throwComponent.ammo
```

不额外做跨 BattleMode 的 ammo persistence。

### 待进一步确认

是否应该由 ThrowComponent 直接触碰 InventoryManager，还是由 BattleMode 在成功 release 后负责同步 Inventory。

当前更倾向：

> ThrowComponent 不直接依赖 InventoryManager。

理由：

- ThrowComponent 需要知道的是本场战斗 ammo
- Inventory 是探索 / 持久资源
- 避免 Character capability component 反向依赖 Explore-side Inventory 系统

因此可能的语义是：

```text
ThrowComponent.release()
    ↓
返回 success / consumed
    ↓
BattleMode 同步 Inventory
```

但请项目 AI 结合当前项目的 service ownership 再确认。

# 14. 建议项目 AI 重点评审的问题

请结合实际代码重点确认以下几点：

### A. ThrowComponent ownership

现有 Component 生命周期机制更适合：

```text
Character optional component
```

还是：

```text
BattleMode runtime component
```

不要只从理论架构判断，要看项目现有 Component 的装配 / dispose 模式。

### B. throw_release 路由

当前：

```text
BattleMode.#onThrowRelease()
    ↓
ThrowComponent.release()
```

是否符合现有 AnimationEventBus / BattleMode ownership。

确认哪些参数应该由 BattleMode 提供，例如：

```text
origin
direction
projectileManager
opponent / target
```

哪些参数应该由 ThrowComponent 自己知道。

### C. Inventory / ThrowComponent 边界

确认：

```text
ThrowComponent
```

是否应该依赖：

```text
InventoryManager
```

还是：

```text
BattleMode 做资源同步
ThrowComponent 只管理战斗 ammo
```

### D. release → consume 的原子性

确认：

```text
ProjectileManager.spawn()
```

失败时是否应该：

```text
ammo 不扣
inventory 不扣
```

最好保证整个 release 是：

```text
success → consume
failure → no consume
```

### E. Scene interpolation

确认 `snapshotRenderTransform()` 的具体调用时序。

如果 previous/current 严格按 simulation tick 更新，则可以未来复用：

```text
renderTransform.previous
```

作为 swept collision 的 previous simulation position。

如果不是，则不要依赖这个双重语义。

### F. 同 tick cut / hit

需要明确：

```text
projectile ↔ weapon
projectile ↔ character
```

同时发生时：

- 被 cut 后本 tick 是否还能 hit character？

第一版建议考虑：

```text
先 resolve weapon cut
→ projectile 已 destroyed / invalid
→ 不再产生 character hit
```

除非现有 CombatSystem 的 effect ordering 有不同约束。

## 16. 本轮实现原则

核心原则只有三个：

1. **BattleMode 编排，不实现 Throw gameplay。**
2. **ThrowComponent 管 Character 的投掷能力，不管理 Projectile 生命周期。**
3. **Projectile 是独立 simulation entity，不伪装成 Character。**

这次重构的目的不是泛化系统，而是让当前已有的 Projectile 基础逻辑和即将加入的 Pickup / Ammo 逻辑形成稳定边界。
