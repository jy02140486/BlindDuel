# 单场景多战斗重构计划

日期：2026-10-16  
场景：`prologue`  
目标：在场景左侧 `x=-25.5` 增加一场可选的 `rabble_stick` 战斗，同时保留右侧原有主线战斗。

## 1. 本次范围

本次支持的是：

- 同一场景内存在多个 battle trigger。
- 每个 trigger 指向独立 BattleDef。
- 每场战斗有独立敌人、边界、镜头配置、失败重试点、入场/退场演出和结算 flag。
- 任一时刻只进行一场战斗。
- 每场战斗严格限定为 **1 名玩家 vs 1 名敌人**。

本次不做：

- 1v2、2v2、多阵营、多敌人同场围攻。
- 群体胜利条件、多 AI 协作、群体碰撞规则。
- trigger 级复杂序列覆盖机制。
- 非参战敌人的通用显隐/冻结框架。

结论：引入 `BattleSession`，但不泛化为完整群战框架。

## 2. 当前核心限制

### 2.1 敌人 controller 是场景级单例

- `Scene.init()` 固定查找 `enemy_1`。
- Scene 只维护一个 `rabbleController`。
- `_rabbleControllerBound` 会阻止第二个敌人绑定自己的 controller。
- `_initRabbleController()` 从所有 entityDef 中找第一个 enemy，而不是使用当前敌人定义。
- `sharedContext.rabbleStick`、`sharedContext.rabbleController`、`actorRegistry["enemy"]` 都是单对手别名。

直接增加 `enemy_2` 会导致其没有正确的 AI 驱动，或运行时仍使用 `enemy_1` 的别名。

### 2.2 Battle trigger 只查出 BattleDef，没有战斗会话

当前触发流程只设置 `pendingBattleDef`，缺少：

- 本次 trigger id；
- 明确的 player/opponent 实体；
- 本场失败重试点；
- 已解析的入场/退场序列；
- 配置有效性校验；
- pending/active 生命周期。

### 2.3 BattleMode 依赖全局唯一对手

- 固定从 context 解构 `rabbleController`。
- 通过 `combatants[0] / combatants[1]` 猜测玩家和敌人。
- 近战、pushbox、投掷物都依赖传入的 combatants 数组，但数组来源仍受单战斗假设影响。
- 胜利后 checkpoint 使用场景第一个 spawn，而不是本次战斗定义的位置。

### 2.4 Timeline / Camera 使用全局敌人别名

入场序列在 BattleMode.enter 前播放，但 Timeline 的 duel blend 和 `fighterDistance` 读取 `ctx.rabbleStick`。因此新战斗的入场镜头必须在 pending 阶段就能找到正确对手。

Scene 初始化时还会读取第一个 battle trigger 的 `stageBounds` 和 `duelCamera`。多战斗场景下，第一场战斗的镜头配置不能代表后续战斗。

## 3. 目标模型

### 3.1 BattleSession

`BattleDef` 是静态配置；`BattleSession` 是某次 trigger 命中后生成的运行时上下文。

本次使用严格 1v1 结构：

```js
{
  triggerId,
  battleId,
  battleDef,
  playerId,
  opponentId,
  player,        // 解析后的 live entity，不复制位置
  opponent,      // 解析后的 live entity，不复制位置
  retryCheckpointSpawnId,
  enterSequence,
  exitSequence,
}
```

不使用 `opponentIds: []`，避免提前引入群战语义。

### 3.2 生命周期

```text
ExploreMode 检测 trigger
  → 解析 BattleDef 和实体
  → 校验 1 player + 1 enemy
  → 创建 pendingBattleSession
  → 应用本场 duelCamera 配置
  → 保存本场失败重试 checkpoint
  → 播放 enterBattleSequence
  → switchMode("battle", { session })
  → BattleMode.enter 设置 activeBattleSession
  → 战斗更新、相机、结算、投掷物均使用 session
  → exitBattleSequence / BattleMode.exit
  → 清理 pending/active session
```

Session 保存的是身份和配置引用，角色位置仍实时从 live entity 读取。

### 3.3 角色身份校验

不能使用 `combatants[0]` 和 `combatants[1]` 作为角色身份来源。Session 创建时应通过 `actorRegistry` 解析实体，并按 `entity.kind` 校验：

- 恰好一个 `kind === "player"`；
- 恰好一个 `kind === "enemy"`；
- 两个实体均存在、未 dispose、未死亡；
- 均具备战斗能力；
- BattleDef 中声明的 id 能在 actorRegistry 中解析。

配置错误时中止进入战斗并输出明确错误，不允许进入序列后才出现相机或 AI 异常。

## 4. 改造方案

### 4.1 Scene：每个敌人独立 controller

- 移除 `_rabbleControllerBound`。
- `_initRabbleController(entityDefs, entity)` 改为 `_initEnemyController(entityDef, entity, hero)`。
- 每个 `kind: "enemy"` 实体生成时，根据自己的 entityDef 创建 controller，并写入 `entity.controller`。
- BattleMode 只驱动当前 session 的 `opponent.controller`。
- 可保留 `rabbleController/rabbleStick/enemy` 兼容旧序列，但新主路径不得依赖这些别名。
- 同名 alias 冲突时输出 warning；BattleDef 和新 sequence 一律使用 `rabble_tutor/rabble_react` 显式 id。
- 新增实例级 AI 配置注入：entityDef 携带 `aiProfile`（7 个性格 knob）与可选 `aiTuningOverrides`（如 `attack.baseWeight/preemptiveBonus`、`defense.reflexMaxMs`），Scene 创建 AIController 时深合并出**实例专属 tuning**，禁止直接污染全局 `AITuning` 单例。
- 统一 aiProfile 读取路径：当前 `attackPreferences` 读 `tuning.aiProfile`、`throwPreference` 读 `stateGraph.aiProfile`，而 AITuning 默认无 aiProfile，导致偏好实际不生效。改造后实例注入的 profile 必须同时接通 Posture 与 Utility 两层。

### 4.2 ExploreMode：创建 BattleSession

新增统一的 session 构建逻辑：

1. 遍历 enabled battle triggers。
2. 多个 trigger 重叠时，选择距离 hero 最近的一个；距离相同按 JSON 顺序兜底。
3. 读取 `BATTLE_DEFS[triggerDef.battleId]`，缺失则报错并中止。
4. 根据 BattleDef combatants 和 actorRegistry 解析 player/opponent。
5. 解析本场序列：BattleDef 优先，SceneDef 共享序列兜底，最后代码 fallback。
6. 读取 `triggerDef.checkpointSpawn` 作为失败重试点。
7. 创建 `context.pendingBattleSession`。
8. 播放入场序列。

### 4.3 Timeline：从 pending session 取战斗双方

- duel blend 的中心点、Y baseline、fighterDistance 从 `pendingBattleSession.player/opponent` 读取。
- `switchMode("battle")` payload 传递 session。
- 新 prologue 序列使用显式 `rabble_tutor/rabble_react`，不再使用通用 `enemy`。

### 4.4 Camera：入场前应用本场配置

分两步：

- pending 阶段：应用 `battleDef.duelCamera`，保证入场 blend 使用本场镜头参数。
- active 阶段：BattleMode 应用 `stageBounds` 和战斗运行参数。

Scene 初始化不再从第一个 battle trigger 推断全局 stageBounds/duelCamera，只设置安全默认值。

### 4.5 BattleMode：只处理当前 session

- `enter({ session })` 保存 active session。
- player/opponent 从 session 获取，不再从数组位置猜。
- AI 固定调用 `opponent.controller.fixedUpdate()`。
- CombatSystem、PushboxResolver、StageBoundary、ProjectileContactResolver 继续只接收本场 `[player, opponent]`。
- 非当前敌人不进入战斗系统，因此不需要在各 resolver 内增加全局阵营过滤。
- 胜负仍按严格 1v1：player 死亡则失败；opponent 死亡则胜利。
- exit 时清理 active session 和本场投掷物。

### 4.6 Checkpoint 语义

区分两类 checkpoint：

1. **失败重试 checkpoint**：进入战斗前由 trigger 的 `checkpointSpawn` 保存，用于本场战败恢复。
2. **进度 checkpoint**：战斗胜利后是否更新，由 BattleDef 显式声明。

左侧可选战斗胜利后不应默认把全局进度复活点改到场景左侧。没有显式 `onVictory.checkpoint` 策略时，保留当前进度 checkpoint，不再使用 `Object.keys(sceneDef.spawns)[0]`。

战败恢复通过现有整场景重载完成：flags 恢复到入场前快照，未完成战斗的敌人会按 `spawnIf.flagNot` 重新创建，因此不需要单独回滚敌人状态。

## 5. Prologue 数据要求

### 5.1 两个敌人命名与定位

两者 `archetype` 都是 `rabble_stick`（同一工厂与 StateGraph），用实体 id 与实例级 AI 配置区分：

| 实体 id | 位置/战斗 | 行为定位 |
|---|---|---|
| `rabble_tutor` | 右侧原主线 `prologue_battle`（替代现 `enemy_1`） | 教学敌人：模式化、**无预测能力**、偏好 `swing` |
| `rabble_react` | 左侧新增 `prologue_extra_battle` | 预测机制引入前的普通敌人：**较弱预测**、其它招数标准 |

### 5.2 AI 行为配置

参考 `docs/AI系统说明.MD`：

- `rabble_tutor`（教学型）
  - 采用文档教学 profile：高进攻、慢人格切换、低变招成本，`attackPreferences` 明显偏向 swing，如 `{ swing: 1.6, thrust: 0.4, dash: 0.3 }`。
  - **无预测**：角色级 `attack.preemptiveBonus = 0`，使 `#scoreAttack` 不产生 PREEMPTIVE 抢先截断，退回静态评分 + recovery PUNISH；不读取预测事件做抢先决策。
- `rabble_react`（弱预测反应型）
  - 采用文档“被动反应型”：低 `attack.baseWeight`、极低但非 0 的 `preemptiveBonus`（约 0.08），`attackPreferences` 接近标准（不强行偏 swing）。
  - 通过 `defense.reflexMaxMs` 注入反应抖动，表现为反应慢/时机不稳，对应“较差的预测能力”。

工程前置（B6 不在本次落地）：

- 完整 `predictionAccuracy`（识别率/timing 噪声/reactionDelay）仍在 backlog，本次不做。
- “无/弱预测”仅用 `preemptiveBonus` 与 `reflexMaxMs` 表达；后续 B6 落地后再替换为统一精度旋钮。
- 因两敌人共用 StateGraph，上述 profile/tuning override 必须走 entityDef 实例注入，不能写进共用的 `RabbleStick.json`。

### 5.3 战斗与场景数据

- `bt_prologue_extra`：`pos = [-25.5, y, 0]`，`battleId = prologue_extra_battle`。
- `prologue_extra_battle`：combatants 为 `hero` 与 `rabble_react`。
- 原 `prologue_battle` 的 combatant 由 `enemy_1` 改为 `rabble_tutor`。
- 独立失败重试 spawn，位置必须在 trigger AABB 外。
- 左侧专用 enter sequence；Charlotte 的撤退位置不能继续写死为 `x=-9`。
- 左侧胜利只写 `prologue_extra_battle` flag，不推进主线 scenario。

位置注意：altar 位于 `x=-25`，blocker 半宽 2.6、半高 0.8、centerY 1.4，约覆盖 X `[-27.6,-22.4]`、Y `[0.6,2.2]`。trigger 的 Y、敌人初始点、battle bounds 和 checkpoint 必须结合 walkArea 与 altar blocker 实测，不能只设置 X。

## 6. 实施顺序

采用“先重构、后加内容”的两阶段推进，每阶段结束都有可运行、可回归的状态，便于定位问题。

### 阶段 A：Session 抽象（零数据改动，行为保持等价）

> 本阶段不改任何 SceneDef/BattleDef 数据，敌人 id 仍为现有 `enemy_1`；目标是仅替换运行时组织方式，现有战斗表现与改造前一致。

1. 固定 BattleSession 契约、严格 1v1 校验和 pending/active 生命周期。
2. 改 Scene 的敌人初始化为“每敌人独立 controller”，并搭好 entityDef 实例级 AI 配置注入通道（本阶段不注入新 profile，行为保持默认）。
3. 改 ExploreMode：trigger 命中后构建 session、解析实体/序列、保存 retry checkpoint、播放入场序列；多 trigger 重叠取最近。
4. 改 Timeline 和 Camera：入场前从 pending session 取双方并应用本场 duelCamera，替代全局敌人别名。
5. 改 BattleMode：按 session 驱动 AI、战斗数组、结算；拆分 retry checkpoint 与进度 checkpoint 语义。
6. **回归门禁（必须全绿才进入阶段 B）**：现有全部战斗零数据改动跑通——序章 `prologue_battle`、`battle_field_1/2`、tavern room，覆盖胜利、战败恢复、投掷物、镜头切换与 X/C 调试开关。

### 阶段 B：接入序章新战斗

7. 数据落地：现有 `enemy_1` 更名为 `rabble_tutor`（原主线战斗 combatant 同步改名）；新增 `rabble_react`、`bt_prologue_extra`、`prologue_extra_battle` 与独立 flag。
8. 分别为两个敌人注入实例级 aiProfile/tuning：tutor 教学型+无预测，react 弱预测反应型；确认 attackPreferences/posture 实际生效。
9. 制作左侧专用 enter sequence（含 Charlotte 撤退位置）、敌人站位、bounds、checkpoint，并结合 altar blocker 实测 Y 坐标。
10. 左侧战斗纵向验证（胜利/战败/镜头/AI 性格），再做一次全战斗回归。

## 7. 验收清单

### 7.1 阶段 A 重构基线（数据未变）

- 现有各战斗触发、入场、AI、镜头、stageBounds、投掷物、pushbox 行为与改造前一致。
- 主流程已不依赖 `rabbleStick/rabbleController/enemy` 全局别名（旧别名仅作兼容保留）。
- 多个 battle trigger 按距离选择最近一个；BattleDef/actor 配置错误时明确报错且不进入序列。
- 战败恢复到对应 trigger 的安全 spawn，不立即重入 trigger；胜利 checkpoint 语义按 BattleDef 显式策略。
- 控制台无 BattleDef 缺失、actor 缺失、controller undefined、camera distance NaN/跳变等错误。
- X/C 调试开关仍能统一控制 AI 与碰撞可视化。

### 7.2 阶段 B 新战斗

- scenario < 105 时，左侧敌人与 trigger 不生效。
- scenario >= 105 时，左右两个敌人和两个 trigger 可独立存在。
- 左侧 trigger 只开启 `rabble_react` 战斗；右侧 trigger 只开启 `rabble_tutor` 战斗。
- `rabble_tutor` 行为模式化、以 swing 为主，且不会做 PREEMPTIVE 抢先截断（无预测）。
- `rabble_react` 招数偏好标准、预测/反应较弱且时机不稳定，表现接近预测机制前的普通敌人。
- 两个敌人的性格差异来自 entityDef 实例注入，全局 `AITuning` 单例不被污染；attackPreferences/posture 实际生效。
- 两场战斗的 AI、镜头、stageBounds、投掷物、pushbox 都只作用于本场 player/opponent。
- 非当前敌人不出现在本场镜头中；如入镜，只按场景数据处理站位或显隐，不引入全局群战规则。
- 左侧胜利只写 `prologue_extra_battle`，不推进 scenario，不默认改变全局进度 checkpoint。
- 右侧主线胜利仍推进 `SCENARIO.BATTLE_1_COMPLETED`。
- 任一战战败后恢复到本场 trigger 对应的安全 spawn，且不会立即重新踩入 trigger。
- 战败重载后，本场敌人以初始位置、HP、AI 状态重建；已完成的另一场战斗不回滚。
- 新序列使用显式敌人 id，旧序列保持兼容。
