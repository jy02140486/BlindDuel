# AI 招式伤害与 Tag 条件修饰接入方案

> 类型：AI 系统增量扩展
>
> 原则：保持现有四层架构与 Utility 决策机制不变，仅补充攻击知识及运行时有效参数。
>
> 状态：待项目代码审查与方案确认

## 1. 背景与目标

近期战斗系统引入了不同招式的伤害差异：

| 招式类型 | 伤害 |
|---|---:|
| 轻攻击 | 1 |
| 重攻击 | 2 |
| 派生攻击 | 3 |

但当前 AI 尚未接入伤害信息。

另外，项目对派生攻击的设计并不是一个可以随时使用的独立高伤害招式，而是一套基于 Tag 的条件修饰机制：

1. 角色执行前置招式后，按照现有战斗规则获得相应 Tag。
2. 在 Tag 有效期间，执行符合条件的后续招式。
3. 该招式获得对应的效果，例如启动时间加速。
4. Tag 的产生、持续、消耗和具体效果由战斗系统现有规则决定。

因此，同一个攻击招式在不同运行时状态下，可能具有不同的实际启动时间和战斗收益。

本次扩展希望让 AI 能够识别这种差异，避免始终使用静态 Attack Profile 进行决策。

### 核心目标

- AIKnowledgeRegistry 能够获取招式伤害信息。
- AI 能够识别招式与 Tag 之间的条件修饰关系。
- AI 计算攻击时，能够使用当前 Tag 状态下实际生效的攻击参数。
- 现有 Startup Factor、Preemptive Bonus、预测事件等机制能够使用正确的有效启动时间。
- 不改变现有 Utility 决策架构，不引入新的高层决策机制。

## 2. 设计原则

### 2.1 区分基础攻击数据和运行时有效数据

建议保留两个概念。

**Base Attack Profile**

描述招式本身的基础属性，由 AIKnowledgeRegistry 从现有攻击配置中提取。

示意：

```js
{
    attackId: "derived_attack",
    damage: 3,
    startupMs: 600,
    // 其他已有攻击属性
}
```

**Effective Attack Profile**

描述攻击者在当前运行时状态下，实际能够执行出的攻击属性。

例如：

```text
Base Attack Profile:
    startupMs = 600
    damage = 3

当前没有对应 Tag:
    effectiveStartupMs = 600

当前拥有对应 Tag:
    effectiveStartupMs = 300
```

以上数值仅为示例，实际倍率和效果以项目现有战斗规则为准。

### 2.2 Tag 是条件修饰，不默认作为独立招式或候选类型

不要因为引入 Tag 就增加新的 Utility candidate kind。

派生攻击仍然是原有攻击候选，只是其有效参数受到角色当前 Tag 状态影响。

也不要默认 Tag 是招式解锁条件。除非检查现有代码后发现它确实控制招式可用性，否则应将其视为条件性 Modifier，而不是候选资格判断。

### 2.3 战斗系统是规则权威

AI 不应自己重新定义 Tag 的产生和效果。

需要检查：

- Tag 在什么条件下产生。
- 是攻击启动、完成、命中还是其他事件触发。
- Tag 是否有持续时间。
- Tag 是否会被消耗。
- Tag 能否被覆盖或叠加。
- Tag 对哪些招式生效。
- Modifier 实际修改了哪些攻击属性。

AI 只读取和评估战斗系统已经定义的规则。

如果战斗系统已有获取有效攻击参数的方法，应优先复用，而不是在 AI 中复制一套 Modifier 计算逻辑。

如果没有合适的共享接口，再评估是否需要抽取一个轻量级的纯计算函数，避免产生两套可能不一致的规则实现。

## 3. 第一阶段：扩展 AIKnowledgeRegistry

目标：让 AI 获得完整的基础攻击知识，但暂时不改变决策结果。

为现有 Attack Profile 补充：

- damage
- 对应 Tag Modifier 的描述或引用
- 已有的 startup 等基础攻击属性

示意：

```js
{
    attackId: "derived_attack",
    damage: 3,
    startupMs: 600,
    tagModifiers: {
        "followup_bonus": {
            startupMultiplier: 0.5
        }
    }
}
```

注意：

1. 上述结构仅是概念示例，不要求直接采用该字段命名。
2. 如果现有 Tag 系统已经有自己的 Modifier 配置，应引用或读取现有配置。
3. 不要在 aiProfile 中复制一份伤害和 Tag 规则。
4. 不要为了满足 AI 而建立第二份权威攻击配置。
5. 缺少伤害或 Modifier 信息时，应保持合理的兼容行为，不应导致攻击候选失效。

本阶段只接入数据，不增加 damage bonus，也不改变 Utility 排序。

## 4. 第二阶段：引入 Effective Attack Profile

这是本次扩展的核心。

在 AI 评估攻击候选时，基于攻击者当前实际持有的 Tag，获取攻击的有效参数。

建议数据流：

```text
AIKnowledgeRegistry
    |
    | Base Attack Profile
    v
Attack Candidate
    |
    | 查询当前角色 Active Tags
    v
Effective Attack Profile
    |
    | 应用现有战斗规则的 Modifier
    v
Utility Scoring
```

### 4.1 启动时间必须保持一致

当前 AI 有多处逻辑依赖攻击启动时间，例如：

- Startup Factor
- Preemptive Bonus
- 对手攻击窗口比较
- 攻击可行性判断
- predictedOpponentEvents 相关的时序判断

这些逻辑不能一部分使用 Base Startup，另一部分使用 Effective Startup。

应先梳理项目中所有读取 `startupMs` 或同等数据的路径，再决定如何统一接入有效参数。

尤其需要注意：

**AI 使用的有效启动时间必须与战斗系统实际执行该招式时使用的启动时间一致。**

例如，角色持有 Tag 时，战斗动画或攻击状态实际提前了攻击生效时刻，那么 AI 的时序预测也必须反映这个变化。

反之，如果 AI 只修改自己的评分计算，却没有对应实际攻击时序，就会出现决策认为自己可以抢先攻击，但实际攻击仍然来不及的错误。

### 4.2 同时考虑对手的 Tag

现有 AI 会读取 opponent KB，并且有 predictedOpponentEvents 预测机制。

因此需要检查是否也应该为对手计算 Effective Attack Profile。

例如：

```text
对手当前持有 followup_bonus
    |
    v
预测对手对应攻击的有效 Startup
    |
    v
生成 predictedOpponentEvents
    |
    v
当前 AI 根据实际预测时序决定反应
```

否则，AI 可能知道自己持有 Tag 时能够加速攻击，却无法识别玩家持有相同 Tag 后的攻击时序变化。

这一部分需要复用现有对手状态读取机制，不额外建立新的感知系统。

### 4.3 避免修改共享静态数据

不要因为某个 AI 角色获得 Tag，就直接修改共享的 Base Attack Profile。

不同角色、不同实例可能处于不同 Tag 状态。

Effective Attack Profile 应当是基于当前攻击者实例和当前状态计算出的结果，避免出现不同角色之间互相污染攻击数据的问题。

如果考虑缓存，需要明确 Tag 变化、失效和消耗时的缓存更新机制。首轮实现优先考虑简单、正确的计算方式，不必提前优化。

## 5. 第三阶段：伤害信息接入决策，但暂不实施

本次不建议立即让伤害参与 Utility 评分。

原因是伤害与攻击可行性不是一回事。

例如：

| 招式 | 伤害 | 基础启动时间 |
|---|---:|---:|
| 轻斩 | 1 | 200ms |
| 重斩 | 2 | 450ms |
| 派生攻击 | 3 | 600ms |

即使派生攻击具有最高伤害，也不代表它在所有情况下都是最优选择。

- 对手处于较长恢复窗口时，派生攻击可能有更高收益。
- 对手正在发动快速突刺时，轻攻击可能具有拦截价值。
- 当前攻击机会不足时，AI 可能应该防御或调整位置。

而且当前 Utility 候选池中，Attack、Defense、Positioning 是相互竞争的。

直接将伤害作为普遍攻击 Bonus，可能导致：

- 高伤害招式过度占据攻击候选优势。
- 原有轻攻击拦截能力下降。
- 攻击相对于防御和走位的竞争力意外上升。
- 原有角色人格和攻击偏好受到破坏。

因此，本次只要求 AI 能读取伤害数据，不要求 AI 立即根据伤害改变决策。

后续如果确认有必要，再单独讨论：

- 相近 Utility 的攻击候选之间，是否可以将伤害作为次级排序依据。
- 是否根据对手恢复窗口评估不同伤害招式的收益。
- 是否值得进一步考虑前置招式创造派生机会的策略价值。

尤其是最后一项涉及多步动作规划，不应混入本次修改。

## 6. 回归测试与验收标准

本次修改应重点验证数据一致性和原有行为稳定性。

### 测试 A：Tag 不存在

角色没有对应 Tag。

- 攻击使用基础启动时间。
- 伤害读取正确。
- 原有 Utility 决策结果不应因为本次数据接入而改变。

### 测试 B：Tag 存在

角色拥有对应 Tag。

- 有效攻击参数正确应用 Modifier。
- 实际攻击时序与 AI 使用的时序一致。
- Startup Factor 使用有效启动时间。
- Preemptive Bonus 使用有效启动时间。
- 不出现预测时序和实际攻击时序不一致。

### 测试 C：Tag 失效或消耗

- AI 不再使用过期 Tag 的效果。
- 不残留之前的 Effective Profile。
- 再次获得 Tag 后能够重新计算。

### 测试 D：对手持有 Tag

- 能够读取对手的实际 Tag 状态。
- 对手的预测攻击时序反映 Tag 修饰。
- 原有防御和预判逻辑仍然正常。

### 测试 E：回归整体决策

比较修改前后：

- 攻击频率
- 防御频率
- Positioning 选择比例
- 轻攻击与重攻击使用情况
- 拦截行为
- 角色之间的行为差异

由于本次第一阶段不应该改变 Utility 评分，所以如果仅仅接入伤害和 Tag 知识就导致行为大幅变化，应检查是否意外改变了原有数据或计算路径。

## 7. 本次明确不做的事情

为了控制风险，以下内容不纳入本次实施范围：

1. 不重构 Memory / Situation / Posture / Utility 四层架构。
2. 不增加新的 Utility candidate kind。
3. 不改变 Action Commitment。
4. 不调整现有 aiProfile 人格参数。
5. 不修改 CombatMemory 和 Feedback Learning。
6. 不引入完整的 Expected Damage 或攻击收益预测系统。
7. 不让 AI 为了获得派生 Tag 而自动规划前置攻击序列。
8. 不在本次直接增加高伤害攻击偏好。
9. 不复制战斗系统已有的 Tag 产生和 Modifier 规则。

## 8. 希望项目 AI 先完成的工作

本轮首先是代码审查和实施方案确认，不要求直接开始大范围修改。

请检查：

1. 现有伤害数据具体存储在哪里，AIKnowledgeRegistry 如何扫描和读取攻击配置。
2. Tag 系统的真实数据结构、产生时机、持续及消耗规则。
3. Tag Modifier 如何影响实际攻击启动时间，以及是否还影响其他属性。
4. 战斗系统是否已有获取有效攻击参数的接口。
5. AI 当前所有使用基础 Startup 数据的代码路径，尤其是 Utility、Startup Factor、Preemptive Bonus 和 predictedOpponentEvents。
6. 对手 Tag 状态能否通过现有感知机制获得。

然后给出：

- 现有代码结构与本方案的对应关系。
- 最小修改范围。
- 是否需要共享的 Effective Attack Profile 计算接口。
- 可能影响原有行为的风险点。
- 建议的实施顺序和回归测试方案。

如果现有系统已经有可复用的机制，应优先复用，不要为了符合本文的示意结构而重构现有代码。

## 9. 最终设计方向

本次扩展的核心不是让 AI 更喜欢高伤害招式，而是让 AI 理解：

**同一个招式的实际战斗性能，可能取决于角色当前所处的运行时状态。**

过去的 AI 主要依赖静态 Attack Profile 进行决策。现在需要在保留现有架构的基础上，让攻击评估能够反映当前 Tag 对招式的实际修饰。

先解决知识正确性和时序一致性，再考虑是否需要将伤害和派生机会引入更高层次的收益评估。

保持增量迭代，不推倒现有系统。
