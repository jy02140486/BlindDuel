# Phase 3 — Startup Utility 实施计划

> 基于 `AI_Decision_Adaptation_Guideline.md` Phase 3
> 目标：把 startupMs 从「特殊 preemptive 条件」升级为一般性时间价值输入

---

## 问题背景

当前 `#scoreAttack` 里 timing 只用了一处：

```javascript
// opponent 在 startup 且我能在他 active 前出手 → 加分（抢先）
if (sit.opp.phase === "startup" && timing) {
    const myStartupMs = timing.startupMs ?? 0;
    if (myStartupMs <= sit.opp.remainingMs) score += this.tuning.attack.preemptiveBonus;
}
```

这导致 reach 稍长的招式长期统治 reach 稍短但 startup 更快的招式——快招的时间优势没有在评分里体现。

## 架构约束（不变）

```
Knowledge 层     — AIKnowledgeRegistry 已提供 timing.startupMs / activeMs / recoveryMs
Rules 层         — CombatResolver 判定结果，只读不改
Decision 层      — AIController 评分公式内加 context-sensitive factor
```

**KB timing 数据已就绪**（`AIKnowledgeRegistry.#scanAttackState`）：

```javascript
attackProfile.timing = {
    startupMs,   // 从状态 enter 到第一个有 weaponbox 的帧
    activeMs,     // 所有 active 帧的累计时间
    recoveryMs,   // 最后一个 active 帧到动画结束
    totalMs       // 三者之和
}
```

## 设计：三个 context-sensitive 场景

### 核心公式

在 `#scoreAttack` 里加一个 startup factor，以乘法形式作用在现有 score 上（不是加法），因为 startup 好坏影响的是「这个攻击在当前局面下有多划算」，不是简单的加分项。

```text
startupFactor = 1.0 + startupReward - startupRiskPenalty
```

其中 startupRatio = minStartupMs / myStartupMs（范围 (0, 1]，越大越快）：

| 变量 | 计算 | 含义 |
|---|---|---|
| `startupReward` | `recoveryStartupBonus * startupRatio` | opp recovery 时，快招（ratio→1.0）拿满额奖励，慢招拿得少 |
| `startupRiskPenalty` | `activeStartupPenalty * (1 - startupRatio)` | opp active 时，慢招（ratio→0）扣分多，快招扣分少 |

### 场景 1：Opponent Recovery — Punish 窗口短才是真短

```text
opponent 在 recovery 阶段
  + 我的 startupMs 越小 → 越容易在 opponent 恢复前命中
  → 快招加分
```

实现：
```javascript
if (sit.opp.phase === "recovery") {
    const reward = this.tuning.attack.recoveryStartupBonus * startupRatio;
    // startupRatio 越大（越快）→ reward 越大
    // ratio=1.0（最快招）拿满额 recoveryStartupBonus
    // ratio=0.68（慢招）只拿 68% 的奖励
}
```

### 场景 2：Opponent Active — 被打断的风险

```text
opponent 正在 active（已经出刀了）
  + 我在他 reach 内
  + 我的 startupMs 越长 → 越可能在 startup 阶段被打断
  → 长招风险扣分
```

注意：**现有 threatPenalty 已经在 opp.active + in-range 时扣分**，但它不区分我自己是快招还是慢招。这里要加的是「同样有威胁，你是 120ms 快招还是 420ms 慢招」的差异。

实现：
```javascript
if (sit.opp.phase === "active"
    && sit.distance <= (sit.opp.attackProfile?.range?.maxReach ?? 99)) {
    const riskPenalty = this.tuning.attack.activeStartupPenalty * (1 - startupRatio);
    // startupRatio 越小（越慢）→ riskPenalty 越大（扣分越多）
    // ratio=0.68（慢招）扣 32% 的 activeStartupPenalty
    // ratio=1.0（最快招）riskPenalty = 0，不额外扣分
}
```

### 场景 3：距离 — 只有在接近时时间差才重要

```text
距离远 → 无论快招慢招，都得先走近 → startup 差异不重要
距离近 → startup 差异直接影响命中窗口
```

实现：用距离权重平滑衰减上面两个 factor。当 `distance > effectiveRange * 0.7` 时衰减到 0。

## startupRatio 定义

startupMs 是绝对值，不能直接乘。需要一个归一化基准：

```javascript
// 方法一：相对 self KB 中最快的攻击
const selfAttacks = this.kbProfile.attacks;
const minStartupMs = Math.min(...selfAttacks.map(a => a.timing.startupMs));
const startupRatio = minStartupMs / (timing.startupMs ?? minStartupMs);
// 最快招 → ratio = 1.0；慢招 → ratio < 1.0
```

startupRatio 范围 (0, 1]。值越大 = 越快 = 越好。

**设计取舍**：用 self-relative 基准（而非 opp-relative），因为我们比较的是「self 各种攻击之间的 startup 快慢」。opp 的 timing 影响的是 opp.recoveryMs / opp.startupMs 这些 context，已经在场景判断里用了。

## Tuning 参数（进 AITuning.attack）

| 参数 | 初始值 | 含义 |
|---|---|---|
| `recoveryStartupBonus` | 0.12 | opp recovery 时快招的最大加分（ratio=1.0 最快招拿满额） |
| `activeStartupPenalty` | 0.10 | opp active + in-range 时长招的最大扣分（ratio→0 最慢招扣满额，ratio=1.0 最快招不扣） |
| `distanceStartupSmooth` | 0.3 | startup factor 开始衰减的距离窗口 |

**不新增 startupRatio 基准**——算法内部从 KB 动态算（self KB 中最快攻击的 startupMs），不暴露给 tuning。

## 接入点

在 `#scoreAttack` 里，**现有 score 计算完成后（feedback/continuity 之后），clamp 之前**，乘上 startupFactor：

```javascript
// ... 现有所有 score += / -= ...

// ---- Phase 3: Startup Utility ----
const startupFactor = this.#computeStartupFactor(attack, sit);
score *= startupFactor;

return Math.max(0, Math.min(1, score));
```

用乘法而不是加法的原因：startup 影响的是「这个攻击值不值得现在出」，和 reach feasibility 的语义一致（reach 远的时候 return 0 本质就是 score *= 0）。

## 验证标准

| 场景 | 预期行为 |
|---|---|
| AI 有 swing（reach 2.67, startup 420ms）和 thrust（reach 2.56, startup 320ms），opp 在 recovery | thrust 因为 startup 快，在 recoveryStartupBonus 作用下比 swing 得分更高 → AI 出 thrust |
| opp 正在 active，双方距离近，AI 可选快招 (320ms) 或慢招 (420ms) | 慢招 activeStartupPenalty 扣分多 → 快招胜出 |
| 距离远（接近 effectiveRange 上限） | startupFactor 衰减到 1.0（无影响）→ 现有 reach + feedback 逻辑主导 |
| opp 在 startup（现有 preemptiveBonus 场景） | startupFactor 的 reward 不重复加（preemptiveBonus 是加法，startupFactor 是乘法，已正交） |

## 设计取舍

**Q: 为什么用乘法而不是加法？**
加法下 `baseWeight + bonus - penalty` 会让 startup 和其他维度（reach、feedback）线性叠加，无法真正表达「这个攻击现在出就很蠢」的语义。乘法自然让差招趋近 0，和现有 `return 0` 门控语义对齐。

**Q: 为什么 startupRatio 用 self KB 基准而不是 opp 的？**
因为我们比较的是「self 各种攻击之间的 startup 快慢」，和 opp 无关。opp 的 timing 影响的是 opp.recoveryMs / opp.startupMs 这些 context，已经在场景判断里用了。

**Q: 为什么 distance 衰减用 effectiveRange * 0.7 而不是更激进的值？**
让 startup factor 在大部分接近场景（0 ~ 0.7 effectiveRange）全效工作，只在边缘区域让 reach 主导。0.3 的 smooth window 让衰减平滑不跳变。实际数值后续可在 Phase 5 微调。
