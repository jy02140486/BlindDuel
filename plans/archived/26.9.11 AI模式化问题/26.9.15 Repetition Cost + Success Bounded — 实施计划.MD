# Repetition Cost + Success Bounded — 实施计划

> 目标：解决"连续命中同招后 AI 锁死"的问题
> 核心机制：Success Memory（短期有效信号）与 Repetition Cost（重复行为成本）两个相反的力
> 基于 GPT 反馈的模型重梳理

---

## 问题诊断

当前 Attack Utility 评分模型中，让 AI 锁死同招的根本原因是**成功信号无封顶 + 重复无成本**：

| 现有机制 | 问题 |
|---|---|
| `feedbackSuccessBonus = 0.05 × consecutiveSuccess` | 无封顶，连续命中 10 次 +0.50 直接 clamp 到 1.0 |
| `continuityBonus = +0.05/次` （每次同招都加） | 从"tie-break"变成主动力 |
| `reactionVariance = 0.15` (±7.5%) | 分数差 > 0.15 时翻不动牌 |

**没有任何机制告诉 AI："这招虽然好，但别因为好就无限重复。"**

---

## 设计原则

1. **Success = 短期有效信号**（有界，只反映最近 2~3 次）
2. **Repetition Cost = 重复行为的边际成本**（随连续使用次数线性增长）
3. **Continuity = 弱 tie-break**（只避免两个相近分数来回抖）
4. **Random = 最终 tie-break**（分数接近时才介入）
5. **四档 profile = repetitionCostRate 的四个预设值**（连续值而非开关）

---

## 新 Attack Utility 评分结构

```
Attack Utility
    = SituationValue          // 现有：distance + startup + reach + oppPhase + interaction + risk
    + ShortTermSuccess        // 改：封顶 0.15（最近 3 次成功）
    + Continuity              // 改：降为 +0.02（弱 tie-break）
    - RepetitionCost          // 新增：rate × min(count-1, maxCount)
    - FailureCost             // 保留：feedbackFailPenalty × consecutiveFail
```

所有加性项之后 × startupFactor × rangeFactor → clamp 到 [0, 1]

### 和现有架构的关系

**完全兼容**。Knowledge → Situation → Utility → Commitment → Outcome → Memory 架构不变。

## Step 1: 计数器 — consecutiveAttackUsage（新增字段）

### 语义

"连续选择同一个 attack action 的次数"。**被非 attack 动作打断就 reset**。

```
Committed 序列: Thrust → Thrust → Guard → Thrust
                                        ↑
                         Thrust 的 consecutiveAttackUsage.count = 1
                         （Guard 打断了连续 attack，reset 后重新开始计数）
```

### 数据结构

```javascript
// AIController.js 私有字段
#consecutiveAttackUsage = null;  // { stateName: "thrust", count: 2 }
```

### 更新逻辑（接入点：#executeCommitted）

```javascript
// #executeCommitted({ kind, action }) 内更新
if (kind === "attack") {
    if (this.#consecutiveAttackUsage?.stateName === action.stateName) {
        this.#consecutiveAttackUsage.count++;
    } else {
        this.#consecutiveAttackUsage = { stateName: action.stateName, count: 1 };
    }
} else {
    // dodge / guard / positioning → reset
    this.#consecutiveAttackUsage = null;
}
```
### 为什么不直接从 #memory entries 推导

`#memory` 只存 attack outcome（hit/miss/guard_block），不存非 attack 的 committed。所以 `Thrust→Thrust→Guard→Thrust` 在 memory 里是连续 3 个 Thrust outcome，会错误地算成 count=3。**计数器独立维护更干净**。

## Step 2: Repetition Cost 计算（#scoreAttack 新增减项）

### 公式

```javascript
const usageCount = (this.#consecutiveAttackUsage?.stateName === attack.stateName)
    ? this.#consecutiveAttackUsage.count
    : 0;

const rcRate = this.tuning.attack.repetitionCostRate ?? 0.06;
const rcMax  = this.tuning.attack.repetitionCostMax ?? 0.18;

// 连续第一次：cost=0（-1 从 0 开始）
// 连续第二次：cost=rate×1
// 连续第三次：cost=rate×2 → clamp 到 rcMax
const repetitionCost = Math.min(rcMax, rcRate * Math.max(0, usageCount - 1));
score -= repetitionCost;
```
### 接入位置

在 `#scoreAttack` 内，所有加性项之后、乘性项之前（startupFactor × rangeFactor 之前）。

### 数值推演

tuning: repetitionCostRate=0.06, repetitionCostMax=0.18, successMaxBonus=0.15

连续命中场景（Thrust 基础分 0.70，Swing 基础分 0.75）：

| 连续次数 | Thrust success | Thrust repetition | Thrust 净 | Swing（无 repetition） | 结果 |
|---|---|---|---|---|---|
| 1 | +0.05 | 0 | 0.75 | 0.75 | **平手→tie-break** |
| 2 | +0.10 | -0.06 | 0.74 | 0.75 | **Swing 略优** |
| 3 | +0.15（封顶）| -0.12 | 0.73 | 0.75 | Swing 稳定领先 |
| 4 | +0.15（封顶）| -0.18（封顶）| 0.67 | 0.75 | Swing 明显领先 |

**明显更好的情况**（Thrust 在该场景真的应该赢）：

| 连续次数 | Thrust base | Thrust 净 | Swing base | 结果 |
|---|---|---|---|---|
| 任意 | 0.95 | 0.85（cost 封顶后） | 0.40 | **Thrust 继续** ✓ |

这正是"可预测但不机械"——强招持续赢，只是锁死的场景被打破了。

## Step 3: Success Bonus 封顶（修改）

### 当前

```javascript
if (adaptation.consecutiveSuccess >= 1) {
    score += this.tuning.attack.feedbackSuccessBonus * adaptation.consecutiveSuccess;
}
// 无封顶
```

### 改后

```javascript
const cappedSuccess = Math.min(adaptation.consecutiveSuccess, this.tuning.attack.successMaxCount ?? 3);
if (cappedSuccess >= 1) {
    score += this.tuning.attack.feedbackSuccessBonus * cappedSuccess;
}
// 封顶 3 次 → 最多 +0.15（反馈成功封顶保持不变）
```
---

## Step 4: Continuity 降级（修改）

### 当前

```javascript
if (attack.stateName === this.#lastCommittedState && adaptation.consecutiveFail < 2) {
    score += this.tuning.attack.continuityBonus;  // +0.05
}
```

### 改后

```javascript
// 改为小值，仅做 tie-break
// tuning: continuityBonus 0.05 → 0.02
if (attack.stateName === this.#lastCommittedState && adaptation.consecutiveFail < 2) {
    score += this.tuning.attack.continuityBonus;
}
```

**只有 tuning 值改**，代码逻辑不变。

---

## Step 5: Random 降级为 tie-break（tuning 调整）

### 当前

```javascript
reactionVariance: 0.15  // 固定 ±7.5% 乘性扰动
```

### 改后

```javascript
reactionVariance: 0.05  // ±2.5%，只在分数差很小时有影响
```

**只有 tuning 值改**。

## Step 6: #computeStartupFactor 数据源修复（顺手修）

### 当前（不一致）

```javascript
// L383 — 仍然用 displacement
const fwdBoost = (attack.displacement ?? 0) < 0 ? -attack.displacement : 0;
```

### 改后（和 #scoreAttack 对齐）

```javascript
const effectiveDisp = attack.activeDisplacement ?? attack.displacement ?? 0;
const fwdBoost = effectiveDisp < 0 ? -effectiveDisp : 0;
```
dash 当前两者恰好相同不会出错，但其他攻击 future 如果加了 activeDisplacement 就会不一致。

## Step 7: Tuning 参数总览（Data/AITuning.js）

### 新增参数

```javascript
attack: {
    // ... 保留现有参数

    // === Repetition Cost ===
    repetitionCostRate: 0.06,      // 每次连续使用的成本增长（每轮 × count-1）
    repetitionCostMax: 0.18,       // 单次累计成本上限（防止盖过一切）
    successMaxCount: 3,            // feedbackSuccessBonus 封顶次数（短期记忆）
},
```

### 修改值

```javascript
// 原 → 新
continuityBonus: 0.05 → 0.02    // 降级为弱 tie-break
reactionVariance: 0.15 → 0.05   // 降级为 tie-break
```
### 四档 profile 如何从 repetitionCostRate 派生（未来扩展）

| Profile | repetitionCostRate | repetitionCostMax | 说明 |
|---|---|---|---|
| tutorial | 0.02 | 0.06 | 容忍重复，教学用 |
| normal | 0.06 | 0.18 | 本计划默认值 |
| elite | 0.10 | 0.30 | 更快打破惯性 |
| boss | 0.15 | 0.45 | 高适应，低重复容忍 |

**不是在本计划中实现四档**，而是为未来扩展预设计好参数入口。Phase 1-5 稳定后再评估是否需要角色级 override。

## 验证清单

1. **Ctrl+Shift+R 硬刷新**（AITuning.js 浏览器缓存是已知坑）
2. Console 看 `[dbg-ai] KB attacks:` —— dash effR 应在 2.77 左右（已被上一轮修复）
3. 连续让 AI 命中同一招 3 次以上，观察：
   - 第 1-2 次：AI 继续该招（合理）
   - 第 3-4 次：分数被 Repetition Cost 拉低，其他招开始有机会
   - 分数差距大时：继续原招（强招应该持续赢）
4. 非 attack 动作（dodge/guard/positioning）打断后，下次 attack 的 repetition count 从 1 重新开始
5. 切换角色后 repetition cost 应独立计算（如果 AI 有多个敌人类型）
