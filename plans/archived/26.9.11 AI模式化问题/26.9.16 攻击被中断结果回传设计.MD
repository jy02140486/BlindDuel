# 攻击被中断 Outcome 回传设计

## 1. 问题陈述

AI committed attack 在 **startup 阶段**（weaponbox 未激活、尚未产生任何 contact）被对手 hit 打断时，**没有 outcome 回传给攻击者的 controller**。

**现象**：AI swing 被玩家 hit 打断 → memory 里没有这条 outcome → `#computeAdaptationFactor` 读不到失败记录 → AI 以为"没发生" → 继续 swing。

**日志证据**（handoff 里已贴）：

```
[attack] swing: base=0.400 success=0.000(n=0/3) fail=0.000 ...
```
## 2. 根因分析

### 2.1 时序链路

`BattleMode.fixedUpdate` 的执行顺序（`BattleMode.js:74-106`）：

```
帧 T:
  ① playerController.fixedUpdate()
  ② rabbleController.fixedUpdate()     → AI 决定 swing
  ③ character.fixedUpdate() × N        → AI 进入 swing，保存 _currentAttackInstanceId
     └─ CombatCharacter.js L491 miss 检测：oldAttackActive=true, newAttackActive=true → 不触发
  ④ combatSystem.fixedUpdate()         → 检测到玩家 hit → hit effect
     └─ A.takeDamage() → A.enterState("hit")   ← 状态在此被切换

帧 T+1:
  ⑤ character.fixedUpdate() 对 A:
     └─ oldState="hit", oldAttackActive=false → L491 条件永不满足 → miss 检测彻底错过
```
### 2.2 关键代码路径

miss 检测的唯一入口在 `CombatCharacter.js:491-496`：

```js
if (oldAttackActive && !newAttackActive && oldState !== newState) {
    // ...回传 miss...
}
```
但当 `CombatSystem.fixedUpdate` 在步骤 ④ 中调用 `A.takeDamage()` 直接触发 `enterState("hit")` 时，步骤 ③ 已经跑完了。下帧 ⑤ 读 oldState 已是 "hit"，oldAttackActive=false，检测条件永远不成立。

**结论**：状态转换（attack → hit）完全绕过了 miss 检测，且没有其他代码路径补上这个空缺。

## 3. 方案设计

### 3.1 Outcome 类型选择

**方案：新增 `"interrupted"` 类型，不归类为 `"miss"`。**

理由：
- `miss` 的语义是"攻击完成但没打中"，`interrupted` 是"攻击被对手动作打断"——两者语义不同
- AI 评分可以对 `interrupted` 应用与 `miss` 相同（或更重）的惩罚，但保留区分粒度对未来扩展有用（例如：被打断次数多了 AI 可能选择更短的招式）
- 在 `#FAIL_OUTCOMES` Set 里加一项即可，零额外成本

### 3.2 检测层选择

**方案：在 `CombatSystem.fixedUpdate` 的 hit effect 处理段（`CombatSystem.js:79-100`）中、`takeDamage()` 调用之前检测。**

理由：
- CombatSystem 同时看到 hit effect（知道攻击方向）和 target（知道 target 的当前状态）
- 改动集中在一处，不涉及多文件时序协调
- 此时 target 还没被打入 hit 状态，可以正确读到 attackActive 状态

### 3.3 TargetState 时序陷阱

**问题**：`#dispatchOutcomes` 在所有 effect 处理完毕后统一执行，此时 target 的 stateName 已被 `takeDamage()` 改成了 "hit"。

**解法**：在 outcomeMap entry 中**提前缓存** `targetState: target.currentStateName`（采集时 target 还是攻击状态），dispatch 时优先读 entry.targetState，而非实时读 `attackerChar.currentStateName`。

### 3.4 边界排除

通过 `CombatCharacter` 新增公开方法排除两类假阳性：

```js

    const id = this._currentAttackInstanceId;
    return !!(this._lastAttackHadHit || (id && this._resolvedAttackIds.has(id)));
}
```

## 4. 改动点明细

### 4.1 `CombatCharacter.js` — 新增公开方法

**位置**：`CombatCharacter.js:65`（`markAttackHit()` 之后）

```js
/** Feedback Memory: 当前攻击是否已有 resolved outcome（hit 或 CombatSystem 已回传） */
isCurrentAttackResolved() {
    const id = this._currentAttackInstanceId;
    return !!(this._lastAttackHadHit || (id && this._resolvedAttackIds.has(id)));
}
```
### 4.2 `CombatSystem.js` — hit effect 段新增 target 中断检测

**位置**：`CombatSystem.js:79-100`，hit effect 处理段

**现有代码**：

```js
if (effect.type === "hit") {
    // hitstop → 攻击者 hitstop → markAttackHit → takeDamage
    // 无 outcome 收集给 target（被击中者）
}
```
**新增逻辑**（在 takeDamage 之前、outcomeMap 已有内容时）：

1. target = 被击中角色
2. 如果 target.currentStateDef?.attackActive === true:
   3. 且 target.isCurrentAttackResolved() === false:
   4. 且 outcomeMap 中还没有 target.id 的条目（防止 clash/hit 双重覆盖）:
   5. outcomeMap.set(target.id, {
        outcome: "interrupted",
        attackInstanceId: target._currentAttackInstanceId,
        targetState: target.currentStateName,    // 缓存！此时还在 attack 状态
        counteredBy: effect.context.attackerId   // 打断者 = 本次 hit 的 attacker
      })
注意：`#collectOutcomeFromEffect` 现在只处理 hit/clash/defenseSuccess **对攻击者的正向 outcome**。中断检测是**反向**的——给 hit 的 target 收集一个 outcome。可以放在 hit effect 主循环里（不进 `#collectOutcomeFromEffect`），因为它需要额外读取 target 的 CombatCharacter 内部状态。

### 4.3 `CombatSystem.js` — #dispatchOutcomes 优先读 entry.targetState

**位置**：`CombatSystem.js:204-207`

**现有**：

```js
attackerChar.controller.onCombatResult({
    outcome,
    targetState: attackerChar.currentStateName,   // ← 读实时值，此时可能已是 "hit"
    counteredBy: defenderChar?.currentStateName ?? null
});
```
**改为**：

```js
attackerChar.controller.onCombatResult({
    outcome,
    targetState: entry.targetState ?? attackerChar.currentStateName,
    counteredBy: defenderChar?.currentStateName ?? null
});
```
### 4.4 `AIController.js` — FAIL_OUTCOMES 新增 "interrupted"

**位置**：`AIController.js:21`

**现有**：
```js
static #FAIL_OUTCOMES = new Set(["parried", "guard_blocked", "clash", "miss"]);
```

**改为**：
```js
static #FAIL_OUTCOMES = new Set(["parried", "guard_blocked", "clash", "miss", "interrupted"]);
```

### 4.5 下游消费分析（无需额外代码改动）

interrupted 经 `onCombatResult` 写入 `#memory.entries` 后，现有三条消费链路自动生效：

| 消费点 | 机制 | interrupted 行为 | 需要额外改动？ |
|--------|------|-----------------|---------------|
| **Adaptation failDelta** | `#FAIL_OUTCOMES.has(outcome)` → consecutiveFail++ | 自动半罚/满罚 | 否 |
| **Adaptation successDelta** | 只认 `outcome==="hit"` | 不污染 success 计数 | 否 |
| **Continuity** | `#lastCommittedState === stateName && consecutiveFail < 2` | 失败不覆盖 lastCommittedState，正确 | 否 |
| **Repetition Cost** | `#executeCommitted` 选非 attack 时 reset | 被 hit 后 AI 选 positioning/dodge 自动 reset | 否 |

**tuning 参考：第一次 interrupted 的近似抵消效应**

第一次 interrupted 时 `consecutiveFail=1`（半罚约 -0.05），而 continuity 条件 `consecutiveFail < 2` 仍成立 → continuityBonus（约 +0.05~+0.10）仍然加上。两者近似抵消，AI 被打断后**第一次不会强烈换招**。第二次起 consecutiveFail=2，continuity 门控失效，才满罚。这是合理的梯度，但如果实战观察到 AI 被打了还硬上同招，可以：
- 调大 `feedbackFailPenalty`（如 0.05→0.08）
- 或把 continuity 门控从 `consecutiveFail < 2` 改成 `< 1`（零失败才给惯性）

## 5. 测试验证

### 5.1 手动验证
启动本地服务器，进入战斗场景：
1. AI 出招（swing/thrust）→ 玩家在 startup 阶段 hit AI → 观察 AI 是否调整后续决策
2. 日志中应该出现 `[attack] swing: ... fail=1.000(n=1/...)` 这类有失败积累的输出
3. `_resolvedAttackIds` 应该包含被中断那次攻击的 instanceId

### 5.2 日志验证
在 dispatch 处加一条 debug log（前缀 `[dbg-interrupted]`）：

```js
console.log(`[dbg-interrupted] ${attackerChar.id} interrupted at state "${entry.targetState}" by ${counteredBy}`);
```
### 5.3 不回归测试
- AI 攻击成功命中 → 继续正常记录 success → 不受影响
- AI 攻击 miss（挥空）→ CombatCharacter.fixedUpdate L491 正常触发 → miss outcome → 不受影响
- AI 攻击被 guard_block → CombatSystem 正常产生 guard_blocked → 不受影响
- 双方同帧互相命中 → 双方各自有 hit outcome（给各自 attacker），不会被 interrupted 污染

## 6. 不在本次范围内

- 把 interrupted 的惩罚权重和 miss 区分开（当前 FAIL_OUTCOMES 里两者等价，后续 tuning 可以单独加 interruptedPenalty）
- 调整 BattleMode.fixedUpdate 的执行顺序（那样改动面太大，超出本次范围）

### Step 3: CombatSystem 主改动——hit effect 段新增 target 中断检测

**文件**：`scripts/Systems/CombatSystem.js`

**位置**：`fixedUpdate` 主循环内，`if (effect.type === "hit")` 分支内、`takeDamage()` 调用**之前**（约 L98-99 之间）

**操作**：在现有 hit effect 处理逻辑（hitstop → 攻击者 hitstop → markAttackHit）之后、`takeDamage()` 之前，追加：

```js
// Feedback Memory: 若被击中者当前在 committed attack → 产生 interrupted outcome
// 注意：此时 target 还没被打入 hit 状态，可正确读到 attackActive
if (target.currentStateDef?.attackActive === true
    && typeof target.isCurrentAttackResolved === "function"
    && !target.isCurrentAttackResolved()
    && !outcomeMap.has(target.id)) {
    outcomeMap.set(target.id, {
        outcome: "interrupted",
        attackInstanceId: target._currentAttackInstanceId,
        targetState: target.currentStateName,
        counteredBy: attackerId
    });
}
```

**验证**：hit effect 处理后、takeDamage 前打断检测触发。加一条临时 debug log 确认：`console.log("[dbg-step3] interrupted queued for", target.id)`。

### Step 5: 端到端验证

启动服务器，进入 prologue 战斗场景：

1. 让 AI 出招 → 玩家在 startup 阶段 hit AI → 观察 console 出现 `[dbg-step3] interrupted queued for ...`
2. 观察 `[attack] swing: ... fail=0.050(n=1/...)` 或类似带 fail 值的输出（之前 fail 恒为 0）
3. 连续打断 AI 同招两次 → fail 累积到 2 次满罚 + continuity 失效 → AI 应该换掉这招
4. 不回归：AI 正常命中 → 仍 success，miss → 仍 miss，guard_block → 仍 guard_blocked

---

**分步原因**：Step 1-2 是独立准备工作，Step 3 是核心检测逻辑，Step 4 是修正 dispatch 时序陷阱。Step 3 和 Step 4 必须成对生效——如果只做 Step 3 不做 Step 4，interrupted 的 targetState 会错误地是 "hit" 而非攻击状态名，Adaptation 调节器读 stateName 就会按 "hit" 去查历史（查不到），惩罚就白白浪费了。
