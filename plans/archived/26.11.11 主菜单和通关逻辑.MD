# 主菜单与通关逻辑计划（26.11.11）

## 一、背景与目标

当前游戏一启动直接进 prologue 场景，缺少：
1. 主菜单（新游戏 / 继续）
2. 最终战斗（`battle_tavern_night_manatarms`）胜利后的通关流程：结算 sequence → 推进 scenario → 通关画面 → 回主菜单

本计划新增一个 **GameFlowManager**（游戏流程管理器），作为 Mode 层之上的顶层流程状态机，同时顺带修正 `#checkBattleEnd` 中 scenario 推进时机偏早的问题。

## 二、方案选型：为什么不用 UE 式「专门 GameMode + 专门 Scene」

UE 的 GameMode/Level 对应到本项目，等价物分别是 **BattleDef/ExploreMode 体系** 和 **SceneDef/Scene**。评估结论：

- 现有 GameModeManager 是 **Scene-scoped** 的：每次 `Scene.init()` 重建并硬编码 `start("explore")`，Mode 持有的 sharedContext 全是场景级引用（entityPool / walkArea / actorRegistry）。它天生只服务「一个 gameplay 场景内部的模式切换」，不适合承载主菜单。
- 主菜单不需要实体/碰撞/AI，若做成一个 Scene，会为按钮界面加载全部图集资源，成本不成比例。

**结论**：主菜单走轻量路线（见 §四），顶层流程归新的 GameFlowManager 管。

## 三、GameFlowManager 的定位与分层

```
GameFlowManager（新增，Game-scoped，跨 Scene 存活）    ← 顶层游戏流程
  ├── menu    ：DOM 主菜单可见；可 gate 主循环（可选优化）
  ├── playing ：委托给下层 Mode 体系，自身不介入
  └── ending  ：通关画面 → 过渡回 menu
        │ 唯一交互点
GameModeManager（现有，Scene-scoped）                  ← 场景内玩法模式
  └── explore / battle
```

职责边界（三层划分）：
- **GameFlowManager**：管流程——状态流转 + UI 显隐 + 转场互斥，只调用 Game 的生命周期接口，**不直接触碰 currentMode / Scene / Mode 内部结构**。
- **Game**：管运行时生命周期，提供幂等的 `teardownGameplay()`（① 先 `currentMode.exit()` ② 清场景运行时资源与引用 ③ 不遗留相机状态/投掷物/输入 held 状态/session）及 `startNewGame() / continueGame() / leaveGameplay()` 等入口。
- **GameModeManager**：保持现状不动，只在 playing 态内部被触碰。

**收编旧债**：`Game.restoreCheckpoint` 里「显式调 `currentMode.exit()` 防止 BattleMode.exit 被跳过」的逻辑（注释详述相机残值 bug）收进 `teardownGameplay()`，restoreCheckpoint 与回主菜单共用。战败回 checkpoint 在语义上也是一次 playing 内部重置。

## 四、主菜单：DOM overlay

- 全屏 HTML overlay（黑底 + 标题 + 按钮列），纯 DOM 零 Babylon 资源，组织在 `scripts/UI/` 下，与 InventoryBar/HpBar 等 UI 组件同构。

### 4.1 按钮清单（暂定四项）

| 按钮 | 行为 | 备注与边界 |
|---|---|---|
| New Game | `resetWorldState()` + 加载 prologue 场景 | 无存档检查，直接覆盖（原型阶段） |
| Continue | `restoreCheckpoint()`（存档基建已完备复用） | 无存档时置灰（实现细节：`Game.hasCheckpoint()` 已有查询口） |
| How to Play | 弹出二级面板：操作说明（键位表/战斗规则摘要） | 静态内容，本期不挂交互式教学；关闭后回主菜单 |
| Credits | 弹出二级面板：制作名单 | 静态内容；通关画面若将来做 staff roll 可复用同一数据源 |

- 二级面板（How to Play / Credits）实现为同一个 overlay 容器的子视图切换，不新开流程状态——它们不改变 gameState，仍停在 `menu` 态。
- 通关后回主菜单，Continue 按钮的有无/置灰与 checkpoint 状态自然联动（见 §5.4 checkpoint 语义开放问题）。

### 4.2 显示与流转

- 启动流程调整：bootstrap 后先显示主菜单（`menu` 态），**真正延迟 `Game.init()`**——点按钮才做 Scene 加载，不是先加载再盖菜单。bootstrap 里的资源预加载与影子稳定对象（B1）保留（Scene-agnostic，无害）。`character_demo.js` 调用时序相应调整。
- menu 态下主循环可 gate 掉 Mode 层 fixedUpdate（性能优化，非正确性必需，画面被遮住）。
- 转场互斥：FlowManager 持 `transitioning` 标志，连续点 New Game/Continue、ending 完成重复回菜单等异步竞争一律早退。
- 音频的 AudioContext 解锁依赖首次 pointerdown/keydown（见 §八风险），菜单按钮点击天然满足该条件，顺带解决了音频解锁时序。
- 手柄菜单操作纳入基础范围：上下选择 / 确认 / 返回，复用 InputSystem 菜单映射，不引入 UI 框架。

### 4.3 输入隔离

- 菜单/通关 overlay 显示期间：gate Gameplay InputSystem，UI 按键事件阻止向下传播。
- 进游戏 / 回菜单两个方向都清空按键与手柄按钮 held 状态。
- 通关画面的「任意键继续」必须消费 fresh input edge——玩家打倒敌人后攻击键可能仍按着，不能立即关闭通关画面（需按键释放后重新按下）。
- 后备方案（本期不做）：若将来想要动态背景菜单，做一个无敌人的轻量 SceneDef（如 `mainmenu.json`）复用 Scene 链路，基建已备好。

## 五、通关逻辑

### 5.1 数据驱动入口

`BattleDef.onVictory` 新增 `ending` 块（仅最终战斗声明）：
- `scenario`：通关 milestone（独立于 checkpoint.scenario，天然区分「完成状态」与「恢复点」，不引入新概念）
- `text`：通关画面那行字
- `sequence`：ending sequence 文件 ID（Data/Sequences/ 下独立 JSON，BattleDef 只引用 ID 不内联分镜——与既有 Sequencer 剧情组织方式一致，避免 BattleDef 膨胀）

### 5.2 触发路径（BattleMode）

`#checkBattleEnd` 胜利分支增加判断：`onVictory.ending` 存在时**不走默认 exit 路径**，改为：
1. 首次检测到胜利立即置 `battleEndHandled`，保证幂等（现有 `sceneSequencer.isBusy()` 守卫只防 sequence 播放期重入，不覆盖 callback 之后的重复触发）。
2. 不立即推进 scenario（时序修正，见 5.3）。
3. **冻结战斗模拟而非整个 Scene 更新**：ending 期间跳过 AI 决策、战斗结算、投掷物更新（飞行中的冻结/清理），Sequencer、CameraManager、必要动画更新照常——停整个更新会导致 sequence 自己也播不了。复用既有 controlledBySequence / ScriptedCameraRig 机制，不另建 CutsceneMode。
4. 播 ending sequence（引用 §5.1 的 sequence ID，结构参考 `#handleDefeat`：inputLock → 收刀 → fade 黑屏 → callback）。
5. callback 通知 GameFlowManager：推进 scenario → 显示通关画面 → （fresh input）回主菜单。

### 5.3 时序修正（顺带修的现存问题）

当前 `#checkBattleEnd` 在播 exitSequence **之前**就 `advanceTo` → WorldState 通知 → 动态 spawn，镜头 blend 期间新 NPC 可能已刷出穿帮。ending 路径把 scenario 推进挪到 ending sequence 的 callback（黑屏之下），顺序自然正确。默认 exit 路径的同类问题本期不展开，仅记录。

### 5.4 通关画面与回主菜单

- 通关画面：黑底 + 一行字 DOM overlay（与主菜单共用 overlay 基建），出现时停 BGM。
- 回主菜单前必须执行 playing 清理（走 `Game.teardownGameplay()`，见 §三），防止 BattleMode 的 session/投掷物/相机上下文残留跨入下一局。
- **New Game 必须清旧 checkpoint**：`resetWorldState()` 同时清 `Game._checkpoint` 与 InventoryManager，避免「重置世界后 Continue 又载回旧进度」。
- **通关后 Continue 语义（定案：方案 A）**：恢复最终战斗前 checkpoint，可重打最终战。理由：当前 `_checkpoint` 是内存级（无 localStorage 持久化，页面刷新即失），方案 B（保存完整通关状态）依赖尚不存在的存档持久化，留作后续 SaveManager 工作（见 §八）。

## 六、边界纪律（防 GameFlowManager 膨胀）

1. **不进主循环**：无 fixedUpdate，纯事件驱动（按钮点击、BattleMode 回调），不碰 FrameClock。
2. **不持 Babylon/Scene 引用**：Scene dispose/重建对它透明——这正是它比 Mode 层高一层存在的意义。
3. **UI 外包**：FlowManager 只调 overlay 的 show()/hide()，DOM 结构与样式归 UI 组件。

## 七、实施步骤

1. `Game.teardownGameplay()` 统一清理（先抽 restoreCheckpoint 现有 Mode 清理逻辑，保证幂等）——后续步骤都依赖它
2. GameFlowManager 骨架 + 主菜单 overlay + 真延迟 init + 输入隔离 + 转场互斥
3. New Game / Continue 存档语义（含清旧 checkpoint）
4. Ending overlay（通关画面）
5. BattleMode ending 分支（battleEndHandled + 模拟冻结）+ `onVictory.ending` 声明 + ending sequence JSON
6. 通关提交与回主菜单全链路验证（完整生命周期跑通）

每步有可单独验证的结果。预估规模：一个新系统文件（百行级）+ 两个 UI overlay + Game/BattleMode 小改，不动 Mode/Scene 现有结构。

## 八、风险与开放问题

- **gate 主循环与 AudioContext 解锁**：menu 态下若 gate fixedUpdate，注意音频 resume 逻辑依赖的 pointerdown/keydown 监听不受影响。
- **回主菜单时的 WorldState 复位**：从菜单「新游戏」需保证 resetWorldState 后所有 flag/quest/sceneStates 干净（现有方法已覆盖，实现时验证 onVictory ending 的 scenario 推进不与 checkpoint 恢复打架）。
- **ending sequence 的相机归属**：黑屏后 ScriptedCameraRig/DuelCameraRig 残留是否需要复位，回菜单时 Babylon 相机静止即可，无需特殊处理，但需确认 fade 效果不被 mode.updateRender 的 context 覆写。
- **开放问题**：通关画面是否支持「制作人员名单」复用（本期不做，overlay 结构留扩展口）。
- **存档持久化（未来工作）**：当前 checkpoint 仅内存级，属已知限制；后续若做 SaveManager，需将 campaignCompleted 与 checkpoint 分开持久化，通关标记不得因异常退出丢失。

## 九、外评意见采纳记录（26.11.12）

**已采纳**：Game 生命周期接口分层（§三）、ending 冻结战斗模拟 + battleEndHandled 幂等（§5.2）、New Game 清旧 checkpoint + 通关后 Continue 方案 A（§5.4）、ending sequence 独立文件 ID（§5.1）、真延迟 init + 输入隔离 + 手柄菜单 + 转场互斥（§4.2/4.3）、实施顺序重排（§七）。

**未采纳/修正（评审方无代码视角产生的偏差）**：
- 「checkpoint 持久化、异常退出丢失通关进度」——当前 checkpoint 本就是内存级无持久化，该风险暂不存在，转为 §八未来工作项。
- 「bootstrap 提前创建 GameModeManager/AIController 是问题」——bootstrap 创建的是 B1 影子稳定对象，不接 Scene 无副作用；真正修复点是延迟 `Game.init()`，已按此表述。
- 「SaveManager 纳入 bootstrap 清单」——项目尚无该系统，不在本期范围。

## 十、落地记录（26.11.12）

步骤 1~5 全部完成，剩步骤 6 全链路回归。与计划的偏差与补充：

1. **初始场景修正**：`resetWorldState()` 原硬编码 prologue 与 WorldState 构造器（ep1_tavern_night）不一致，New Game 会进错场景——已对齐并常量化 `INITIAL_SCENE_ID`（BACKLOG 同步关闭）。
2. **ending 时序**：实际采用「退场序列（exitSequence）先播完，尾部 ending_hook callback（atMs=durationMs−100，避开完成判定同帧竞态）→ fetch ep1_ending.json → 黑屏淡出 → atMs 2500 callback 推进 scenario + saveCheckpoint + showEnding」。scenario 推进发生在黑屏稳定后，无穿帮。
3. **handler 机制**：JSON callback 用字符串 handler 名，`battle_on_ending_black` 注册进 `ctx.sequenceHandlers`（bootstrap 已有 Map）并在触发后一次性自删，防跨局死引用。
4. **通关回菜单升级为完整卸载**：`unloadScene()` = teardownGameplay + scene.dispose + 换新空壳 Scene + 清 sharedContext 场景级字段 + `_flowReady=false`（冷启动等效态，New Game/Continue 零特判）。原 `_suspendWorld` 冻结方案保留给 defeat/暂停等复用场景路径。教训入档：sharedContext 字段分三类，复用稳定对象（cameraBasePosition/cameraTarget 等 Scene.init 只读回的 Vector3）禁止清理（PROJECT_CONTEXT §6.21）。
5. **顺手修复**：CombatCharacter `_commitStaminaCost` guard/dodge 分支裸 `costs` ReferenceError（实战丢飞刀被闪开必炸，属 26.11.9 遗留 bug）；EndingOverlay 补 dispose（对齐 Scene.dispose 清理纪律，防 Game.dispose 后已武装监听 re-entry）。
6. **HUD 显隐临时方案**：GameFlowManager._setHudVisible 手搓 id 列表，待 BACKLOG「抽象 HUD 类」收编。
