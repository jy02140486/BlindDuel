## 0. 前序实现反思（为什么重来）

### 0.1 前序方案的 3 个根本缺陷

| # | 缺陷 | 表现 | 根因 |
|---|------|------|------|
| ① | **无条件触发** | 开阔地也会产生 pushback，远超预期 | 原 ImpactMovementResolver 把 momentum 当作 "永远有值" 的量注入，`totalAttackerRequested = 0 + momentumPushbackX` 在开阔地仍非零 → 每次 hit 都触发 |
| ② | **时机错** | attacker 反推在 hitstop **之前**瞬时写入 position | 原方案把 resolver 放在 hitstop 前执行，算完立刻写 position。正确时机应该是 **hitstop 解除的瞬间** |
| ③ | **触判不明确** | victim 距边界很远时也被当作 "接近版边" | 原方案没有显式门槛，用 `residual > 1e-6` 这种连续量隐式判断，边界紧了就会误触发 |

### 0.2 MomentumDisp 算不出来的时序问题

原方案设计 `getRemainingAttackMomentumDisplacement()` 从 `frameIndex + 1` 累加剩余帧。但 CombatCharacter.fixedUpdate（推进动画 + 消费 frameSpeeds）在 CombatSystem.fixedUpdate 之前执行，命中检测发生时短攻击（3 帧）已经在末帧了，剩余帧为空 → momentumDisp 恒为 0。即使改成扫全帧，数值量级（speed 1.4 m/s × 1/60s = 2.3cm）也太小，不是用户能直接观察到的量。

### 0.3 已清理的前序代码

- ImpactMovementResolver.js（整个文件）
- CombatCharacter.getRemainingAttackMomentumDisplacement()
- CombatCharacter._suppressFrameSpeeds 初始化
- CombatSystem hit handler 里所有 boundary + momentum pushback 块
- TimeControlComponent.hitstopSlipFrames / hitstopSlipPerFrame
- TimeControlSystem 里的 slip 消费逻辑 + SLIP TICK log

当前代码基线：**hit handler 已干净**，只有 hitstop 设置 + takeDamage + Feedback Memory。可以在干净的基线上重新迭代 pushback。

## 1. 核心设计（先对清楚再动代码）

### 1.1 Pushback 是什么

attacker 在命中 victim 后被**向后推离 victim**。这是一个**边界场景特有的效果**——表达 attacker 的前冲力量被墙 "反弹" 回来的物理感。

### 1.2 完整流程图

```
帧 N:
  ContactResolver.resolve() 判定 hit
  → 产出 effect { knockbackX, hitstopFrames }
  CombatSystem hit handler:
    1. 给双方 applyHitstop(hitstopFrames) → 动画冻结
    2. takeDamage(knockbackX) → 【注：这里也要确认时机，可能应该延后】

帧 N+1 ~ N+hitstopFrames-1:
  hitstop 期间 → 双方 position 都不动

帧 N+hitstopFrames:
  hitstop 解除
    → victim.position += victimKnockbackX（带边界 clamp）
    → attacker.position += attackerPushbackX（带边界 clamp）
    → 两边边界 clamp 兜底（BattleMode post-combat clamp 已有）
```

### 1.3 触判条件（必须同时满足）

只有以下条件全部满足时才产生 pushback：

1. victim 被推方向有边界（不是所有方向都有墙）
2. victim 到该边界的距离 < `PUSHBACK_TRIGGER_THRESHOLD`（一个 pushbox 宽度，后续可调）

**开阔地永不触发**——不管 attacker 冲得多猛、momentum 多大，只要 victim 没被墙挡，就没有 pushback。

### 1.4 不做的事（明确排除）

| 不做 | 原因 |
|------|------|
| clash/parry 延迟路径 pushback | clash 状态自身 frameSpeeds 已有后退；clash 远少于 hit；先聚焦 hit 路径 |
| attacker 自身贴墙也算触判 | 触判只看 victim 那一侧的边界——attacker 贴右墙打左侧 victim，victim 没被右墙挡 → 不触发 |
| 开阔地也推 attacker | 用户明确说不要；开阔地 momentum 量级也太小（cm 级）不可观察 |
| ImpactMovementResolver 架构 | 整套换掉，不再需要 |

## 2. 迭代路线（三轮）

### **第一轮：固定值 + 瞬时写入（当前正在做）**

**目标**：让 pushback 链路跑通可观察，先不管时机和触判

**做什么**：
- 在 CombatSystem hit handler 里，每次 hit 都给 attacker 瞬时写反推位移
- 方向：`-dir`（推离 victim）
- 固定值：`speed 4 m/s × duration 1.0s = 4.0 m` 总位移（足够大，一眼能看到）
- 暂不加边界 clamp
- 暂不加触判条件（每次 hit 都触发）

**验证**：
- [ ] Console 看到 `[Pushback v1]` log
- [ ] 左攻右时 attacker 被往左推（远离 victim）
- [ ] 右攻左时 attacker 被往右推（远离 victim）
- [ ] attacker 位移方向正确、量级明显（4m 足够从场地中央飞到边界）

### **第二轮：修正时机 + 加触判条件**

**前置**：第一轮链路确认可观察

**做什么**：
- 把 attacker 反推从 hit handler 瞬时写入 → 延后到 **hitstop 解除的瞬间**（需要找到一个 hook 点：TimeControlSystem.hitstopFrames 归零时的回调，或者在 CombatSystem.fixedUpdate 末尾统一处理上一帧结束 hitstop 的角色）
- 加触判条件：victim 被推方向的边界距离 < threshold 才触发 pushback
- 第一轮的固定值暂保留（时机对了先测体感）

**验证**：
- [ ] hitstop 期间双方都不动，hitstop 结束时 attacker 才反推（视觉正确）
- [ ] 开阔地命中：attacker 不反推（无 pushback）
- [ ] victim 贴左墙被往左推命中：attacker 反推
- [ ] attacker 贴右墙打左侧 victim：无 pushback（victim 不碰右墙）
- [ ] victim 贴墙但推离墙方向（不可能，clash/parry 才会）：无 pushback

### **第三轮：固定值 → 计算值**

**前置**：第二轮时机和触判都正确，体感可接受

**做什么**：
- 用计算值取代第一轮的固定 4.0m
- 计算逻辑待定（可能的方案：从 frameSpeeds 扫全帧取 maxSpeed × 某个时间常数；或者从 StateGraph impact 里读 pushbackDistance 配置）
- 方向 `-dir` 保留不变
- 边界 clamp 加入

**验证**：
- [ ] 重招（dash、zornhut）反推比轻招（thrust）远
- [ ] pushback 不会把 attacker 推出边界
- [ ] 连续命中同一 attacker 不出现累积偏移
