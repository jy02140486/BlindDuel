# 反击机制重构计划：`parryBonus` → `postDefenseCounter` Trait

> 关联 guideline：`plans/post_defense_advantage_guideline.md`
> 关联规范：`docs/战斗规则说明.MD` §八

---

## 一、目标与设计决策

### 1.1 目标

将当前状态图中隐式的 `parryBonus` tag 反击机制，重构为正式的 `characterTraits` 配置。使 LongSwordMan 和 RabbleStick **用同一套 trait 系统**获得防御后反击能力。

### 1.2 已确认的设计决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| Trait 架构 | 保留 `postDefenseMobility`，新增**并列**的 `postDefenseCounter` | 两者效果维度不同（移动 vs 出招），不应合并成万能容器 |
| Counter 效果范围 | 只影响**攻击动画速度**（`bonusTimeScale`），不影响移速 | 两个 trait 完全独立，各管各的 |
| 新反击状态名 | **Nachschlag**（LongSwordMan） | 独立于 zornhut 的新动画 |
| Rabble 的反击动画 | 本次只做 LongSwordMan，Rabble 等 Nachschlag 完成后再决定 | 降低单次改动范围 |
| AI 检测方式 | 从扫描 transition 条件改为查 `characterTraits` 配置 | 避免依赖 runtime tag 名的脆弱检测 |

### 1.3 不做什么

- 不重写 State Machine 或 CombatSystem 架构
- 不改变 parry / guard_block / clash 的结算逻辑
- 不同时重构 RabbleStick 的反击动画（留给后续任务）

## 二、当前现状

### 2.1 `parryBonus` 的三重效果

| # | 效果 | 消费者 | 位置 |
|---|---|---|---|
| ① | 移动速度加成 | `CharacterBase._collectSpeedModifiers` | `CharacterBase.js:443-444` |
| ② | 攻击动画加速（用状态的 `bonusTimeScale`） | `CombatCharacter._getStateTimeScale` | `CombatCharacter.js:89` |
| ③ | 状态转移资格（guard/clash → zornhut/quart） | State Graph transitions | `LongSwordMan.json:260,267,320,327` |

### 2.2 `parryBonus` 的来源

| 环节 | 位置 | 行为 |
|---|---|---|
| ContactResolver 产出 | `ContactResolver.js:121` | parry 成功后**无条件** push `parryBonus` effect，对所有角色无差别 |
| CombatSystem 处理 | `CombatSystem.js:28-35` | 无差别加 `parryBonus` timed tag（`bonusDurationFrames`） |

### 2.3 已有 Trait 系统（`postDefenseMobility`）

| 环节 | 位置 | 行为 |
|---|---|---|
| ContactResolver 产出 | `ContactResolver.js:120,127` | 所有 defense 结果都 push `defenseSuccess` event |
| CombatSystem 处理 | `CombatSystem.js:66-79` | 遍历 `characterTraits`，检查 triggers 匹配 → 触发 trait |
| RabbleStick 配置 | `RabbleStick.json:4-11` | 已有 `postDefenseMobility`（triggers: guard_block/parry/dodge, durationMs: 500, speedMultiplier: 1.5） |

### 2.4 已知问题：RabbleStick parry 时双重加成

ContactResolver parry 成功，**同时走两条路径**：

- 老路径（line 121）：无差别 push `parryBonus` effect → CombatSystem 加 `"parryBonus"` timed tag → `_collectSpeedModifiers` line 443 命中 → 1.3x
- 新路径（line 120/127）：push `defenseSuccess` → RabbleStick 的 `postDefenseMobility` trait 触发 → `"postDefenseMobilityActive"` pending tag → `_collectSpeedModifiers` line 448 命中 → 1.5x
- 最终 1.3 × 1.5 = **1.95x 双重加成**

根因是"两套并存"的过渡态，迁移完成后老路径删除，此 bug 自然消失（Step 5）。

## 三、目标架构

### 3.1 两个 Trait 的分工

```
postDefenseMobility（已有，不变）
  └─ 影响：角色移动速度
     ├─ durationMs
     ├─ speedMultiplier
     └─ triggers: ["guard_block", "parry", "dodge"]

postDefenseCounter（新增）
  └─ 影响：反击出招资格 + 攻击动画速度
     ├─ durationMs
     ├─ allowedCommands: ["nachschlag", "quart"]
     └─ triggers: ["guard_block", "parry"]   ← dodge 不触发 counter
```

### 3.2 `postDefenseCounter` Trait Schema

```json
"postDefenseCounter": {
  "enabled": true,
  "triggers": ["guard_block", "parry"],
  "durationMs": 500,
  "allowedCommands": ["nachschlag", "quart"]
}
```

字段说明：

| 字段 | 含义 | 谁消费 |
|---|---|---|
| `triggers` | 哪些 defense result 触发这个 counter | CombatSystem |
| `durationMs` | runtime tag 持续时间 | CombatSystem |
| `allowedCommands` | 角色有哪些反击 command | AI（AIKnowledgeRegistry/AIController） |

**注意**：
- `allowedCommands` 是给 AI 读的，State Graph **不直接查它**
- State Graph 只查统一的 runtime tag：`hasTag: "postDefenseCounterActive"`
- `triggers` 可以与 `postDefenseMobility` 不同（比如 dodge 不触发 counter 但触发 mobility）

### 3.3 完整数据流

```
Combat Event
  ↓
ContactResolver.resolve()
  ↓
  ├─ push defenseSuccess { source: "parry" | "guard_block" | "dodge" }
  ├─ (老路径，Step 5 删除) push parryBonus effect
  ├─ push clash effect
  └─ push hitstop / blockstun effects
  ↓
CombatSystem.fixedUpdate() — defenseSuccess 分支（line 66-79，需扩展）
  ↓
  遍历 characterTraits:
    ├─ postDefenseMobility → markPostDefenseMobilityPending(durationFrames)
    └─ postDefenseCounter  → addTimedTag("postDefenseCounterActive", durationFrames)
  ↓
State Graph Transition 评估
  hasTag: "postDefenseCounterActive" → 允许进入 Nachschlag（该状态自己定义 bonusTimeScale）
```





### 3.3 两个 Trait 的分工
postDefenseMobility（已有，不变） └─ 影响：角色移动速度 ├─ durationMs ├─ speedMultiplier └─ triggers: ["guard_block", "parry", "dodge"]

postDefenseCounter（新增） └─ 影响：反击出招资格 + 攻击动画速度 ├─ durationMs ├─ allowedCommands: ["nachschlag", "quart"] └─ triggers: ["guard_block", "parry"] ← 注意：dodge 不触发 counter

## 六、边界条件与注意事项

### 6.1 `chainBonus` 不受影响

`chainBonus` 是独立的连招系统机制，本次迁移只处理 `parryBonus`。Step 5 删除老路径时 **不要动 chainBonus** 的任何逻辑。

### 6.2 `markPostDefenseMobilityPending` 的 pending 机制

`postDefenseMobility` 使用的是 pending 机制（defenseSuccess → 转非 restricted 状态时才开始计时），这是因为 mobility buff 在防御状态里不该生效。`postDefenseCounter` 不同——它的 tag 在 defenseSuccess 后立即生效（500ms 窗口内随时可以按 command 反击），所以直接 `addTimedTag` 即可，不需要 pending。

### 6.3 `canParry` 的自动推导

`CombatCharacter.js:285`：

```javascript
canParry: box.type === "weaponbox" && this.currentStateDef?.guardType === "guard",
```

这个推导逻辑不在 trait 配置里——任何角色只要 guard 状态有 `guardType: "guard"` 就能触发 parry 判定。**这是正确的**：trait 决定"parry 后获得什么能力"，而不是"能不能 parry"。

### 6.4 旧的 `_moveSpeedBonus`

`CharacterBase.js` 里的 `this._moveSpeedBonus` 当前值是 1.3，来自某个 trait 或 tag 配置。Step 5 删除 parryBonus 路径后，如果没有其他地方使用它，可以考虑清理（但不是本次必须做的事）。
