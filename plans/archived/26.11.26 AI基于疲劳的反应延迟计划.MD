# 26.11.26 AI 基于疲劳的反应延迟计划

> 状态：**已完成关闭（2026-11-27）**。实现与计划的偏差、验收结果与已知问题见 §6~§8。

## 0. 定案摘要

- **方案**：最简延迟 commit（粗粒度威胁锁存）。不是窗口压缩，也不是完整方案 2（不要事件 ID / stateEntrySerial 数据通路）。
- **T_max 初值**：150ms，调参区间 [100, 200]。
- **投掷物 reactive dodge**：对齐玩家侧哲学——玩家疲劳从不拦截输入（staminaSlowdown / dodge 位移缩放都是执行层惩罚），AI 侧同样不做可行性门拦截，延迟到点后照常 commit，物理赶不上即自然失败。
- **实施第一步**：先做 active 阶段 guard 物理有效性实测（决定行为基线）。

## 1. 机制

```
F = 1 - staminaRatio
T_fatigue = maxReactionDelayMs × F^curvePower    // disabled 或满耐力 → 0
```

防御路径顺序（melee）：

```
guard suppression 过滤 → #scoreDefense → startup timing 门（现有 reflex 不动）
→ dodge i-frame 门 → 【fatigue pending 锁存】→ commit
```

pending 锁存规则：

- 候选通过全部门控后，若 T_fatigue > 0 且无 pending：记
  `pending = { readyAt: now + T_fatigue, action, threatState: opp.stateName }`，本 tick 不 commit。
- pending 存续期：评分照常运行（AI 继续出手/走位——涌现"明知该防但先挥了"的人类行为）；不重复锁存。
- 取消条件（唯一）：opp phase 离开 startup/active（威胁消失）。自身状态变化（被击中、进入攻击等）**不取消** pending——Controller 不预测 Character 能否接受动作，可执行性冲突由 Character 层在提交时自然拒绝。
- 等待期间其他 Action Commit 不受影响、不清除 pending（评分照常运行，AI 可照常出手/走位）。
- readyAt 到点：**提交一次并立即无条件清除 pending**——不论 Character 最终是否接受（状态冲突拒绝）、dodge 是否重过 i-frame 门，都不因提交失败而在后续 Tick 重复提交。到点时 opp 已进入 active 也照常提交（物理失效是预期行为）。
- 涌现行为：到期提交遇自身动作占用被 Character 拒绝时，该次防御即真正错过（"想起来防时手上招还没打完"），不重试。单字段 + 单一取消条件 + 一次性提交，无计时器生命周期管理。

## 2. 边界（吃/不吃延迟）

| 路径 | 处理 | 理由 |
|---|---|---|
| melee guard / dodge commit | 吃（pending 锁存） | 核心 目标 |
| reactive 投掷物 dodge | 吃（同一 latch，**不设可行性门**） | 对齐玩家"不拦截输入"哲学 |
| reactive 投掷物 cut | 不吃 | timingAlignment 是纯物理窗口，主动择机行为 |
| preemptive 投掷物 | 不吃 | 提前规划 ≠ 突发刺激反应 |
| positioning（posPlan / B5 preemptive） | 不吃 | 策略走位 ≠ 防御反应；职责二分：重刺加速管走位规避，疲劳延迟管防御响应 |
| escapeLatency（dodge i-frame 口径） | 不计入 T_fatigue | 允许"判断正确但执行不及时"的无效 dodge |
| cutReadyMs（throw 风险自评） | 不吃 | 否则 AI 把疲劳惩罚算进时机评估，违反约束 |
| scoring 层 | **不可见 T_fatigue** | 锁存实现于 commit 前，评分层天然看不到——满足"AI 不能用它计算行动时机" |

配置位置：`CombatTuning.stamina.fatigueReaction`（规则级机制，与 staminaSlowdown 同区，不放 AITuning）：

```javascript
fatigueReaction: {
    enabled: true,
    maxReactionDelayMs: 150,   // 调参区间 [100, 200]
    curvePower: 2.0,
}
```

个体差异（tutorial/boss）暂不做；确有需要时走 aiTuningOverrides 局部倍率。
命名用 fatigueReaction / maxReactionDelayMs——实现是真延迟锁存，语义准确，无混淆。

## 4. 验证矩阵

| 情境 | 期望 |
|---|---|
| 无疲劳、慢速攻击 | 正常提前防御（与现状一致） |
| 中度疲劳、慢速攻击 | 大部分正常防御，偶尔较晚 |

## 6. 落地记录与实现偏差（2026-11-27）

- Step 0 实测结论：**迟到 guard 物理有效（5/5）**——guard 防御盒第 0 帧生效、commit 与 block 同 tick 完成；quart active 窗口极长（normTime 0.60~0.93 均可挡）；疲劳（stamina 50~63）不削弱物理有效性。**行为基线 = "迟到的防御"**，T_max 目标 = "多数 guard 落在 active 窗口内仍有意义"。
- 偏差 1：延迟曲线由幂函数 `F^curvePower` 改为 sigmoid `delayMaxMs / (1 + e^((0.5-F)×steepness))`，配置键 `curvePower` → `steepness`（10）。满耐力 ≈1ms、半耐力 75ms、空耐力 ≈delayMaxMs。
- 偏差 2：键名 `maxReactionDelayMs` → `delayMaxMs`，初值 150 → **100**（实测调参）：100ms 决策 tick 的锁存扣减向上取整，150 档低耐力 sigmoid 值（>100）锁存 2 tick=200ms，叠加检测量化 1 tick 最坏 300ms 过慢；100 档低耐力恰 1 tick，总延迟最坏 200ms（原版最快档 + 一拍）。量化后曲线实际二值化：<50ms 不锁存（即时）、50~100ms 锁存 1 tick。
- 偏差 3：诊断日志为 `[AI-Diag] fatigueDefenseDelay`（mode/delayMs/stamina/oppState）+ `[AI-Diag] fatigueDefenseCommit`（kind），受 X 键 debug 门控（IS_RELEASE 构建下静音）。
- 锁存实现补充：`remainingMs -= decisionIntervalMs` 从首次检测 tick 起扣减不重置；attack/throw/positioning 候选提交时**取消 pending**（"防御可弃，攻击优先"——对计划"其他 Commit 不清 pending"的实现修正，实测按攻击优先执行）；其余规则与计划一致（不重复锁存 / 到点一次性提交不重试 / 唯一取消条件 opp phase 离开 startup/active）。

## 7. 验收结果（对照 §4 验证矩阵）

- 满耐力（stamina>60）：无 Delay 日志，行为与原版一致（开场即时格挡正常）✅
- sigmoid 精度：全部日志样本与理论值偏差 ≤2ms、单调 ✅
- 量化：中耐力（39~49）1 tick、低耐力（13~33）原 2 tick → delayMaxMs=100 调参后 1 tick ✅
- 延迟后防御物理有效：stamina=13 极限样本 quart light 仍 blocked=true ✅
- 疲劳代价可见：深疲劳段受击集中于 idle@0（锁存等待窗口挨打）+ 攻击态被 counter（attack 取消 pending 分支）✅
- Delay→Commit 配对 14/14 无孤儿 pending ✅；无"迎面走上前挨打"/positioning 回归 ✅

1. **重锁存循环**：到点提交被 `#executeCommitted` gate（dodge 冷却 / guard 压制）拒绝 → 下 tick 重新检测重新锁存，每轮多付一个决策 tick（100ms）。日志特征：同 delayMs 连续两组 Delay→Commit。根因与 26.11.9 gate 口径差同源（评分层不可见执行 gate 拒绝），按本计划"评分层不可见"边界故意不修。
2. **P1 hitDedupe 理论缺口**：同一攻击实例已产生 hit 后，迟到的 guard 仍可触发格挡（双重结算）。Step 0 实测未观察到样本，记观察项。

## 9. 实现升级定案：fixedUpdate 级 pending 提交 + 提交节流（2026-11-27 已实施并实测验证）

### 动机

偏差 2 的降参（150→100）本质是为适配量化而牺牲曲线：100ms 决策 tick 的锁存扣减把 sigmoid 值 ceil 成 tick 整数倍，行为面只剩 {0, 100} 两档。根因是**决策节流与提交耦合在同一 100ms 循环**——而提交本身很便宜（一次 gate 验证），贵的只是评分。

### 机制

```
fixedUpdate（每 ~16.67ms fixed tick）：pending 计时（clock.fixedTime 差值，hitstop 自动冻结）
  + 取消条件检查（opp phase 离开 startup/active，每 tick 查，更及时）
  + 到点提交一次并标 tried（不清除 pending）
决策 tick（每 100ms）：评分 + 产生新锁存候选
  - pending !tried → 拦截维持（不重复锁存）
  - pending tried → 允许新防御候选替换（新 readyAt + 重置 tried）
  - attack/throw/positioning 提交 → 取消 pending（不变）
```

**提交节流语义**：到点提交不论 Character 接受与否都标 tried，fixed 级不再重复发送；重试资格只能由下个决策 tick 的新评分授予。等价于把既成事实的「重锁存循环」规范化——行为基线不变，重试频率被封顶在每决策 tick 一轮（避免 fixed 级提交风暴），而计时精度从 100ms ceil 升到 ~16.67ms 分辨率。

**pending 生命周期保证**（防旧决定被顶掉 / 防防御雄痪，实施时按此为准）：

1. **无饿死路径**：`tried` 只可能在到点提交后为 true——替换的前提是旧的已至少尝试过一次提交。`!tried` 的 pending 跨决策 tick 不可被替换，每个锁存必定在 ≈readyAt 获得恰好一次提交机会。延迟 >100ms 时新决策照常被拦截（tick 100 检查 pending 仍在等待中 → 拦截维持），不会中途作废旧决定。
2. **提交被拒的重试节奏**（全额延迟，既定行为）：节奏公式 = `delayMs(新 sigmoid 值) + decisionIntervalMs(≤100)`。例：delayMs=130 → 0 锁存 / ≈133 提交被拒 / 200 决策 tick 重锁存 readyAt=330 / ≈333 二次提交——两次防御尝试间空窗 ≈200ms，期间评分照常（可打可走，attack 提交会主动取消 pending，不会被延迟卡死）。
3. **重锁存付全额新延迟为设计语义**（与现行 tick 级实现行为一致，非新引入）：疲劳时反复犹豫本就是惩罚的一部分；「扣除已等待时间」变体考虑过并否决——偏离行为基线混入实测变量 + 多一个计时字段不值。

### 影响

- sigmoid 值近似精确兑现（80ms 就是 ≈80ms），「越累越慢」曲线语义真正落地；
- **解锁 delayMaxMs 回 150**：ceil 到 2 tick 的惩罚消失，偏差 2 的降参理由不复存在——是否回调待实测手感再定，配置先不动；
- 日志形态：Delay→Commit 配对间隔从 tick 整数倍变为 ≈delayMs 真值；重锁存循环仍可识别（同 delayMs 多轮配对）；
- 改动面：仅 AIController（#pendingDefense 加 tried 标志 + fixedUpdate 一行接线 + #makeDecision 开头到点扣减逻辑迁出），CombatTuning 零变化；
- 文档联动：AI系统说明「量化行为」小节二值化描述随实施作废改写。
