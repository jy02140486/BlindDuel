# 防御缺口补完计划 — Clash Seeker 实现

> 背景：2026-10-22 诊断发现 Manatarms（被动 shield 角色）面对玩家 zornhut（heavy slash）时永远站着被砍。
> 根因分析见对话链；本文档为落地实施计划。

---

## 1. 问题根因

Manatarms 有 config 级 passive shield box，但战斗规则 shield 挡不住 heavy slash。
同时 Manatarms 没有原生 guard 状态——即没有「遇到 heavy slash 我该进什么状态」的逃生出口。

AI 决策链路三重门挡：

1. `#scoreAttack` Line 947：`distance > maxRange → return 0` —— 远距离所有攻击候选被距离硬门槛直接刷掉
2. `#scoreDefense` Line 1256：`timeUntilActive > decisionBuffer → return 0` —— 普通防御反应时序门挡
3. `#scoreDefense` Line 1301-1303：shield vs heavy slash → `blocked=false` → 被判为无效防御 → 扣 `badDefensePenalty`

结果：attack 全 0，guard 全负分，positioning 选 hold —— AI 只能站着被砍。

---

## 2. 设计目标

当盾牌角色（或侵略性角色）预测到对手攻击即将到来时，
利用自己较短的前摇主动出击，争取双方武器 clash，避免被打到 hitbox。

一句话定义：**主动出击的防御**（Offensive Defense）——用进攻动作实现防御目的，不是挡，是撞。

### 受益角色

| 角色 | 为什么需要 | 启用方式 |
|---|---|---|
| Manatarms | 被动盾挡不住 heavy slash，无原生 guard 状态 → 没别的出口 | 强制开（clashSeekerWeight=1.0） |
| 侵略性 RabbleStick | 有 guard 能挡，但表达个性选择主动出击 | aiProfile 设 clashSeekerWeight=1.2 |
| 消极 RabbleStick | 有 guard 能挡，个性消极 | clashSeekerWeight=0 → 完全不开 |
| LongSwordMan | 有 guard 能挡 | 默认 clashSeekerWeight=0（无额外收益） |

---

## 3. 实现位置

在 `#scoreAttack` 里增加一个独立分项 `clashSeekerBonus`，与 preemptive bonus / vulnReward 同级。
不是新 kind 不是新分支，就是同一 attack 候选的第 N 个打分项。

**为什么不做独立 kind？**
- 同一招（quart）普通 hit / preemptive hit / clash seeker 是同一个动作走同一个 transition
- 合并到同一个 attack 候选里，执行层零改动
- 避免 `{kind:"attack",action:"quart"}` 和 `{kind:"clash_seek",action:"quart"}` 两个相同动作竞争

---

## 4. Clash Seeker Bonus 资格条件（5 项）

### ① opp.phase === "startup"

对手必须正在起手——active/recovery 阶段不适用。

### ② opp 有明确 attack profile

`predictedOpponentEvents` 里能查到 `opp_attack_active_window`。

### ③ 时序可行（区间重叠检查，GPT 修正）

必须用**区间重叠**判断，不能只检查单端：

```
myActiveStart = myStartupMs
myActiveEnd   = myStartupMs + myActiveMs
oppActiveStart = oppTimeUntilActive
oppActiveEnd   = oppTimeUntilActive + oppActiveMs

overlapStart = max(myActiveStart, oppActiveStart)
overlapEnd   = min(myActiveEnd, oppActiveEnd)

if (overlapStart > overlapEnd) → return 0
```

双方 weaponbox active 窗口必须有重叠。
单端检查（原 `myActiveStart ≤ oppActiveEnd`）只能排除"我太慢"，
但不能排除"我早就结束你才开始"的情况。

**注意：这和 preemptive bonus 的时序检查语义不同。**
preemptive 关心"我能不能抢先打到 hitbox"——只需要 `myStartup < oppTimeUntilActive`（抢先起手）。
clash seeker 关心"双方武器能不能同时 active 并碰撞"——必须用 overlap。

### ④ 空间可行（关键！与普通 attack 不同门）

```
self.effectiveRange + opp.effectiveRange  ≥  sit.distance
```

普通 attack 的距离门是 `distance <= self.effectiveRange`（我的武器能够到对方 hitbox）。
clash seeker 的距离门是两把武器 reach 加起来能不能覆盖双方间距。

**为什么这能解决远距离问题？**

日志里 Manatarms quart effR=3.29，zornhut effR≈3.22，加起来=6.51。
distance=5.54 < 6.51 → 空间可行。
但普通 attack 门 5.54 > 3.29 → 距离硬失败。

### ⑤ aggressiveness knob > 0

```javascript
const clashSeekerWeight = this.tuning.aiProfile?.clashSeekerWeight ?? 0;
if (clashSeekerWeight <= 0) return 0;
```

Manatarms aiProfile 设 1.0，侵略性角色 1.2，消极角色 0。

## 5. 评分逻辑

### 5.1 基础结构

```javascript
// #scoreAttack 末尾，在 preemptive bonus 之后、rangeFactor 乘法之前
// 新增 clash seeker bonus 分项
if (oppAtkWindow && timing) {
    const clashSeekerWeight = this.tuning.aiProfile?.clashSeekerWeight ?? 0;
    if (clashSeekerWeight > 0) {
        const bonus = this.#computeClashSeekerBonus(
            attack, sit, oppAtkWindow, oppAtk
        );
        if (bonus > 0) {
            score += bonus * clashSeekerWeight;
            _breakdown.clashSeeker += bonus * clashSeekerWeight;
        }
    }
}
```

### 5.2 计算函数（GPT 修正版）

```javascript
#computeClashSeekerBonus(attack, sit, oppAtkWindow, oppAtk) {
    // --- 资格检查 ---
    if (sit.opp.phase !== "startup") return 0;

    const myStartupMs = attack.timing.startupMs ?? 0;
    const myActiveMs   = attack.timing.activeMs ?? 0;
    const oppTimeUntilActive = oppAtkWindow.startMs;
    const oppActiveMs = oppAtk.timing.activeMs ?? 0;

    // 时序：区间重叠（GPT 修正，原单端检查不够）
    const myActiveStart = myStartupMs;
    const myActiveEnd   = myStartupMs + myActiveMs;
    const oppActiveStart = oppTimeUntilActive;
    const oppActiveEnd   = oppTimeUntilActive + oppActiveMs;
    const overlapStart = Math.max(myActiveStart, oppActiveStart);
    const overlapEnd   = Math.min(myActiveEnd, oppActiveEnd);
    if (overlapStart > overlapEnd) return 0;  // 无重叠窗口

    // 空间：两把武器 reach 加起来够覆盖间距
    // ⚠️ GPT 修正: -activeDisplacement ?? 0 有 NaN bug
    //    一元负号优先级高于 ??，-undefined = NaN，NaN ?? 0 = NaN
    const disp = attack.activeDisplacement ?? 0;
    const myEffR = attack.range.maxReach + disp + this.rangeBuffer;
    const oppEffR = oppAtk.range?.maxReach ?? 0;
    if (myEffR + oppEffR < sit.distance) return 0;  // 空间不够

    // --- 评分 ---
    // ⚠️ GPT 修正: 第一版只加一个 baseBonus，不加 clashSeekMax 上限
    //    数学上 bonus 不可能超过 baseBonus=0.25（timingAlign≤1, urgencyMult≤1）
    //    上限等测试真的需要时再加
    let bonus = this.tuning.attack.clashSeeker?.baseBonus ?? 0.25;

    // 时序对齐：我 active 起点越接近对手 active 起点，bonus 越高
    const timingDiff = Math.abs(myActiveStart - oppTimeUntilActive);
    const timingAlign = Math.max(0.3, 1 - timingDiff / Math.max(1, oppTimeUntilActive));
    bonus *= timingAlign;

    // 威胁 urgency：对手攻击我能不能防住？
    // 防不住 → 必须 rush，urgency 高；防住 → 个性表达，urgency 低
    const selfGuardType = this.kbProfile?.guards?.[0]?.guardType ?? null;
    const interaction = ContactResolver.evaluateInteraction({
        offenseTrajectory: oppAtk.trajectory,
        offenseWeight: oppAtk.weight,
        defenseGuardType: selfGuardType,
        defenseIsDodging: false,
    });
    const urgencyMult = interaction.blocked ? 0.5 : 1.0;
    bonus *= urgencyMult;

    return bonus;
}
```

### 5.3 硬门槛绕过方案（GPT 修正 + 补充）

**问题：** `#scoreAttack` Line 948 `if (sit.distance > maxRange) return 0` 是硬门槛。
距离 5.54 > maxRange(4.28) → 直接 return 0，clash seeker bonus 加不到任何地方。

**GPT 修正方向：** clash seeker 合格的 attack 候选应该**不被 Line 948 硬门槛挡掉**。

**执行细节（GPT 未看到的完整代码结构补充）：**

#scoreAttack 函数末尾有 `return score * rangeFactor`。
如果 clash 合格但 distance > maxRange，rangeFactor=0，乘出来还是 0。
所以需要两处同时处理：

```javascript
// === 修改 1: Line 948 硬门槛，对 clash 合格候选放行 ===
if (sit.distance > maxRange) {
    const clashEligible = this.#checkClashSeekerEligible(attack, sit);
    if (!clashEligible) return 0;
    // clash 合格 → 继续往下走，rangeFactor 保持 0
} else {
    rangeFactor = 1.0;
    // ... 正常的 rangeFactor 衰减计算 ...
}

// === 修改 2: 函数末尾 return，clash 模式不乘 rangeFactor ===
// ... 所有评分项计算完毕 ...
if (clashEligible) {
    return score;                    // clash 模式：不受 rangeFactor 影响
}
return score * rangeFactor;          // 普通模式：距离衰减生效
```

**为什么要同时做这两处：**
- 只做 Line 948 放行：clash 合格候选继续往下走，但 rangeFactor=0，最终 return score * 0 = 0
- 只做末尾 return：硬门槛已经 return 0 了，根本走不到末尾

**minReach 门控不绕过：**
Line 936 `distance < minReach → return 0` 保持不变。贴脸时 weaponbox 全叠在一起，本来就会 clash。

### 5.4 和 preemptive bonus 的关系

两者独立分项、同时计算。
- preemptive：关注「我能不能抢先打到 hitbox」（单端时序检查：`myStartup < oppTimeUntilActive`）
- clash seeker：关注「双方 weaponbox 能不能同时 active 并碰撞」（overlap 区间检查）

执行时都是同一个 action 走同一个 transition。
最终 clash 是否成功由战斗系统实际判定（Phase 1 weapon-vs-weapon 相交 → 拼刀）。

## 6. Tuning 配置

### 6.1 系统级默认（AITuning）

**GPT 修正：** 不平铺到 attack 对象下，而是用子组保持结构清晰。
第一版只加 baseBonus，不加 clashSeekMax（数学上不需要，见 §5.2 注释）。

```javascript
// AITuning.js attack 对象内新增：
attack: {
    // ... 现有字段保持不变 ...

    // === Clash Seeker：主动寻求武器碰撞 ===
    clashSeeker: {
        baseBonus: 0.25,
    },
},

// 读取方式：
const baseBonus = this.tuning.attack.clashSeeker?.baseBonus ?? 0.25;
```

**为什么不用 attack.baseWeight？**
- attack.baseWeight 表达整体进攻倾向（无条件基础分）
- clashSeeker.baseBonus 表达特定战术机会（opp.startup + overlap + reachSum 都成立才激活）
- 合并后无法表达"平时不积极但擅长 seek clash"的个性
- 两者触发条件和设计意图不同，应保持独立

## 8. 架构影响评估（GPT 修正后）

| 风险点 | 评估 | 处理 |
|---|---|---|
| 为 clash 而 clash 乱出招 | 可控 | 4 层 gate（overlap 时序 + reachSum 空间 + knob > 0 + urgencyMult），clash seeker 是 attack 分项不是强制候选 |
| 和 preemptive bonus 重复 | 有重叠但可区分 | preemptive 关注 hitbox 命中（单端时序），clash seeker 关注 weaponbox 碰撞（overlap 区间） |
| 执行层状态机冲突 | 无 | 决策层选 quart → enterState("quart") → 和普通 quart 走同一个 transition |
| 消极角色被意外干扰 | 不会 | clashSeekerWeight=0 完全不进分支 |
| 硬门槛绕过导致远距离乱放行 | 可控 | 只对 clash 合格候选放行（overlap + reachSumOk），且只有 knob > 0 的角色能合格。不合格的仍然被 Line 948 + Line 936 两道原门挡掉 |
| 绕过硬门槛后 rangeFactor=0 导致 score * rf = 0 | 已解决 | §5.3 函数末尾 return 改为 clash 模式直接 return score（不乘 rf），两处同时修改 |
| shield 挡不住 heavy slash 才需要这个——那普通角色为什么要有 | 为了个性表达 | 通过 aiProfile knob 控制；消极角色默认 0 |
| -activeDisplacement ?? 0 产生 NaN | 已修复 | 先判断 `const disp = attack.activeDisplacement ?? 0` 再加减，避免一元负号与 ?? 的优先级冲突 |

### 硬门槛绕过的安全性说明（GPT 强调）

普通攻击候选满足两个独立条件即可参与评分：
1. 普通距离条件：`distance <= maxRange`（Line 948 硬门槛）
2. 或 clash seeker 专用条件：overlapOk + reachSumOk + knob > 0

两种条件**互不干扰**。满足普通距离条件 → 正常 rangeFactor 衰减；
仅满足 clash 条件 → 用 clash 评分，跳过 rf 衰减。

这避免了"所有远距离攻击都被放行"，也避免了"合法的 clash 候选被提前排除"。
