## 1. 问题诊断历程

### 1.1 初始假设（错误）

最初认为是 `closestMinReach = 0`（smash.minReach 扫描为零）导致 positioning retreat 阈值退化为贴脸，hold 区间覆盖 `(0, maxEffReach]` 全程。

### 1.2 数据层根因（已修复）

`AIKnowledgeRegistry.#computeReach` 和 `#computeMinReach` 忽略了 weaponbox 的 `angle` 字段，把所有旋转后的 AABB 当成轴对齐矩形计算水平投影。Manatarms 所有攻击的 weaponbox 都是竖直或近竖直方向（angle ≈ 90° 或 -89°），导致用 `w/2` 计算水平半宽而非正确的 `|w/2·cosθ| + |h/2·sinθ|`。

修复：新增 `#boxHalfProjX(box)` 辅助函数，`#SCHEMA_VERSION` 5 → 6 强制缓存失效。

验证结果：
| Attack | v5 minR（错误） | v6 minR（修复后） | v5 maxR | v6 maxR |
|--------|---------------|-----------------|---------|---------|
| quart | 1.03 | **1.40** | 2.71 | 2.35 |
| reverse_quart | 1.09 | **0.90** | 2.69 | 2.88 |
| smash | 0.00 ❌ | **0.22** ✅ | 1.49 | 1.31 |

### 1.3 新发现：hold 全程赢与 closestMinReach 无关

数据层修对后，AI 仍然全程 hold 定住。通过 attackChain 诊断日志发现真正原因是**三层叠加**：

1. **资格门槛层面**：opp=none 时，positioning 三候选中只有 hold 有资格进入竞争池
   - approach 门槛：`distance > maxEffReach(3.52)` → 所有测试距离 (2.29~3.49) 都在范围内
   - retreat 门槛 A：`distance ≤ closestMinReach(0.22) + 0.3 = 0.52` → 太远，不满足
   - retreat 门槛 B：`oppThreat > normalThreat(0.6)` → opp=none 时 oppThreat=0，不满足
   - hold 门槛：`closestMinReach(0.22) < distance ≤ 3.52` → 所有距离都满足

2. **分数层面**：hold 是固定 0.15 且**不受 posture multiplier 调节**（设计上"hold 是基线"），而 attack 分数被 baseWeight(0.10) × posture attackMultiplier(0.60) 双重压制到 0.06~0.10。

3. **CombatPosture multiplier 钳制**：Manatarms baseAggression=0.25 导致 attackMultiplier 触底 MIN_ATTACK_MULT=0.60，advanceMultiplier 和 retreatMultiplier 也都被钳到下限 0.70。

**结论：closestMinReach 修复是必要的基础设施修正，但 hold 全程赢是 positioning 评分结构本身的问题——候选资格门槛设计 + hold 免乘 multiplier + 固定分数，三者共同导致。**

### 1.4 Step 2 首次实施失败复盘（2026-10-26 上午）

Step 1 + Step 2 按原计划实施后，Manatarms 在 opp=startup 场景下 clash seeker 完全失效，经诊断**根因不在距离模型设计，而在计划遗漏了两个绕过静态 hold 门槛的保底加分路径**：

**现象**：dist=4.16 时 `hold=0.080`，而静态 hold 条件本应不满足，holdScore 应为 0。

**根因定位**：

| 绕过路径 | 代码位置 | 逻辑 | 绕过方式 |
|----------|---------|------|----------|
| posPlan hold bonus | `#scorePositioning` line 2062-2066 | `holdScore += 0.08`（无条件加） | 静态 holdScore=0 时仍加 0.08 |
| throw_windup hold 保底 | `#scorePositioning` line 2015-2016 | `holdScore = Math.max(holdScore, 0.05)` | 静态 holdScore=0 时仍保底 0.05 |

**为什么旧代码没暴露**：旧 hold 上界 `maxEffReach(3.52)` 几乎覆盖所有战斗距离，那两个保底本来就是"额外叠加"。Step 2 把 hold 上界缩到 `idealEffReach×1.15(3.14)` 后，**3.14~4.16 区间出现了静态 hold 无资格但 posPlan 仍加 0.08 的漏洞**。

**为什么 clash seeker 被压制**：opp startup 时 approach 先被 `×0.1`（line 1993 suppression）再被 `×0.5`（line 2065 posPlan）= 总 `×0.05`，而 hold 凭 posPlan 的 0.08 赢过 approach 进而赢过 attack——clash seeker bonus 根本没机会加到 attack 上。

**修复方向**：两个保底加分都需加静态 hold 资格门控——**只有当 `holdScore > 0` 时才允许加保底分**。这不改变 posPlan 本体逻辑（events 驱动的阈值跨越计算不动），只是收紧消费端。

## 2. 设计原则

本次修正不往 AITuning 新增参数，优先减少固定常数的支配作用。

1. **数据层与决策层语义分离**：closestMinReach 只负责攻击的物理合法性（proximal gap），不再作为 positioning 的退距阈值。
2. **候选资格围绕"理想交战距离"**：positioning 的三个候选都应该在不同距离段有资格，而不是 hold 独占全程。
3. **hold 封顶 + 超时强制打破**：不做 smoothstep 曲线化（防御型角色需要区间内 hold 稳定压过 attack 基础分），改为 `holdScore = Math.min(0.15, 0.15 * attackMultiplier)` 封顶 attack 基础分，再用 `holdCommitStart` 超时强制打破 opp idle 僵局。
4. **不新增配置参数**：先用现有攻击射程推导理想交战距离，比例因子硬编码先跑通。
5. **职责收窄而非新增**：closestMinReach 的职责收窄为物理合法性，positioning 自己推导战术距离。

## 3. 距离模型重设计

### 3.1 新增：理想交战距离 idealEffReach

从攻击有效射程推导：

```
perAttackEffReach = attack.range.maxReach + (attack.activeDisplacement ?? 0 > 0 ? 0 : -attack.activeDisplacement)
```

**idealEffReach = median(perAttackEffReach)**

用中位数而非 max，因为 maxEffReach 是最远那招的极限，不是"多数攻击都舒服"的距离。

以 Manatarms v6 数据为例：
```
smash:         effR = 1.31 + 1.18 = 2.49
quart:         effR = 2.35 + 0.38 = 2.73
reverse_quart: effR = 2.88 + 0.44 = 3.32
median ≈ 2.73
```

### 3.2 closestMinReach 职责收窄

| 用途 | 保持/移除 | 说明 |
|------|----------|------|
| `#scoreAttack` 硬门控 `distance < minReach → return 0` | ✅ 保持 | 物理合法性 |
| Debug 可视化红圈 | ✅ 保持 | 真正的物理贴脸无效区 |
| positioning 退距阈值 | ❌ 移除 | 改为 idealEffReach × 比例推导 |

### 3.3 positioning 候选资格新门槛

| 候选 | 旧条件 | 新条件 | 意图 |
|------|--------|--------|------|
| approach | `dist > maxEffReach` | `dist > idealEffReach × 1.15` | 距离超过理想值 15% 才想靠近 |
| hold | `closestMinReach < dist ≤ maxEffReach` | `closestMinReach < dist ≤ idealEffReach × 1.15` | 舒适交战区间 |
| retreat | `dist ≤ closestMinReach + 0.3` 或 threat 高 | `dist ≤ idealEffReach × 0.4` **OR** threat 高 | 距离小于理想值 40% 就想退 |

**验证（Manatarms idealEffReach=2.73）**：

| 距离段 | 旧有资格候选 | 新有资格候选 |
|--------|-------------|-------------|
| 0~1.09 (近距) | hold + (贴脸才 retreat) | **hold + retreat** ✅ |
| 1.09~3.14 (舒适区) | hold | **hold** + (attack 竞争) ✅ |
| 3.14~3.52 (远距) | hold | **approach + hold** ✅ |

### 3.4 hold 分数封顶设计（v3 最终版）

**v1 尝试（已回退）**：`holdScore = 0.15 * smoothstep(|dist - idealEffReach|, 0, idealEffReach * 0.5)`

**回退原因**：防御型角色的 hold 不是"距离多近才想原地不动"，而是"在所有自己能打到 opponent 的距离内，保持防御姿态等待对手出招"。smoothstep 在区间左侧衰减过快（有效宽度 1.365 远小于 hold 区间左半侧 2.51），导致 dist=2.00 时 holdFactor=0.448 → holdScore=0.067 < attack 基础分 0.090 → AI 疯狂出招视防御型设定如无物。

**v3 最终版**：

```js
holdScore = Math.min(0.15, 0.15 * this.combatPosture.attackMultiplier);
```

| 角色 | attackMult | holdScore | attack 基础分 | 效果 |
|------|-----------|-----------|-------------|------|
| **Manatarms（防御型）** | **0.60** | **0.09** | ~0.09 | **= attack 基础分，jitter 后偶尔 attack 赢** ✅ |
| Rabble（标准） | 0.75 | 0.1125 | ~0.30 | attack 本来就稳赢，无影响 |
| 精英 aggressive | 1.10 | 0.15（封顶） | ~0.44 | 无影响 |

语义：**hold 意愿和攻击意愿正相关**——防御型不想打时也不想 hold 太死，攻击性想打时 hold 封顶 0.15 但 attack 本来就赢。

### 3.5 hold 超时强制打破机制

**问题**：防御型角色在 hold 区间内 holdScore=0.09 ≈ attack 基础分 0.09，jitter 能偶尔打破僵局，但 opp 长时间 idle（51s+）时 hold 胜率仍然偏高（0.059~0.061 vs attack 0.056，差距极微但方向稳定）。

**设计**：

```js
// 字段声明
#holdCommitStart;  // 首次连续 commit hold 的 timestamp（ms），非 hold commit 时重置

// constructor 初始化
this.#holdCommitStart = null;

// 最长 hold 时间计算
#getMaxHoldMs() {
    const attacks = this.kbProfile?.attacks || [];
    const totalAttackMs = attacks.reduce((sum, a) => sum + (a.timing?.totalMs ?? 0), 0);
    if (totalAttackMs === 0) return Infinity;
    const aggression = this.tuning.aiProfile?.baseAggression ?? 1.0;
    return totalAttackMs * (1 - aggression);
}
```

| aggression | maxHoldMs 语义 |
|-----------|---------------|
| 0（最保守） | totalAttackMs（等完所有攻击动画） |
| 0.25（Manatarms） | totalAttackMs × 0.75 ≈ 1500ms |
| 1（最侵略） | 0（立即过期，不阻碍其他行动） |

**触发**：连续 hold commit 时 `holdCommitStart` 首次赋值；非 hold commit（approach/retreat/attack/defense/throw）时重置。下次 positioning 评分时，若 `now - holdCommitStart > maxHoldMs`，holdScore 强制归零。

**Manatarms 效果**：dist=2.99，opp idle → 前 1.5s hold 赢 → 超时后 holdScore=0 → attack:quart(0.056) 或 approach 赢 → commit → holdCommitStart 重置。

## 9. 本轮实施踩坑记录

### 9.1 smoothstep 曲线化回退

**尝试**：`holdScore = 0.15 * (1 - smoothstep(|dist - ideal|, 0, ideal * 0.5))`

**问题**：
1. 有效曲线宽度 `idealEffReach × 0.5 = 1.365` 远小于 hold 区间左半侧（ideal - closestMinReach ≈ 2.51）
2. dist=2.00 时 holdFactor=0.448 → holdScore=0.067 < attack 基础分 0.090 → AI 疯狂出招
3. dist=3.00 时 hold 勉强赢 attack（差距 0.028），opp idle 就能无限僵持

**回退决策**：防御型角色的 hold 语义是"在自己能打到 opponent 的区间内，保持防御姿态等待对手出招"，需要在区间内稳定压过 attack 基础分。放弃 smoothstep。

### 9.2 hold 封顶设计演进

| 版本 | 公式 | 问题 |
|------|------|------|
| v1 smoothstep | `0.15 * (1 - smoothstep(...))` | 曲线衰减过快，防御型在舒适区也 hold 不住 |
| v2 比例缩放 | `Math.min(0.15, 0.15 * attackMultiplier)` | 语义正确但 0.09 ≈ 0.09，长时间 opp idle 仍会僵持 |
| **v3 封顶 + 超时** | `Math.min(0.15, 0.15 * attackMultiplier)` + holdCommitStart 超时 | **区间内 hold 稳定，超时后强制打破** ✅ |

### 9.3 #getMaxHoldMs 重复方法语法错误

**错误**：旧版 `#getMaxHoldMs()`（用 `tuning.hold.maxHoldMs`）残留，新版又加了一个，JS 报错：
SyntaxError: getter and setter for private method #getMaxHoldMs should either be both static or non-static
**修复**：删除旧版定义，只保留新版。
