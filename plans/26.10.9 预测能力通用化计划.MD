## §1 为什么要通用化

### 已完成了什么

`26.10.7` 计划实现了一条**硬编码的 throw 预测路径**：

```
throw_windup（已知 stateName）
  → throwRemainingMs + distance/speed × 1000
  → predictedTTI
  → 复用 #scoreCutForProjectile
```

这条路径**只认识 throw_windup 一个 state**，对普通攻击（swing/thrust/dash）视而不见。

### 想让 AI 做到什么

| 行为 | 现状 | 需要 |
|------|------|------|
| opp 出 swing（startup 长 500ms） | AI 只看到 oppPhase=startup，不知道是 swing | 能识别 stateName，知道 startupMs=500 |
| opp 出 thrust（startup 短 250ms） | AI 同上，无法区分 | 能识别 stateName，知道 startupMs=250 |
| opp 抬手扔 dagger（远距离） | ✅ 已能 preemptive cut | — |
| opp 抬手扔 dagger（近距离 reach 内） | ❌ AI 只会等 projectile 出来斩（物理上赶不上）| 能在 windup 期间直接打 opp 打断投掷 |
| opp 出重击、AI 在攻击 reach 内 | ❌ AI 看不到"我可以抢先截断"这个机会 | 对比 own startupMs vs opp startupMs，判断能不能抢先 |

### 架构差距

现有代码**没有通用的"opp 当前在出什么招"感知层**。`Situation` 里只有 oppPhase（startup/active/recovery），没有 stateName / attackProfile。预测逻辑也硬编码在 `#buildSituation` 的 throw_windup 分支里。

统一预测层要解决两个问题：
1. **识别**：opp 当前 committed 的 state 是什么（stateName + attackProfile 属性）
2. **外推**：这个 state 会在多少 ms 后发生什么事件（active window、release 等）

**关键设计原则**：prediction layer 只产出纯时间线数据，不做战术判断。`threatLevel`、`canPreempt` 等取决于当前距离、自身动作选择、战斗规则——这些由评分函数算，events 层不越权。

## §2 架构认知

### 预测链四步

```
① Identify          ② Predict Events          ③ Classify            ④ Feed Utility
Opponent Action   → Future Event Timeline   → Threat / Chance   → Score Counter
(opp committed    → (state enter/exit,      → (这个事件是威胁    → #scoreAttack
 stateName +      →  projectile release,   →  还是机会)         → #scoreDefense
 attackProfile)   →  impact, recover end)                      → #scorePositioning
```

现有 throw preemptive cut **手工拼了 ①→②→③**，然后直接调了评分函数。通用化要把这四步变成一个**可扩展的管线**，且 ② 保持中立，③ 由评分层承担。

### 统一预测层：predictedOpponentEvents[]

引入一个中间层，**subsume 现有 throw preemptive 代码路径**（不是并行）。

谁生产：`#buildSituation` 内部新建 `#buildPredictedOpponentEvents()`，根据 opp 当前 committed state + attackProfile 生成

谁消费：Utility 层的 `#scoreAttack` / `#scoreDefense` / `#scorePositioning` / `#evaluateProjectileDefense` 全部从 events 读预测信息，而不是从零散的 Situation 字段

### 数据结构（纯时间线，中立）

```
predictedOpponentEvents[]:  有序数组，按 startMs 升序
  eventType: enum
    "opp_attack_active_window"            // 普通攻击 weaponbox 激活窗口
    "opp_throw_release"                   // 投掷物 release 时刻
    "opp_projectile_arrival_estimate"     // 投掷物预计到达当前距离目标的时刻（简化物理假设）
    // （第一版只产这三种，够了）

  startMs: number        // 距现在多少 ms 开始发生
  endMs: number          // 距现在多少 ms 结束（瞬时事件 startMs === endMs）
  sourceState: string    // 来源 stateName（如 "swing"、"throw_dagger"）

  properties: {          // 原始 attackProfile 字段，评分层按需取用
    startupMs: number,
    activeDurationMs: number,
    recoveryMs: number,
    reach: number,
    // projectile 事件额外：
    projectileType: string,
    cuttable: boolean,
    speed: number,
  }
```

**统一时间基准**：所有事件时间一律表示"从当前决策时刻起，距事件发生还剩多少 ms"。换算：`remainingStartupMs = startupMs - (oppNormTime * totalMs)`，每帧重读 oppNormTime 保证时序最新。优先复用 AIKnowledgeRegistry 已缓存的 timing。

**为什么用数组**：opp 一个 state 可能产出多个事件链（如 throw_dagger → release → projectile_arrival_estimate 两个事件），数组天然支持。上限 5 个 + startMs 超过 2000ms 丢弃。

### Step 4：B4 — 近距离 reach 内打断 throw ✅ 意外实现

> 原本计划在此处显式加 throw interrupt bonus（查 `opp_throw_release` 时间，我的 startup < release → 加分）。
> **实际测试发现：intentWeights 基础设施 + common baseWeight 已经自然实现了这个行为：**
> - `preemptive_only` 模式下 commonW 在 opp.commitied state（含 throw_windup）时 = 1.0
> - common 基分（0.4）> hold（0.15）→ AI commit attack
> - opp 刚好在抬手 → AI 攻击 hitstun 打断投掷
>
> 效果等同显式 interrupt bonus，但评分理由是"opp 有 committed state，正常攻击"而非"主动去打断 throw"。
> 如果后续需要**精准时序控制**（opp 抬手但赶不上 release 时不误 commit），再加显式 `opp_throw_release` 判断。
> 当前跳过，先观察 normal 模式下自然行为。

**目标**：opp 在 attack reach 内抬手扔 projectile → AI 抢先打 opp（hitstun 打断投掷）

**时间条件（修正版）**：
```
从 events 找 opp_throw_release 事件 → 得到 T_release
对每个候选攻击：
  T_my_active = own 剩余 startupMs
  if T_my_active < T_release          // 我的攻击先激活（hitstun 作用于 opp）
     AND distance ≤ own.maxReach       // 够得着 opp
     AND opp throw 状态可被 hitstun 打断
     → preemptive interrupt bonus
```

> 修正说明：原计划用 `throwReleaseMs ≤ ownStartupMs` 判断，方向反了。正确原则是我的攻击先于 release 激活。这里用 active 起点近似 hitstun 生效时刻（与现有战斗系统精度一致）。

**验收**：
- 近距离 reach 内 + 时间充足 → AI 抢先 swing opp 打断投掷
- 近距离 + 时间不足 → AI 不误判赶得上
- 远距离 → 走原有 preemptive cut / reactive 路径

## §4 Post-Phase 5 — B5：预测驱动的 positioning

### §4.0 背景：为什么现在做

原来 Post-Phase 5 下只有一句话 backlog——"先让 prediction 对 attack/defense 有明确收益，再单独迭代 positioning"。

**前置条件现在满足了**：
- `#scoreAttack` 完全从 events 读时序（PREEMPTIVE bonus 用 `opp_attack_active_window.startMs`）
- `#scoreDefense` 读 events 区分 opp trajectory
- `#evaluateProjectileDefense` 全迁移到 events 消费

Positioning 是唯一一个还在用"静态阈值 + events 抑制"思维的评分函数——还没真正消费 events 做决策。

---

### §4.1 核心约束：moveSpeed = 0.4 m/s

**所有可行性计算必须用真实数值**（CharacterFactory.js `DEFAULT_CHARACTER_OPTIONS.moveSpeed = 0.4`，缓存于 AIKnowledgeRegistry `kbProfile.movement.moveSpeed`）。

```
opp startup 典型窗口：300-500ms
AI 在窗口内可移动距离：0.4 m/s × 0.4s ≈ 0.15m（15cm）
```

**可行性边界**：
| 行为 | 是否可行 | 原因 |
|------|---------|------|
| opp reach 边缘（3.4-3.6m）退到 reach 外 | ✅ | 15cm 足够跨过阈值 |
| PREEMPTIVE 边缘（2.9-3.1m）压进 effectiveRange | ✅ | 15cm 足够跨过阈值 |
| 从 3.5m 压到 3.0m | ❌ | 1250ms，远超任何 startup 窗口 |
| 从 3.8m 退到 4.0m | ❌ | 500ms，只有最长 startup 窗口勉强够 |

**moveIntent 只有方向**（-1/0/1），无精确距离控制。Positioning 每帧重评，本质是方向控制系统。

---

### §4.2 当前 positioning 的问题（AIController.js #scorePositioning）

```javascript
// 现有逻辑（简化）
if (distance > maxEffReach) {
    approachScore = 0.35 × distanceHunger;  // 静态 smoothstep
}

// events 消费 = 条件抑制（打折扣）
if (opp.phase === "throw_windup" && hasCuttableThrow) {
    approachScore *= 0.1;   // 不前进，但不是主动找位置
}
if (opp.phase === "startup" && hasActiveWindowEvent) {
    approachScore *= 0.1;   // 不前进，但不是主动找位置
}
```

**问题**：
1. events 只做"不敢动"的抑制，不是主动规划——AI 不知道自己为什么安全
2. opp reach 边缘没有主动避弹逻辑（approach 被抑制了，但没退）
3. PREEMPTIVE / cut 边缘没有主动压线逻辑（要么触发，要么不触发）
4. 大范围 reposition 不可能，但小范围阈值跨越（15cm 内）完全可做

---

### §4.3 设计目标：events 不主导 positioning，只微调评分

**退化原则（零回归）**：
- **无 events 时** → 完全退化到现有 `distanceHunger` + 静态阈值逻辑
- **events 只做"评分加成/折扣"**，不做强制的门控或硬切换
- **不引入新候选**（仍然是 approach / hold / retreat 三候选）
- **不引入精确位置目标**（moveIntent 只有方向，维持方向控制系统）

**events 介入的三个场景**：

| 场景 | 现状 | 改进后 | 物理前提 |
|------|------|--------|----------|
| opp reach 边缘（AI 距 opp 0~0.2m 在 oppReach 内） | approach 被抑制 → hold，但没退 | events 算 "退 15cm 就安全，赶得上" → retreat 加分 | 15cm ≤ 可移动上限 |
| PREEMPTIVE / cut 边缘（AI 距 effectiveRange 差 ≤0.2m） | 要么触发，要么不触发 | events 算 "压进 range 需要 X ms，opp 还有 Y ms" → approach 加分 | X ms ≤ opp startup |
| 知道自己 PREEMPTIVE 不了（距离差 0.5m+） | approach 被抑制 → hold，不知道为什么 hold | events 算 "差 1.2m，2500ms，彻底赶不上" → 明确 hold（等 opp active 结束）或转防御 | 不涉及移动，纯评分 |

---

### §4.4 分两步实施

#### Step 1：positioningPlan — 纯数据层，只观测不消费

**目标**：新增 `#buildPositioningPlan(sit)` 方法，遍历 `predictedOpponentEvents[]`，对每个事件计算阈值跨越可行性，只写日志，不动任何评分函数。

**计算逻辑**（伪代码）：
```
for each event in sit.predictedOpponentEvents:
  moveLimit = kbProfile.movement.moveSpeed × event.startMs / 1000  // 窗口内可移动距离
  
  if event.eventType === "opp_attack_active_window":
    oppReach = event.properties.reach
    oppReachSafetyBuffer = 0.15  // 留 15cm 余量
    
    // 场景 A：我在 opp reach 边缘内，退到 reach 外
    distToEscape = distance - (oppReach + oppReachSafetyBuffer)
    if 0 < distToEscape ≤ moveLimit:
      → retreat = VIABLE（能退到安全）
    
    // 场景 B：我在 PREEMPTIVE range 边缘外，压进去
    distToPreemptive = selfEffectiveRange - distance
    if 0 < distToPreemptive ≤ moveLimit:
      → approach = VIABLE（能压进 PREEMPTIVE range）
    
    // 场景 C：两个都算过了，都不可行
    → hold = VIABLE（知道自己赶不上，不如 hold）
  
  if event.eventType === "opp_throw_release":
    // 类似逻辑：计算 cuttable projectile 的 cut 窗口阈值
    // 场景 A：projectile 飞行到 cutRange 需要 X ms，我能不能先压进去
    // 场景 B：cut 不了，release 后 reactive 接管，现在 hold
```

**日志格式**：
```
[AI-Diag] positioningPlan: moveSpeed=0.40 窗口可移=0.15m
  opp_attack_active_window(startMs=380ms, oppReach=3.5m)
    dist=3.45m oppReach内0.05m: 退出需要0.10m/250ms≤380 ✅retreat
    PREEMPTIVE差0.55m: 压进需要1.37m/3430ms>380 ❌approach
    → 推荐hold(0.55) vs retreat(0.45)
```

**验收**：
- 跑 `preemptive_only` 模式 opp startup 场景，日志输出 `retreat=VIABLE` 当 AI 在 opp reach 边缘内
- 跑 normal 模式，日志输出数值计算符合直觉（比如 moveSpeed×startMs 确实是 0.15m 左右）
- 无 events 时无 positioningPlan 日志（退化到现有逻辑，零回归）

#### Step 2：positioningPlan 接入 #scorePositioning

**目标**：Step 1 日志验证通过后，把 positioningPlan 的推荐结果映射到 approach/hold/retreat 三候选的评分加成。

**映射规则**（暂定，调参验证）：
```
// 现有静态阈值先算完
let approachScore = 0.35 × distanceHunger ...
let holdScore = 0.15 ...
let retreatScore = 0.5 ...

// positioningPlan 做加成（不覆盖静态阈值，只微调相对大小）
if (plan.recommend === "retreat") {
  retreatScore += 0.15;   // 边缘场景优先避弹
  holdScore -= 0.05;      // hold 在边缘场景不如主动退
} else if (plan.recommend === "approach") {
  approachScore += 0.12;  // 压线进 PREEMPTIVE range
} else if (plan.recommend === "hold") {
  holdScore += 0.08;      // 知道赶不上，hold 合理
  approachScore *= 0.5;   // approach 没用，压饿
}
```

**Step 2 验收**：
- opp reach 边缘场景：AI 主动 retreat（之前只会 hold）
- PREEMPTIVE 边缘场景：AI 主动 approach 压线（之前要么触发 PREEMPTIVE 要么 hold）
- 无 events 场景：AI 行为与 Step 1 完全一致（零回归）
- positioning 不会和 attack 竞争导致错误覆盖（check top3 里 attack 仍然能赢 positioning）

---

### §4.5 为什么不做更多

| 不做 | 理由 |
|------|------|
| 精确距离目标（desiredDistance） | moveIntent 只有方向，每帧重评自然形成稳态距离；引入距离目标会和 attack state 自带的 frameSpeeds 冲突 |
| 大范围 reposition 规划 | moveSpeed 0.4 m/s 下，任何需要 >200ms 的移动在 opp startup 窗口内都赶不上。Events 预测主要服务于阈值跨越 |
| throw_projectile 的 cut 窗口 positioning | reactive 路径（projectile 实际飞行中切）已经稳定。Preemptive cut 路径 events 消费已落地（`#evaluateProjectileDefense` 读 events），positioning 接入只是微调已有 approach/hold 偏好，收益低于 opp_attack_active_window |
| opp 远程攻击（远距离） | oppThreat 衰减 + defense 层已覆盖。Positioning 主要解决 AI 自己能做什么（前进/后退），远程防御是 guard/dodge 的事 |

### §4.6 与 B6 的关系

B6（predictionAccuracy 旋钮）可以在 B5 Step 2 之后接入——positioningPlan 里可以给 events.startMs 加 ±Xms 的随机偏移来模拟"迟钝 AI 算不准 timing"。但 B6 本身是 tuning 层改动，不阻塞 B5 Step 1。

## §6 依赖与风险

| 风险 | 缓解 |
|------|------|
| StateGraphDef 不一定暴露所有 attack state 的 timing 属性 | AIKnowledgeRegistry 扫描时已缓存 timing（Phase 4 做的），Step 1 直接复用 |
| 统一层搭建过程中现有 throw preemptive 行为退化 | Step 2 必须有回归验收（玩家扔 dagger → AI 行为不变） |
