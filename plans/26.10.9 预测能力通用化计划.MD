# AI 预测能力通用化计划（Phase 5）

> 目标：把 "识别 opp 动作 → 外推未来事件 → 喂给评分函数" 这条链从只覆盖 projectile，扩展到所有 opponent attack。最终让 AI 能区分 opp 出 swing 还是 thrust，据此决定抢先截断还是避让。

## §1 为什么要通用化

### 已完成了什么

`26.10.7` 计划实现了一条**硬编码的 throw 预测路径**：

```
throw_windup（已知 stateName）
  → throwRemainingMs + distance/speed × 1000
  → predictedTTI
  → 复用 #scoreCutForProjectile
```

这条路径**只认识 throw_windup 一个 state**，对普通攻击（swing/thrust/dash）视而不见。

### 想让 AI 做到什么

| 行为 | 现状 | 需要 |
|------|------|------|
| opp 出 swing（startup 长 500ms） | AI 只看到 oppPhase=startup，不知道是 swing | 能识别 stateName，知道 startupMs=500 |
| opp 出 thrust（startup 短 250ms） | AI 同上，无法区分 | 能识别 stateName，知道 startupMs=250 |
| opp 抬手扔 dagger（远距离） | ✅ 已能 preemptive cut | — |
| opp 抬手扔 dagger（近距离 reach 内） | ❌ AI 只会等 projectile 出来斩（物理上赶不上）| 能在 windup 期间直接打 opp 打断投掷 |
| opp 出重击、AI 在攻击 reach 内 | ❌ AI 看不到"我可以抢先截断"这个机会 | 对比 own startupMs vs opp startupMs，判断能不能抢先 |

### 架构差距

现有代码**没有通用的"opp 当前在出什么招"感知层**。`Situation` 里只有 oppPhase（startup/active/recovery），没有 stateName / attackProfile。预测逻辑也硬编码在 `#buildSituation` 的 throw_windup 分支里。

统一预测层要解决两个问题：
1. **识别**：opp 当前 committed 的 state 是什么（stateName + attackProfile 属性）
2. **外推**：这个 state 会在多少 ms 后发生什么事件（active window、release 等）

**关键设计原则**：prediction layer 只产出纯时间线数据，不做战术判断。`threatLevel`、`canPreempt` 等取决于当前距离、自身动作选择、战斗规则——这些由评分函数算，events 层不越权。

## §2 架构认知

### 预测链四步

```
① Identify          ② Predict Events          ③ Classify            ④ Feed Utility
Opponent Action   → Future Event Timeline   → Threat / Chance   → Score Counter
(opp committed    → (state enter/exit,      → (这个事件是威胁    → #scoreAttack
 stateName +      →  projectile release,   →  还是机会)         → #scoreDefense
 attackProfile)   →  impact, recover end)                      → #scorePositioning
```

现有 throw preemptive cut **手工拼了 ①→②→③**，然后直接调了评分函数。通用化要把这四步变成一个**可扩展的管线**，且 ② 保持中立，③ 由评分层承担。

### 统一预测层：predictedOpponentEvents[]

引入一个中间层，**subsume 现有 throw preemptive 代码路径**（不是并行）。

谁生产：`#buildSituation` 内部新建 `#buildPredictedOpponentEvents()`，根据 opp 当前 committed state + attackProfile 生成

谁消费：Utility 层的 `#scoreAttack` / `#scoreDefense` / `#scorePositioning` / `#evaluateProjectileDefense` 全部从 events 读预测信息，而不是从零散的 Situation 字段

### 数据结构（纯时间线，中立）

```
predictedOpponentEvents[]:  有序数组，按 startMs 升序
  eventType: enum
    "opp_attack_active_window"            // 普通攻击 weaponbox 激活窗口
    "opp_throw_release"                   // 投掷物 release 时刻
    "opp_projectile_arrival_estimate"     // 投掷物预计到达当前距离目标的时刻（简化物理假设）
    // （第一版只产这三种，够了）

  startMs: number        // 距现在多少 ms 开始发生
  endMs: number          // 距现在多少 ms 结束（瞬时事件 startMs === endMs）
  sourceState: string    // 来源 stateName（如 "swing"、"throw_dagger"）

  properties: {          // 原始 attackProfile 字段，评分层按需取用
    startupMs: number,
    activeDurationMs: number,
    recoveryMs: number,
    reach: number,
    // projectile 事件额外：
    projectileType: string,
    cuttable: boolean,
    speed: number,
  }
```

**统一时间基准**：所有事件时间一律表示"从当前决策时刻起，距事件发生还剩多少 ms"。换算：`remainingStartupMs = startupMs - (oppNormTime * totalMs)`，每帧重读 oppNormTime 保证时序最新。优先复用 AIKnowledgeRegistry 已缓存的 timing。

**为什么用数组**：opp 一个 state 可能产出多个事件链（如 throw_dagger → release → projectile_arrival_estimate 两个事件），数组天然支持。上限 5 个 + startMs 超过 2000ms 丢弃。

## §3 实施步骤

### Step 1：B1 — 让 AI 认识 opp 在出什么招

**目标**：`Situation.opp` 从 `{phase, vulnerable, threat}` 扩展到 `{phase, stateName, attackProfile, vulnerable, threat}`

```
现状 → 
  opp: { phase: "startup", vulnerable: 0.3, threat: 0.6 }

Step 1 之后 → 
  opp: { phase: "startup", stateName: "swing", 
         attackProfile: { startupMs: 500, activeMs: 200, recoveryMs: 400, maxReach: 3.0 },
         vulnerable: 0.3, threat: 0.6 }
```

**怎么做**：`#buildSituation` 内部新增一个查询——从 opp 的当前 committed stateName 查 AIKnowledgeRegistry（或 StateGraphDef）拿到 timing + reach 属性，塞进 Situation。这条查询对所有 attack state 都成立（不只是 throw）。

**验收**：AI-Diag log 的 opp 行输出 stateName + startupMs，opp 出 swing 时 startupMs≈500，出 thrust 时 startupMs≈250。

### Step 2a：建立预测事件生成器，先只观测不迁移

**目标**：新增 `#buildPredictedOpponentEvents()`，根据 opp state 生成事件数组，先只写日志验证时间正确，不修改任何评分函数。

```
// opp 正在出 swing → 产 1 个
// { eventType: "opp_attack_active_window", startMs: 300, endMs: 500, sourceState: "swing",
//   properties: { startupMs: 500, activeDurationMs: 200, reach: 3.0 } }

// opp 正在出 throw_dagger → 产 2 个
// { eventType: "opp_throw_release", startMs: 150, endMs: 150, sourceState: "throw_dagger", ... }
// { eventType: "opp_projectile_arrival_estimate", startMs: 364, endMs: 364, sourceState: "throw_dagger", ... }
```

**验收**：
- AI-Diag log 新增 `predictedEvents=[{type, startMs, endMs}]` 行
- swing 的 startMs = startupMs - 已过动画时间（与实际 weaponbox 激活时刻一致）
- throw 的 release startMs 与旧路径的 throwRemainingMs 一致
- projectile arrival startMs 与旧路径的 predictedTTI 一致

### Step 2b：迁移现有 throw preemptive cut 到统一事件层

**目标**：`#evaluateProjectileDefense` 改从 events 里过滤 `opp_projectile_arrival_estimate` 事件，删掉 `sit.predictedProjectileTTI/Cuttable/Distance` 三个孤立字段。

**注意**：reactive 路径（从 `activeProjectileThreats[]` 读 in-flight projectile 实例）保留不动——它来自真实 projectile 对象，不是未来预测，语义不同。

**验收**（回归测试，核心）：
- 玩家抬手扔 dagger（cuttable=true）→ AI 在抬手后半段 commit slash（行为不变）
- 玩家扔 rock（cuttable=false）→ AI 不尝试 preemptive cut（行为不变）
- release 后 reactive cut / dodge 正常接棒（行为不变）

### Step 3：接入通用近身攻击的截击与防御消费

> 这是 Phase 5 核心功能——events 生成了，评分函数要真的用起来。

**#scoreAttack 消费逻辑**（截击判断）：
```
对每个候选攻击，计算 own_active_start = own 剩余 startupMs
找到 opp 的 opp_attack_active_window 事件
if own_active_start < opp_window.startMs  // 我的攻击能在 opp weaponbox 激活前先激活
   AND distance ≤ own.maxReach             // 够得着
   → 给这个 attack 候选加 preemptive bonus
```

**#scoreDefense 消费逻辑**（差异化防御）：
```
找到 opp 的 opp_attack_active_window 事件
根据 opp 攻击类型（swing vs thrust）+ 预计生效时间，调整 guard/dodge/parry 各候选分数
```

**验收**：
- opp 出 swing（startup=500ms）→ AI 出 thrust（startup=250ms，reach 内）→ AI 抢先 commit thrust 截断
- opp 出 thrust（startup=250ms）→ AI 自己最快招 startup=250ms → AI 转防御（来不及截断）

### Step 4：B4 — 近距离 reach 内打断 throw

**目标**：opp 在 attack reach 内抬手扔 projectile → AI 抢先打 opp（hitstun 打断投掷）

**时间条件（修正版）**：
```
从 events 找 opp_throw_release 事件 → 得到 T_release
对每个候选攻击：
  T_my_active = own 剩余 startupMs
  if T_my_active < T_release          // 我的攻击先激活（hitstun 作用于 opp）
     AND distance ≤ own.maxReach       // 够得着 opp
     AND opp throw 状态可被 hitstun 打断
     → preemptive interrupt bonus
```

> 修正说明：原计划用 `throwReleaseMs ≤ ownStartupMs` 判断，方向反了。正确原则是我的攻击先于 release 激活。这里用 active 起点近似 hitstun 生效时刻（与现有战斗系统精度一致）。

**验收**：
- 近距离 reach 内 + 时间充足 → AI 抢先 swing opp 打断投掷
- 近距离 + 时间不足 → AI 不误判赶得上
- 远距离 → 走原有 preemptive cut / reactive 路径

## §4 Post-Phase 5（后移，不阻塞核心交付）

### B5：预测驱动的 positioning

"opp out of reach → advance" 太简化。是否前进取决于敌人 profile、自身攻击范围、opp 时序、策略目标。先让 prediction 对 attack/defense 有明确收益，再单独迭代 positioning。

### B6：predictionAccuracy 旋钮

`oppActionIdentification` / `timingPrecision` / `reactionDelayMs` 是三个不同维度，不应在基础预测层未稳定时一起实现。同一次 opp 动作内误差应保持相对稳定（避免每 tick 随机抖动导致 AI 反复变判断）。保留在 backlog。

| 不做 | 理由 |
|------|------|
| B2 defensePreferences | 独立 backlog，改动极小（加字段 + 一处乘法），本计划聚焦预测层

| AI 自身投掷预测 | Phase 4 还没做 AI throw，暂时不需要 |

## §5 预期收益

| 维度 | 收益 |
|------|------|
| **防御差异化** | AI 能针对 opp 招式类型选择不同防御策略（swing 想截断、thrust 赶不上就只防御）|
| **近距离反制** | reach 内抬手 → 抢先打断投掷（B4），填补现有物理边界 |
| **角色个性表达** | predictionAccuracy 旋钮让"敏锐老江湖"vs"迟钝新手"变成可配置差异 |
| **代码收敛** | 删除 throw preemptive 硬编码路径，统一走 events 管线，后续加新 attack state 自动获得预测能力 |
| **为 Phase 6 铺路** | 未来想加 counter-attack、parry 时机选择等高级行为，都可以直接消费 events 数组 |

## §6 依赖与风险

| 风险 | 缓解 |
|------|------|
| StateGraphDef 不一定暴露所有 attack state 的 timing 属性 | AIKnowledgeRegistry 扫描时已缓存 timing（Phase 4 做的），Step 1 直接复用 |
| 统一层搭建过程中现有 throw preemptive 行为退化 | Step 2 必须有回归验收（玩家扔 dagger → AI 行为不变） |
| events 数组大小膨胀（每个 state 可能产多个事件） | 上限 5 个事件 + predictedMs 超过 2000ms 的事件丢弃（太远的未来不关心） |
| Utility 层改动面广（四个评分函数都要读 events） | 逐步迁移：先 projectile evaluator 切 events → 再 #scoreAttack → 再 #scoreDefense/Positioning |
